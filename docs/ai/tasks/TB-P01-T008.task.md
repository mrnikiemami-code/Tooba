Design a canonical key builder.

Cache keys must be explicit about relevant context.

Potential dimensions:

```text
Edition
DeploymentId
TenantId where applicable
Market
Locale
Currency
Theme
User or authorization scope where applicable
Resource type
Resource id
Version/revision
```

Do NOT include every dimension blindly.

Only include dimensions that affect a cached value.

Hard rules:

```text
Tenant-specific value must include TenantId
Market-specific value must include Market
Locale-specific value must include Locale
Currency-specific value must include Currency
```

Preserve:

```text
Locale != Market != Currency != Tax Jurisdiction
```

## 8. Tenant Isolation

For SingleStore:

```text
Tenant A cache entry
!=
Tenant B cache entry
```

even when both use identical resource identifiers.

No implicit default tenant.

No host-derived key inside low-level cache provider.

The caller/context layer should supply durable TenantId.

Marketplace must not fake SingleStore TenantId.

---

## 9. Edition / Deployment Scope

The same logical key must not accidentally collide across:

```text
Marketplace
SingleStore
different deployments/environments
```

Establish appropriate Edition/Deployment prefixing.

Do not include machine name.

---

## 10. Key Normalization

Cache keys must be deterministic.

Avoid unsafe arbitrary object `ToString()` key generation.

Prefer controlled typed segments.

Handle:

```text
case normalization where semantically required
separator escaping
null/optional dimensions
length constraints
```

Do not place secrets or PII in raw cache keys.

---

## 11. GetOrCreate / Stampede Protection

Implement an in-process anti-stampede mechanism for the initial provider.

Concurrent requests for the same cache key should not all execute the expensive factory simultaneously.

A per-key async lock/single-flight approach is acceptable.

Hard rules:

```text
no global lock
no lock across unrelated keys
respect CancellationToken
do not cache failed factory result
```

Document that distributed stampede protection will need Redis/distributed locking or equivalent later.

---

## 12. Expiration Policy

Support at minimum:

```text
absolute expiration
sliding expiration where justified
```

Do not hard-code one global TTL.

Callers/policies must choose explicit durations.

No infinite caching by default for mutable data.

---

## 13. Cache Policy Abstraction

Provide a minimal policy object/value type if useful.

Conceptually:

```text
CachePolicy
```

with safe options such as:

```text
AbsoluteExpiration
SlidingExpiration
Tags
```

Do not overbuild stale-while-revalidate unless already justified.

---

## 14. Negative Caching

Do not globally cache `not found`.

If abstraction allows negative caching, it must be explicit and short-lived.

Do not cache authorization failures.

Do not cache transient infrastructure errors.

---

## 15. Authorization-Sensitive Data

Hard rule:

```text
authorization-sensitive cached output
must include appropriate authorization/user/scope dimension
or must not be cached.
```

Do not create a general user cache model yet.

Document the rule.

SpiceDB integration is out of scope.

---

## 16. Tag / Namespace Invalidation

Provide a durable invalidation seam.

Preferred concept:

```text
tags
namespaces
version tokens
```

Examples for future use:

```text
catalog:product:{id}
catalog:category:{id}
pricing:offer:{id}
tenant:{tenantId}:theme
```

Do not implement business-specific tags now.

Initial memory provider may maintain tag-to-key tracking safely.

Future Redis implementation may use a different internal technique.

Business code must not depend on provider-specific implementation.

---

## 17. Invalidation Semantics

Document:

```text
write/update/delete
→ invalidate relevant cache entries
```

Cache invalidation must be explicit.

Do not rely only on TTL for correctness-sensitive data.

Future event-driven invalidation may use MassTransit integration events.

Do NOT implement business event handlers in this task.

---

## 18. Versioned Keys

Support version/revision segments where useful.

This is especially valuable for:

```text
content
theme
SEO config
catalog projections
```

Do not force versioning onto every key.

---

## 19. Serialization Boundary

Initial in-memory cache may store typed objects directly.

Future distributed cache will need serialization.

Therefore document:

```text
cached contracts should be serialization-safe
do not cache EF tracked entities
do not cache HttpContext/request objects
do not cache DbContext
```

Do not introduce JSON serialization yet unless needed.

---

## 20. No EF Tracked Entities

Hard rule:

```text
never cache tracked EF entities
```

Cache immutable/read DTOs/projections/value objects instead.

Document this near the abstraction.

---

## 21. Async API

Cache APIs should be async-first where factory work is async.

Do not create fake async wrappers around purely synchronous operations unnecessarily.

Support `CancellationToken`.

## 24. Failure Behavior

Initial memory provider should not introduce infrastructure failures.

Future distributed providers must be allowed to fail-open or fail-closed based on cache usage semantics.

Document that:

```text
cache is optimization
business truth must remain retrievable from authoritative source
```

Do not create business fallback logic now.

---

## 25. Thread Safety

Implementation must be safe under concurrent requests.

Tag maps, lock maps, and invalidation structures must not race or leak unbounded memory.

Clean up per-key lock entries when no longer needed where practical.

---

## 26. Size / Memory Safety

Configure reasonable in-memory safeguards.

If using `SizeLimit`, define a consistent size contract.

If not using it, document why and provide a future operational seam.

Do not allow tag maps to grow forever after entries expire.

Eviction callbacks may be used to clean reverse indexes.
