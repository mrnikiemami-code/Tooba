PART C — DEFINE MIGRATION EXECUTION MODEL

Create a clear production model.

Required principles:

Application startup != production migration orchestration

Production migration must be explicit.

Support at minimum:

PLAN
APPLY
STATUS

Recommended semantics:

PLAN
→ inspect pending migrations
→ no write

STATUS
→ show current/pending state

APPLY
→ apply pending migrations safely

Do not expose destructive reset/drop operations.

PART D — MARKETPLACE EDITION

Marketplace has one operational marketplace DB.

Migration runner must:

resolve correct marketplace connection

apply only module-owned migrations

process modules deterministically

stop safely on failure

return actionable exit code

avoid partial silent success

Document exact ordering policy.

Do not add cross-module SQL.

PART E — SINGLE-STORE EDITION

Single-Store:

one shared publish

tenant resolved independently from hostname at migration time

database per tenant/store

Migration runner must support safe target selection:

single tenant
explicit tenant set
all configured tenants

Default behavior must NOT accidentally migrate every tenant without explicit command/flag.

Require:

tenant identity displayed safely

connection secret not printed

per-tenant success/failure isolated and reported

predictable retry behavior

PART F — MODULE OWNERSHIP

Each module migration must remain module-owned.

Forbidden:

one mega DbContext migration for all modules

cross-module schema mutation

foreign-module migrations

table manipulation outside owning module

Create:

03-module-migration-ownership-map.md
PART G — MIGRATION RUNNER IMPLEMENTATION

Implement the smallest correct operational tool.

Preferred forms:

dedicated console/host project

explicit command in existing operational CLI

repository-supported .NET tool pattern

Do NOT make this a hidden web endpoint.

Production migration execution must not be exposed as an unauthenticated HTTP route.

Expected commands may resemble:

status
plan
apply

Actual command names can match repository conventions.

PART H — SAFETY CONTROLS

Required:

no DropDatabase
no EnsureDeleted
no destructive dev reset
no production seed mutation unless explicitly designed
no automatic all-tenant migration by default
no secret logging
no connection string echo

If pending destructive migration is detectable:
surface warning and fail unless repository has explicit approval mechanism.

Do not invent a fake SQL parser if EF does not expose reliable classification.
Document actual limits honestly.

PART I — LOCK / CONCURRENCY SAFETY

Prevent two migration runners from applying the same DB concurrently.

Use a safe mechanism appropriate to PostgreSQL, preferably one of:

advisory lock

migration history concurrency protections

explicit application-level lock

Do not rely only on "operators won't run twice".

Document:

lock scope

timeout

failure behavior
