## Locked Principles

Preserve:

```text
HTTP/API boundary != Domain/Application
Authentication != Authorization
public error != internal diagnostic
refresh credential != access/session handle
```

Do not expose EF entities.

Do not expose raw internal exception messages.

## API Surface

Create a minimal versioned authentication API boundary.

Exact route style may follow repository conventions.

Support at minimum:

```text
register
login
refresh
logout current session
logout/revoke all sessions
request password reset
complete password reset
request identifier verification
complete identifier verification
change password
current authenticated session/user
```

Do not add unrelated profile/customer endpoints.

## Request/Response Contracts

Use explicit DTO/contracts.

Never return:

```text
password hash
refresh hash
OTP hash
reset hash
SecurityStamp
internal DB ids not required by contract
```

Raw refresh secret may be returned only at issuance/rotation boundary where required.

## Access Session Boundary

Use the session-handle/access boundary from T004.

Do not invent custom JWT crypto.

If HTTP authentication requires a bearer/session token, keep it opaque and validated through Identity-owned session infrastructure.

Document future cookie/BFF/JWT/IdP adaptation seam.

## Authentication Middleware / Principal

Provide a clean request-authentication mechanism that resolves a valid session into a principal/current-user context.

Expose stable:

```text
UserId
SessionId
Tenant/Edition context
```

to application/use-case layers.

Do not parse authorization relationships here.

Do not call SpiceDB just to authenticate.

## Tenant Safety

SingleStore authentication requests must use existing trusted TenantContext.

Do not accept tenant authority from:

```text
X-Tenant-Id
query parameter
client cookie
request body tenant id
```

Marketplace remains distinct.

No Host parsing inside Identity application code.

## Login

Login accepts a typed/login identifier input plus password.

Public failure should avoid obvious account enumeration.

On success:

```text
create session
issue access/session handle
issue refresh credential
```

Do not leak whether the identifier exists when credentials are invalid.

## Refresh

Refresh endpoint must:

```text
validate opaque refresh secret
rotate
return new refresh secret
reject reuse/revoked/expired session
```

Old refresh secret must become unusable.

Do not return internal reuse-detection details publicly.

## Logout

Support:

```text
revoke current session
revoke all sessions
```

Current-session logout should be idempotent where practical.

## Password Reset

Request endpoint must remain enumeration-safe.

Complete endpoint must:

```text
validate challenge
apply password policy
change credential
consume challenge
apply revocation/security-stamp policy
```

Do not expose raw DB/account state.

## Identifier Verification

Support Email/Phone verification endpoints using durable challenge system.

Do not mark verified before successful challenge consumption.

## Password Change

Require authenticated session + current password.

Apply existing lifecycle policy.

Do not allow an unauthenticated caller to use password-change endpoint as reset.

## Rate-Limit Seam

Do not implement full anti-abuse product.

But expose a clean boundary/metadata for future rate limiting on:

```text
login
refresh
reset request
verification request
challenge verify
```

Do not hard-code IP-only identity.

## CSRF / Browser Safety

If cookies are introduced, CSRF/SameSite/secure-cookie policy becomes mandatory.

If this task remains bearer/session-handle based, document that browser-cookie protection is deferred until cookie transport is selected.

Do not create insecure default cookies.

## ProblemDetails

Use existing centralized ProblemDetails.

Map safely:

```text
invalid credentials -> generic auth failure
expired/revoked session -> 401
forbidden authorization is NOT handled here
invalid/expired challenge -> safe 400/401-style contract as appropriate
validation error -> 400
unexpected -> 500
```

Do not leak account existence or stack traces.

## OpenAPI / Contract Clarity

If OpenAPI is already available, expose minimal route metadata.

Do not introduce a large Swagger stack solely for this task unless justified.

Document public contracts clearly.

## Tests — Mandatory

Add HTTP/integration tests covering at minimum:

