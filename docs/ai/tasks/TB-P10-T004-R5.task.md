Title:
Manual Payment Review Reservation Lifecycle — Preserve Inventory Between Customer Proof Submission and Admin Confirmation

Architect Review

Manual runtime testing exposed a real lifecycle gap.

Observed order:
TB-20260912010851-01-456f7b

Behavior:

customer selected manual/card-to-card payment

customer submitted payment tracking/proof

Order remained PendingPayment

Cart reservation still followed short Cart TTL

expiry worker released reservation

later Admin confirm_deposit attempted CommitForPaidOrder

reservation was already Released

Admin received inventory.reservation.not_active

This is NOT acceptable as the normal manual-payment business flow.

A customer who has submitted a payment transfer for review must not lose the Order inventory merely because the original Cart TTL expires before Admin reviews the payment.

Do NOT fix by bypassing Inventory Consume/Commit.

2. Locked Business Semantics

Reservation phases must be distinct:

A. Cart / Checkout hold

Short TTL.
Used before Order/manual payment submission.

B. Manual Payment Review hold

Once customer successfully submits required manual/card-to-card payment reference/proof:

Order already exists

customer claims payment was made

reservation must no longer use Cart TTL

reservation ownership/expiry semantics transition to a payment-review hold

C. Paid Order reservation

When Admin confirms:

review hold transitions/commits to durable paid-order reservation

no expiry under Cart TTL

D. Rejected/expired manual payment

Reservation releases according to explicit manual-payment policy, not old Cart TTL.

3. Manual Review Hold Policy

Use the smallest existing architecture-compatible implementation.

Preferred:

same active Held reservation

replace Cart ExpiresAt with a dedicated manual-review expiration deadline

Introduce/reuse Store/payment-method configuration equivalent to:
ManualPaymentReviewHoldMinutes/Hours

Use a safe default only if current configuration framework requires one; document it.

Do NOT make it indefinite unless current product/business policy explicitly supports indefinite inventory locks.

Recommended commercial default if no policy exists:
24 hours, configurable per manual payment method/store.

But implementation must follow existing configuration patterns.

4. Inventory-Owned Transition

Add/reuse Inventory-owned operation, semantic equivalent:

PromoteReservationForManualPaymentReviewAsync(...)

Requirements:

Inventory owns mutation

idempotent

decimal-safe

no foreign-module SQL

Manual proof submission must invoke this transition only after proof/reference validation succeeds.

5. Admin Confirm

When Admin confirms manual payment:

If review reservation is still active:

commit reservation to durable paid-order semantics

ExpiresAt = null or canonical equivalent

Payment -> Succeeded

forward fulfillment allowed

Admin confirm must NOT depend on original Cart TTL.

6. Admin Reject

When Admin rejects:

manual payment attempt becomes rejected

active review reservation releases according to current retry policy

If customer may retry manual payment on SAME Order:
choose one canonical behavior and document it.

Preferred safe model:

rejection releases current review reservation

customer retry must reacquire inventory authoritatively

if reacquire succeeds, new manual review hold is created

if insufficient stock, retry submission cannot proceed as normal and must show localized inventory-unavailable resolution

Do NOT keep inventory held forever through unlimited rejected retries.

7. Review Hold Expiry

When manual-payment review deadline expires before Admin confirms:

expiry worker releases the review hold

reservation remains historical Released

Admin confirm must NOT resurrect it

If Admin later attempts Confirm:

system should attempt authoritative reacquire if current business policy permits

if reacquire succeeds:

bind new reservation

commit paid-order reservation

then Payment may become Succeeded

if reacquire fails:

do NOT show generic reservation.not_active as normal business UX

move payment/order into explicit manual-resolution state or return stable actionable error such as:
موجودی این سفارش در زمان بررسی پرداخت دیگر در دسترس نیست. لطفاً وضعیت سفارش و بازگشت وجه را بررسی کنید.

Do not silently confirm payment without inventory.

8. Important UX Rule

Normal Admin flow:
Customer submits valid manual payment -> Admin reviews within configured review window -> Confirm should succeed.

Admin should not be told merely:
رزرو موجودی این سفارش دیگر فعال نیست

for the normal within-review-window case.

That error is only a defensive exception.
