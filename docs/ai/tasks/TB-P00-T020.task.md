## Objective

Design Tooba's caching and infrastructure-abstraction architecture deeply enough to support:

- initial deployment without Redis;
- future Redis adoption without domain redesign;
- tenant-safe caching;
- locale / market / currency / sales-channel aware caching;
- theme-aware caching;
- public vs private/user-scoped cache separation;
- server-side response/data caching;
- invalidation/versioning;
- event-driven invalidation;
- cache stampede protection;
- negative caching where safe;
- search/content/catalog/media/pricing/inventory cache distinctions;
- provider-swappable infrastructure;
- graceful degradation;
- future microservice extraction;
- professional UI/UX performance without stale/security-broken data.

This task is architecture documentation only.

Do not install Redis, caching packages, distributed locks, message brokers, CDN providers, or implement cache code.

# A. Core Principle

Hard rules:

```text
Cache != Source of Truth
Cache != Authorization Truth
Cache != Payment Truth
Cache != Inventory Reservation Authority
```

Cache is an optimization layer.

System correctness must not depend on cache containing the only copy of business truth.

---

# B. Initial vs Future Infrastructure

Confirmed direction:

```text
Initial:
no Redis required
```

Future:

```text
Redis or another distributed cache may be added
```

Hard architectural requirement:

```text
Business/domain modules must not depend directly on Redis APIs.
```

Use internal cache abstractions/ports.

No vendor choice now.

---

# C. Cache Abstraction

Design conceptual contracts such as:

```text
ICache
ICacheReader
ICacheWriter
ICacheInvalidator
```

or equivalent.

Avoid leaking:

```text
Redis key types
Redis transactions
vendor-specific TTL semantics
```

into domain/application contracts.

Do not implement interfaces.

---

# D. Cache Categories

Separate cache types conceptually:

```text
Request-local cache
In-process memory cache
Distributed cache
CDN/edge cache
Browser cache
Search/read-model cache
Derived asset cache
```

Do not treat all caches as equivalent.

Each has different consistency/security/invalidation semantics.

---

# E. Cache Ownership

Caching policy belongs near the application/read-model/infrastructure boundary.

Domain entities should not call cache services directly.

Modules may define:

```text
what may be cached
what dimensions affect correctness
what invalidates it
```

Infrastructure decides backend.

---

# F. Key Dimensions

Cache keys must include all dimensions that materially change data.

Potential dimensions:

```text
TenantId
Deployment/Edition
Locale
Market
Currency
SalesChannel
Theme
Buyer/Organization/Contract
Seller
User/Identity where private
Authorization scope/version
EntityId
Query/filter/sort
Version
```

Do not mechanically include all dimensions everywhere.

Require explicit cache-context design per use case.

---

# G. Tenant Isolation

Single-Store:

No cache entry may be shared across tenants unless explicitly platform-global and safe.

Hard rule:

```text
missing TenantId in a tenant-varying cache key = security/correctness defect
```

Marketplace uses deployment/seller/resource scope as appropriate.

Do not use hostname as canonical tenant identity.

---

# H. Locale / Market / Currency

Preserve:

```text
Locale != Market != Currency
```

Examples:

- localized category title varies by Locale;
- price varies by Market/Currency;
- commercial availability may vary by Market;
- formatting may vary by Locale.

Do not cache a universal product page fragment if those contexts change output.

---

# I. Theme-Aware Caching

Single-Store tenants may have runtime themes.

Cache/rendered output may vary by:

```text
Tenant
ThemeId
ThemeVersion
Locale
Page Composition Version
```

Do not allow one tenant's visual/branding output to leak into another tenant.

Theme changes must invalidate/version relevant caches.

---

# J. Public vs Private Cache

Separate:

```text
public anonymous content
authenticated user data
authorization-scoped data
customer order/account data
seller/admin data
```

Hard rule:

Private/user-scoped data must never enter a shared public cache key.

Do not cache authenticated HTML/API responses publicly by accident.

---

# K. Authorization-Aware Caching

Authorization decisions may be cached only conservatively.

Need to consider:

```text
subject
resource
permission
tenant
relationship/version token
TTL
revocation risk
```

Security-sensitive operations may bypass authorization cache.

SpiceDB remains authority.

Do not create a broad:

```text
user:{id}:permissions
```

cache with unbounded/stale semantics.

---

# L. Catalog Caching

Catalog descriptive reads are relatively cache-friendly.

Potential invalidators:

```text
Product changed
Variant changed
Category changed
Brand changed
translation changed
publication status changed
```

Catalog cache must not absorb Pricing/Inventory truth into one stale object unless using explicit composite read model versioning.

---

# M. Pricing Caching

Pricing is highly contextual.

Cache keys may require:

```text
Offer
Market
Currency
SalesChannel
Buyer/Organization/Contract
Quantity bucket
Promotion context
PricingVersion
```

Hard rule:

Do not use:

```text
product:{id}:price
```

as universal key.

Critical checkout price still revalidated/quoted by Pricing authority.

---

# N. Inventory Caching

Inventory/availability changes quickly.

Safe cache uses may include:

```text
display availability projection
short-lived ATS read
```

But:

```text
reservation decision
oversell decision
```

must not be made from stale cache alone.

No cached reservation acceptance.

---

# O. Search Caching

Search result cache dimensions may include:

```text
Tenant
Locale
Market
Currency/display context
query
filters
sort
page/cursor
SalesChannel
```

Personalization later may reduce cacheability.

Search cache does not become source truth.

---

# P. Content / Page Composition Caching

Published content/composition is highly cacheable.

Need invalidation/versioning for:

```text
publish/unpublish
revision change
section config change
schedule activation
locale variant change
theme change
```

Preview/draft content must not contaminate public cache.

---

# Q. Media / CDN Caching

Derived media variants should prefer immutable/versioned URLs.

Use long-lived browser/CDN cache where possible.

Asset replacement should produce:

```text
new version / URL identity
```

rather than relying only on purge.

Media cache strategy remains separate from application data cache.

---

# R. SEO / Rendered Page Caching

SEO-critical rendered pages may be cached when deterministic for context.

Need dimensions such as:

```text
Tenant
Locale
Market where route differs
Theme
Page/Content version
```

Do not serve wrong canonical/hreflang/structured data because of insufficient cache key dimensions.

---

# S. User Dashboard Caching

Customer/Seller/Admin dashboards may cache aggregates/read models.

Must preserve:

```text
user/subject scope
tenant
authorization scope
date/filter context
freshness
```

Private dashboard cache must never be shared across users or tenants.

---

# T. TTL vs Versioning

Do not use TTL as the only invalidation strategy.

Combine where appropriate:

```text
TTL
event-driven invalidation
versioned keys
immutable versioned resources
explicit purge
```

TTL is a safety net, not always primary correctness mechanism.

---

# U. Event-Driven Invalidation

Candidate events:

```text
ProductChanged
PriceChanged
InventoryChanged
ContentPublished
ThemeChanged
PermissionChanged
SellerChanged
```

may trigger invalidation/projection refresh.

Do not finalize event names.

Invalidation should be idempotent.

---

# V. Versioned Keys

Preserve use of versions such as:

```text
ProductVersion
PricingVersion
ThemeVersion
ContentRevision
SearchIndexVersion
AuthorizationVersion token
```

where useful.

Versioned keys can reduce difficult purge fan-out.

Do not create global monotonically increasing version for every change by default.

---

# W. Cache Stampede Protection

Popular keys may expire simultaneously.

Preserve strategies such as:

```text
single-flight/request coalescing
soft TTL
stale-while-revalidate
jitter
lock only where necessary
```

Do not introduce distributed locks as default solution.

---

# X. Stale-While-Revalidate

For safe public/read-only content, SWR may improve UX/performance.

Not appropriate for all data.

Good candidates:

```text
content
catalog description
public landing
non-critical aggregates
```

Bad candidates for unbounded stale use:

```text
authorization
payment status
inventory reservation
checkout price
```

---

# Y. Negative Caching

May be useful for:

```text
missing slug
missing product
unsupported locale route
```

But must be short/bounded where objects may soon be created.

Do not negative-cache authorization denial or payment errors casually.

---

# Z. Cache Failure Behavior

Hard principle:

```text
Cache backend failure should usually degrade to source reads, not break commerce.
```

Exceptions may exist for deliberate rate/protection architecture later.

No business write should be lost because cache is unavailable.

---

# AA. Cache Penetration / Abuse

Protect source systems from repeated requests for nonexistent or expensive keys.

Possible techniques:

```text
negative caching
request coalescing
rate limiting
bounded query complexity
```

Do not use probabilistic filters unless justified later.

---

# AB. Cache Invalidation Reliability

Invalidation events may be lost/delayed.

Need:

```text
TTL safety net
versioning
reconciliation
rebuild
idempotent invalidation
```

System must converge.

---

# AC. Warmup

Avoid requiring full cache warmup before application can function.

Optional warmup may improve:

```text
top categories
homepage
popular products
tenant config
```

but cold cache must remain correct.

---

# AD. Tenant Configuration Cache

Tenant registry/config/theme references may be cached.

Security-sensitive:

```text
tenant status
canonical domain
connection reference metadata
```

must respect fail-closed rules from tenant architecture.

Do not cache raw DB credentials in unsafe general-purpose caches.

---

# AE. Connection / Secret Abstractions

Infrastructure abstractions should preserve:

```text
ITenantConnectionResolver
secret/config reference
provider-neutral secret access
```

Business modules must not own connection-string selection.

No implementation.

---

# AF. Clock / Time Abstraction

Consider an internal time provider for deterministic business/application testing.

Do not scatter direct wall-clock calls through domain logic if time affects:

```text
price validity
promotion validity
reservation expiry
content schedule
token/session expiry
```

Exact implementation deferred.

---

# AG. ID Generation Abstraction

If UUID v7 or another ID scheme is later locked by ADR, generation should be centralized behind stable primitive/service where appropriate.

Do not let modules invent inconsistent ID formats.

Current scheme remains governed by existing ADR/SoT status; do not silently alter it.

---

# AH. External HTTP Client Abstraction

External providers such as:

```text
Payment
FX
SMS/Email
AI
CDN
Storage
Search
```

need controlled HTTP/provider clients with:

```text
timeouts
retry policy
circuit behavior
telemetry
idempotency awareness
```

Vendor clients stay behind adapters.

Do not build a single god HTTP wrapper.

---

# AI. Retry Policy

Retry only transient failures.

Hard rule:

```text
Retry != universal error handling
```

Do not blindly retry:

```text
validation errors
authorization denial
payment declined
business conflicts
non-idempotent operations
```

Retry policy belongs near infrastructure operation with idempotency awareness.

---

# AJ. Timeout Policy

Every external call must have bounded timeout policy.

Avoid default infinite/uncontrolled waits.

Timeouts should be operation-specific.

Exact numbers later.

---

# AK. Circuit Breaker / Resilience

Preserve resilience patterns where useful:

```text
timeout
retry
circuit breaker
bulkhead
fallback
```

Do not require all patterns everywhere.

Optional dependencies such as AI may degrade gracefully.

Critical dependencies may fail readiness.

---

# AL. Message Bus Abstraction

Do not require broker initially.

Architecture may support:

```text
in-process integration events
database outbox
future broker
```

Do not create a fake distributed bus abstraction that hides critical delivery semantics.

Document clear event/transport boundary.

---

# AM. Background Job Abstraction

Background processing may include:

```text
scheduled content

media processing
analytics aggregation
reconciliation

AI index rebuild
```

Need:

```text

retry
observability
```

No scheduler/provider selected.

---

# AN. File/Object Storage Abstraction

Already referenced by Media.

Ensure infrastructure layer supports provider-neutral object storage without exposing vendor types to business modules.

No duplicate competing abstraction.

---

# AO. Email / SMS / Notification Providers

Future notifications should use adapters.

Identity OTP delivery may consume notification/provider contracts but should not depend on one SMS vendor.

Do not design Notification domain fully unless already scoped elsewhere.

---

# AP. Feature Configuration

Preserve distinction:

```text
business configuration
tenant configuration
feature flag
runtime operational configuration
secret
```

Do not store secrets in generic config.

Do not scatter direct environment-variable reads through domain code.

---

# AQ. Feature Flags

Future feature flags may help safe rollout.

Do not use flags to permanently encode edition architecture or bypass domain invariants.

Flags are rollout/operational mechanisms, not substitute for composition/policy architecture.

---

Marketplace vs Single-Store differences should remain in:

```text
configuration
deployment
```

not cache/infrastructure `if` statements spread across modules.

Infrastructure abstractions should work for both editions.


# AW. Serialization / Compatibility

Distributed caches require version-compatible payloads.

Preserve:

```text
schema/version field
backward-compatible reader where needed
safe invalidation on deployment
```

Do not cache full ORM/domain entities as opaque serialized objects by default.

Prefer stable read-model/cache DTOs.

---

# AX. Deployment / Rolling Upgrade

Cache key/version strategy must tolerate mixed application versions during rolling deployment in future.

Do not assume entire fleet switches atomically.

Exact deployment model later.

# AY. UI / UX Performance

Future performance goals should support:

```text
fast category/product pages
fast search
fast admin dashboards
responsive seller workflows
low-latency navigation
stable loading states
```

Do not use stale caches to hide fundamentally bad query/read-model design.

# BD. Decision Summary

Classify:

```text
RECOMMENDED_FOR_ADR
NEEDS_LATER_P00_DETAIL
DEFERRED
```

At minimum recommend:

1. Cache is optimization, never business truth.
2. Initial system does not require Redis.
3. Redis/distributed cache remains addable behind internal abstraction.
4. Cache policy is use-case/read-model aware, not domain-entity-driven.
5. Tenant isolation is mandatory in all tenant-varying cache keys.
6. Locale/Market/Currency/Theme/User dimensions are explicit where relevant.
7. Public and private caches are strictly separated.
8. Authorization caching is conservative and revocation-aware.
9. Pricing/Inventory critical decisions always revalidate at authority.
10. TTL alone is insufficient; versioning/event invalidation are supported.
11. Stampede protection is first-class for hot keys.
12. Cache failure normally degrades to source reads.
13. Immutable/versioned Media/CDN URLs are preferred.
14. Cached payloads use stable/versioned read DTOs, not raw domain entities.
15. Shared-hosting deployment works without heavyweight infrastructure.
16. Dedicated-hosting evolution adds infrastructure without domain redesign.
17. Retry/timeout/resilience are infrastructure concerns with idempotency awareness.
18. Feature flags do not replace edition/composition architecture.
19. Cache observability integrates with OpenTelemetry.
20. Performance optimization must preserve correctness, privacy and professional UI/UX.

Do not create final ADR yet.
