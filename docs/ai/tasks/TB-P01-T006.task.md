## 1. Domain Event Abstraction

Add in BuildingBlocks (no EF, no ASP.NET):

```text
IDomainEvent
```

A Domain Event is an internal fact inside one module boundary.

It is raised during a local use-case and collected before `SaveChanges`.

It is not a public contract.

It is not automatically an Integration Event.

---

## 2. Integration Event Abstraction

Add:

```text
IIntegrationEvent
```

An Integration Event is a versioned externalized fact for other modules or future remote consumers.

Only explicitly translated Domain Events become Integration Events.

Do not auto-publish every Domain Event.

---

## 3. Event Metadata

Define durable metadata, conceptually:

```text
EventId
OccurredAt
EventType
CorrelationId
Version
TenantId?
DeploymentId
Edition
```

`EventId` is the stable identity used as the Outbox row key.

`TenantId` is the durable tenant identity, never derived from HTTP Host by the worker.

`Edition` and `DeploymentId` are reconstructed from the durable row plus the config registry.

---

## 4. Domain Event Collector

Provide composition, not forced entity inheritance:

```text
IDomainEventCollector
IHasDomainEvents
```

Entities may compose a collector. Composition/interface-based collection is acceptable.

Do not require a shared base entity class.

---

## 5. Domain Event != Integration Event

Hard rule:

```text
Domain Event != Integration Event
```

A Domain Event may stay internal.

A Domain Event is published as Integration only through a registered translation.

PlatformProbe must prove both:

```text
translated domain event → outbox row
untranslated domain event → no outbox row
```

---

## 6. Outbox != Message Broker

Hard rule:

```text
Outbox != Message Broker
```

`SaveChanges` persists outbox rows in the same local module transaction.

The dispatcher later claims and publishes.

Consumers are never invoked from `SaveChanges`.

This is not MassTransit, RabbitMQ, Kafka, Azure Service Bus, or any broker product.

---

## 7. Module-Owned Outbox

Each module owns:

```text
schema.outbox_messages
```

No shared mega outbox table for all modules.

No cross-module transaction.

The CLR row type may be reused. The physical table is mapped per module schema.

Host composes registrations. Host does not own probe tables.

---

## 8. Transactional Outbox

Collect domain events during the local unit of work.

Map only registered translations to Integration Events.

Insert outbox rows in the same `SaveChanges` transaction.

Clear collected events only after successful save.

Rollback must leave no outbox row.

---

## 9. Event Translation

Register explicit Domain → Integration translations.

Unregistered Domain Events are not written to Outbox.

Do not invent a global reflection publisher.

Do not treat CLR type names as public contracts.

---

## 10. SaveChanges Interceptor

Implement an interceptor or SaveChanges helper that:

```text
collects domain events from tracked entities / collectors
applies only registered translations
writes outbox rows in the same transaction
never calls consumers
clears events after successful save
```

Do not call `IIntegrationEventHandler<T>` from the interceptor.

---

## 11. Domain Event Collection Policy

Collection must be explicit and local to the module aggregate/entity.

Do not scan the entire process.

Do not require a shared ToobaEntity base class.

Composition/interface-based collection is acceptable.

---

## 12. Outbox Message Shape

Persist at least:

```text
Id
OccurredAt
EventType
Payload
CorrelationId
Version
TenantId
DeploymentId
Edition
ProcessedAt
AttemptCount
NextAttemptAt
DeadLetteredAt

```

`LastError` must not contain secrets, stack traces, or payload.

Tenant/Edition/DeploymentId must be stored as durable columns so the worker does not read Host.

---

## 13. Dispatcher Store / SKIP LOCKED

Add:

```text
IOutboxDispatcherStore
```

Claim pending rows with raw PostgreSQL:

```text
FOR UPDATE SKIP LOCKED
```

Claiming must be safe under concurrency.

One worker must not process a row already claimed by another.

---

## 14. In-Process Publisher

Add:

```text
IIntegrationEventPublisher
InProcessIntegrationEventPublisher
```

This publisher is in-process only.

No broker package.

No MassTransit.

No RabbitMQ client.

Delivery is at-least-once. There is no exactly-once assumption.

---

## 15. Integration Event Handlers

Add:

```text
IIntegrationEventHandler<T>
```

Handlers run after a successful claim, not during `SaveChanges`.

Handlers must be idempotent or later use Inbox.

Do not assume global order across tenants, modules, or databases.

---

## 16. Hosted Dispatcher

Add a HostedService / background dispatcher.

Read from `Tooba:Outbox`:

```text
poll interval
batch size
retry base delay
max attempts
```

The dispatcher claims, deserializes via explicit type map, publishes, then marks processed.

On failure: increment attempt, set `NextAttemptAt`, sanitize `LastError`.

After max attempts: dead-letter.

---

## 17. Retry

Retry is exponential or base-delay based from configuration.

Retry must not busy-loop.

Retry must not reuse a poisoned payload interpretation as a reason to log secrets.

At-least-once means handlers may see duplicates.

---

## 18. Dead Letter

When `AttemptCount` exceeds max attempts, mark dead-letter.

Dead-lettered rows must not be reclaimed by the normal poll.

Do not delete payload as a substitute for dead-letter.

Do not expose payload on a public API in this task.

---

## 19. Serialization

JSON with an explicit event-type map.

No unsafe polymorphic CLR deserialization.

Forbidden:

```text
TypeNameHandling
Type.GetType on payload
AssemblyQualifiedName as EventType
$discriminator dumping arbitrary CLR
```

`EventType` is a registered contract name such as:

```text
platform_probe.record_created.v1
```

Metadata used by the worker must come from durable columns, not from spoofable payload fields.

---

## 20. Tenant-Aware Worker

Hard rule:

```text
Worker must NOT resolve tenant from Host
```

Reconstruct:

```text
Edition
TenantId
DeploymentId
```

from the durable outbox row plus the existing config registry / connection resolver.

Do not invent a second tenant-resolution product.

Reuse T003/T004:

```text
Host → TenantContext → ConnectionReference → IDatabaseConnectionResolver
```

is for HTTP. The worker uses durable message identity, not Host.

---

## 21. Single-Store and Marketplace Polling

Single-Store:

```text
enumerate Active configured tenants
resolve ConnectionReference
poll each database separately
one tenant failure must not corrupt another
no cross-tenant DbContext / connection reuse
```

Marketplace
→ poll module outbox per tenant
database only. Do not invent fake Single-Store tenants.

Poll targets are the module-owned `outbox_messages` tables inside each resolved database.

## 22. Inbox Seam

If a full Inbox table is too large for this task, add only a documented seam:

```text

```

or equivalent interface plus architecture notes.

Do not pretend Outbox is Inbox.

Outbox is producer-side durability.

Inbox is consumer-side idempotency and is deferred unless a tiny seam is required.
