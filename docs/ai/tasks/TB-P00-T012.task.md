# A. Core Separation

Define:

```text
Order
Payment
Payment Provider
Payment Intent
Payment Attempt
Payment state
Order commercial state
Fulfillment state
```

Hard rules:

```text
Order != Payment != Provider
Intent != Attempt
Payment state != Order commercial state != Fulfillment state
Checkout != Payment PSP internals
Order snapshot != live Catalog / Offer / Price / Inventory
```

**Order** = confirmed commercial record with snapshots (T011).

**Payment** = module that owns payment intents, attempts/results, provider references, refund/void commands, and reconciliation facts.

**Payment Provider** = adapter/PSP (Stripe, Zarinpal, COD/manual, later others). Not the Payment domain.

Catalog, Inventory, and Fulfillment do not capture money.

No module may treat “paid” as an Order column that is the whole Payment design.

Must not own as SoT: order lines as catalog copy, live stock, shipments, Price Books, PSP secrets as domain tables.

---

# B. Payment Ownership

Payment owns:

```text
payment intent
payment attempts
provider / method refs
amounts / currency as paid
payment statuses
refund / void commands
reconciliation facts
```

Payment does not own live ATS, Price Books, Catalog, Order commercial snapshots as write-model truth, or Fulfillment tracking.

No Payment schema in this task.

---

# C. Payment Intent vs Attempt

**Intent** = customer/checkout obligation to pay amount X in currency C for an Order/Checkout (or OrderIntent) id.

**Attempt** = one try against a provider/method.

Multiple attempts per intent are allowed.

Success is a fact on an attempt (then projected), not a flag on Order alone.

```text
Intent != Attempt
```

Do not design one table with a status flag as the whole Payment model.

---

# D. Idempotent Payment Initiation

Initiate keyed by idempotency key (checkout/order/command id).

Duplicate click ≠ double charge.

Align with T011 PlaceOrder / pay / reserve idempotency.

Do not implement keys now.

---

# E. Provider Adapter Boundary

Domains use a conceptual provider port (e.g. `IPaymentProvider`).

Stripe / Zarinpal / wallets / COD stay in adapters.

Provider is not chosen in this task.

Payment != Provider. Adapter HTTP is not Order.

---

# F. Redirect / Callback / Webhook Flow

Browser redirect and server webhooks are **transport**.

Truth is the Payment module after an **authenticated** provider event plus amount/currency check.

UI success page is not SoT.

Do not implement webhooks now.

---

# G. Callback/Webhook Security

Verify signature / shared secret, replay window, and source.

Unknown tenant => fail closed.

No unsigned body trust.

Do not design the full threat model as an ADR lock.

---

# H. Duplicate / Out-of-Order Events

Idempotent apply by provider event id.

Out-of-order: ignore stale events if current state is already terminal success/fail per guardrails (AG).

Do not invent silent double capture.

---

# I. Payment Status Model

Candidate statuses (not a locked enum):

```text
Pending
Authorized
Captured / Succeeded
Failed
Cancelled
Refunded (full / partial)
```

Distinct from Order commercial status (T011) and Fulfillment state.

Do not collapse to one `Status` that means paid-and-shipped.

---

# J. Authorization vs Capture

Preserve auth-then-capture for later.

Initial sellable path may capture immediately.

Architecture must not assume only one pattern.

Exact default:

```text
NEEDS_LATER_P00_DETAIL
```

---

# K. Amount & Currency Validation

Webhook / callback amount and currency must match the intent.

Mismatch => fail closed; do not mark Order paid.

Align with T009: unknown/unsupported charge currency fails closed on the sell path.

---

# L. Multi-Currency

Charge currency is the intent currency (T009 / T011 snapshot).

Do not convert in Payment ad hoc.

FX belongs to Pricing / Order snapshot, not Payment FX invention.

Locale != Market != Currency.

---

# M. Payment Method

Methods are adapters: card redirect, wallet, transfer, COD, later invoice/net terms.

Method ≠ Order type.

Do not fork Order into “CODOrder”.

---

# N. COD / Offline / Manual Payments

First-class Payment attempts with a manual/COD adapter.

Still Payment-owned; not a boolean on Order replacing the module.

Exact COD ops process:

```text
NEEDS_LATER_P00_DETAIL
```

---

# O. B2B Payment Readiness

Invoice / net terms later as methods plus credit policy (T007 / T009).

Not Identity. Actor != Buyer still applies.

Do not implement B2B invoicing now.

---

# P. Payment Before vs After Order

Align T011: prefer durable Order (or OrderIntent) id before capture so payment is not orphaned.

Exact sequence:

```text
NEEDS_LATER_P00_DETAIL
```

Must be idempotent and compensatable with Inventory / Checkout on fail.

Do not invent a second Order product for unpaid intents.

---

# Q. Refund

Refund is a Payment command referencing the original capture.

Order / return process **requests** it; Payment **executes** via adapter.

Snapshot refund amounts in Payment; do not rewrite Order line catalog history.

Returns product:

```text
DEFERRED
```

---

# R. Void / Cancel Authorization

Void unused authorization.

Distinct from refund of captured funds.

Checkout / Order cancellation **commands** void/refund (T011); Payment owns execution.

---

# S. Partial Payment / Partial Refund Readiness

Preserve multiple captures/refunds against one intent/order without redesign.

Not implemented now.

```text
DEFERRED
```

---

# T. Marketplace Payment Implications

Customer may pay the marketplace.

Seller settlement is **not** the customer Payment attempt.

Split / payout later.

Do not store settlement in Catalog. Do not merge Seller A money with Seller B.

Exact split settlement:

```text
NEEDS_LATER_P00_DETAIL
```

---

# U. Single-Store

Same Payment module.

One merchant-account config per tenant/store via platform, not Host parse inside Payment (T003).

Do not scatter `if (isMarketplace)` as the Payment model.

---

# V. Tenant / Provider Configuration

Per-deployment / tenant provider credentials live in secrets/config, resolved after trusted tenant context.

Payment does not parse Host as tenant SoT.

Unknown tenant => fail closed.

---

# W. Secrets

Keys never in logs, git, or client.

Rotate via config. Webhook secrets similarly.

Do not commit secrets. Do not implement a vault in this task.

---

# X. Order Integration

Payment emits paid / failed facts.

Order updates **payment refs / status projection**, not line rewrite.

Order does not call PSP.

Checkout/Order command Payment (T011). Payment does not own Cart.

---

# Y. Inventory Integration

Payment fail => Inventory release (T010 / T011).

Payment success may allow commit per checkout policy.

Events / contracts, not table writes. No cross-module joins (T004).

Payment timeout must not leave orphan Inventory reservations.

---

# Z. Fulfillment Integration

Ship after policy (typically paid or COD accepted).

Fulfillment listens to Order / Payment facts, not PSP.

Do not design Fulfillment in this task.

---

# AA. Reconciliation

Compare:

```text
provider reports vs Payment ledger vs Order totals
```

Differences = ops / audit, not silent Catalog, Search, or Inventory ATS edits.

Corrections via module commands.

---

# AB. Payment Ledger / Accounting Boundary

Payment ledger ≠ full accounting product.

Accounting / export later.

Do not duplicate Order commercial snapshot as the only money truth for PSP.

DEFERRED

No PAN / CVV / secrets in logs.

Do not implement OpenTelemetry pipelines here.

# AD. Audit

Security / business events: initiate, succeed, fail, refund, webhook accepted / rejected.

Business audit ≠ technical logs (T000).

Do not implement audit stores now.

# AE. PCI / Sensitive Payment Data Direction

```text

```

At minimum recommend for ADR:

1. Order != Payment != Provider; not one paid flag on Order as the design.
2. Payment Intent != Payment Attempt; multiple attempts per intent allowed.
3. Idempotent initiation; duplicate click does not double charge.
4. Provider adapter / ACL; PSP choice is not the domain.
5. Signed webhooks / authenticated callbacks; UI success page is not SoT.
6. Amount and currency must match intent; mismatch fails closed.
7. Payment state != Order commercial state != Fulfillment state.
8. Authorization vs capture both preserved; default sequence later.
9. Refunds and voids are Payment commands; Order/return request them.
10. Secrets never logged, committed, or sent to the client.
11. No PAN storage; hosted fields / redirect.
12. Fail closed on mismatch, invalid signature, and unknown tenant.
13. Marketplace customer payment != seller settlement.
14. Compensation with Inventory / Checkout on payment fail; no orphan reservations.
15. Single-Store uses the same Payment module; tenant merchant config via platform, not Host parse.
