## Locked Domain Rules

Preserve:

```text
UserAccount != Party
Person Party != UserAccount
Organization Party != UserAccount
Tenant != Party
Seller != hard-coded User role
Agency != hard-coded User role
Customer != hard-coded User role
```

A single User may later act for one or more Parties/Organizations.

A Party may later have multiple Users/Memberships.

## Party Module

Create a dedicated real module:

```text
Party
```

Use:

```text
Domain
Application
Infrastructure
Contracts
```

or current repository convention.

Party owns its own:

```text
DbContext
schema
migrations
write model
```

Suggested PostgreSQL schema:

```text
party
```

No shared Identity DbContext.

No cross-module foreign keys.

## Party Core Model

Implement a minimal Party aggregate/model.

Support at minimum:

```text
Person
Organization
```

Use stable durable IDs.

Do not copy Identity credentials into Party.

A Person Party may represent the business/person entity associated with a user, but linkage is explicit, not inheritance.

## Person Party

Minimal business identity fields only where architecturally necessary.

Avoid overbuilding profile/address/contact systems.

Do NOT duplicate login email/phone credentials from Identity as authoritative authentication fields.

If contact references are needed, model them as business/contact data distinct from login identifiers.

## Organization Party

Minimal organization foundation.

At minimum preserve:

```text
OrganizationId / PartyId
Display/Legal name seam
Status
CreatedAt / UpdatedAt
```

Keep extensible for future:

```text
seller organization
agency
corporate buyer
brand owner
supplier
merchant
```

Do NOT create enum that permanently fixes one organization to exactly one commercial type.

## User ↔ Party Link

Create a stable contract/membership link between:

```text
Identity UserId
PartyId
```

Do not add PartyId foreign key into Identity UserAccount.

The Party module may store the opaque UserId reference.

No cross-module FK.

## Membership Model

Implement membership as first-class data.

At minimum:

```text
MembershipId
UserId
PartyId / OrganizationId
Status
membership type/relation
CreatedAt
```

Avoid a single string role column that becomes the final authorization model.

Membership relation may express business association, while permissions remain in SpiceDB.

Hard rule:

```text
Membership != Authorization
```

## Organization Relationships

Create a minimal typed organization relationship seam for future structures such as:

```text
parent / child
seller operated by
agency represents
corporate hierarchy
supplier relationship
```

Do NOT implement full B2B business rules.

Do NOT encode every future relationship now.

Use a controlled extensible model.

## SpiceDB Projection Boundary

Party/Organization relationship changes must be able to project relationship tuples to the existing authorization foundation.

Use:

```text
IAuthorizationTupleWriter
```

or existing Tooba abstraction.

Do not use Authzed.Net types in Party Domain/Application.

Do not make Party persistence transaction depend synchronously on SpiceDB network availability.

Preferred pattern:

```text
Party local transaction
→ module-owned Outbox
→ explicit integration event
→ relationship projection handler
→ SpiceDB tuple write
```

Implement only the minimal foundation/proof needed.

## Eventual Consistency

Document that:

```text
Party DB = business source of truth for Party/Membership
SpiceDB = authorization relationship projection
```

SpiceDB is NOT the business master for organization metadata.

Use outbox/eventual consistency for cross-system projection.

Do not use distributed transactions.

## Membership / Authorization Semantics

A membership record must not automatically imply every permission.

Example concept:

```text
Membership exists
→ relationship can be projected
→ SpiceDB schema determines permission
```

Do not embed permissions inside membership row.

## Tenant / Edition Semantics

Marketplace:

```text
Party data in marketplace database
```

SingleStore:

```text
Party data in each tenant database
```

Use existing tenant-aware persistence.

Do not parse Host in Party module.

Tenant A Party data must never leak into Tenant B.

## Organization Type / Capability

Avoid rigid enum like:

```text
SellerOnly
AgencyOnly
CustomerOnly
```

that prevents one Organization from holding multiple future commercial capabilities.

Prefer extensible classification/capability seams.

Do not implement those capabilities in this task.
