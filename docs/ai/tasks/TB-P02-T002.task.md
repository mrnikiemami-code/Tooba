## Locked Authorization Principles

Preserve:

```text
Authentication != Authorization
UserId is principal identity, not permission model
Role column != final authorization model
Authorization must be relationship-based / ReBAC-ready
Authorization checks belong at use-case/application boundary
Business modules must not query SpiceDB storage directly
```

## Minimal SpiceDB Schema

Create only a minimal foundation schema sufficient to prove:

```text
user subject
tenant-scoped relation
simple permission check
```

Do NOT model complete Catalog/Order/Seller/Party permissions.

A neutral platform/demo resource is acceptable.

Keep this clearly non-business/disposable.

---

## Schema Versioning

Authorization schema must be treated as versioned infrastructure.

Provide a controlled bootstrap/update mechanism.

Do not auto-overwrite production schema blindly on every app startup.

Development/test may apply schema automatically if explicitly configured.

Document migration/version strategy.

---

## Check API

Implement a stable application-facing check contract.

Conceptually:

```text
CanAsync(subject, permission, resource, context)
```

Return explicit decision.

Do not throw for normal DENY.

Differentiate:

```text
ALLOW
DENY
AUTHORIZATION_UNAVAILABLE / ERROR
```

Avoid fail-open on infrastructure failure for protected operations.

---

## Use-Case Boundary Enforcement

Provide a reusable pattern so Application use cases can require authorization before business logic.

Do not scatter SpiceDB calls inside controllers/endpoints.

Do not call SpiceDB directly from Domain entities.

A behavior/decorator/service approach is acceptable.

Do not add MediatR if not already justified solely for this task.

---

## Tuple Write Boundary

Provide controlled tuple relationship write abstraction.

Do NOT let arbitrary modules send raw SpiceDB tuple strings.

Prefer typed relationship requests.

Validate:

```text
subject
relation
resource
```

before adapter call.

No final Party/Organization relationship writes yet.

---

## Consistency Model

Document SpiceDB consistency semantics.

Do not promise globally stale-free reads without specifying consistency mode.

Expose a seam for future consistency tokens/ZedTokens if supported.

For this foundation, choose a safe default appropriate to authorization checks and document it.

---

## Tenant Isolation

Hard rule:

```text
Tenant A relationship must not authorize access to Tenant B resource.
```

Tests must prove isolation.

Use durable TenantId, not Host.

Do not create wildcard tenant relations as a convenience.

---

## Caching

Do NOT cache authorization ALLOW/DENY decisions globally in this task.

Authorization caching is security-sensitive.

If a future cache is added, it must include relationship revision/version and scope.

For now, no decision caching unless the SpiceDB client itself requires harmless transport behavior.

---

## Failure Semantics

Protected operation on SpiceDB/network failure must NOT silently allow.

Preferred safe result:

```text
authorization unavailable
```

which application layer can map to safe failure.

Do not leak endpoint/internal errors to client ProblemDetails.
