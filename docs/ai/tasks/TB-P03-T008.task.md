Amount Integrity

Hard rule:

client cannot choose payment amount

Payment amount/currency must match the relevant Order snapshot.

If Order amount changes before initiation due to a new valid lifecycle step, create a new explicit payment flow rather than mutate a successful attempt history.

OnlinePurchase vs RequestToReserve

OnlinePurchase:

may create Payment

RequestToReserve:

must not require Payment at initial request submission

Future later-payment support may be a seam.

Do not collapse both modes into one payment-required state.

Gateway Initiation Result

Provider-neutral initiation result may contain:

ProviderRequestReference
RedirectUrl / client action reference
ExpiresAt

Do not expose internal secrets.

Validate redirect/callback URLs against trusted configuration/policy.

Do not accept arbitrary attacker-controlled callback authority if avoidable.

Verification / Callback

Provider callback/webhook must NOT be trusted solely from query/body status.

Verification must call provider/gateway verification contract or equivalent cryptographic verification path.

Hard rule:

callback says success != Payment success

Only verified provider evidence can transition Payment to Succeeded.

Idempotent Verification

Repeated callback/webhook delivery must be safe.

Same provider transaction/reference must not:

mark payment twice
emit duplicate payment success business effect
double-update order

Use durable uniqueness/idempotency.

Success Projection to Order

Payment module emits verified success event.

Order consumes through contract/event seam and moves eligible OnlinePurchase seller order/order to paid/confirmed payment state as defined by accepted lifecycle.

Do not directly update OrderDbContext from Payment Infrastructure.

Preferred:

Payment local transaction
→ Outbox
→ payment.succeeded.v1
→ Order handler

No distributed transaction.

Failure / Cancel

Provider failure/cancel must update Payment attempt/payment state without fabricating Order payment success.

Order may remain PendingPayment or transition according to bounded lifecycle policy.

Do not cancel entire Order automatically unless accepted order policy says so.

Multiple Seller Orders

Marketplace checkout contains seller-scoped orders.

Payment architecture must preserve future ability to support:

one customer payment covering checkout group
or seller-scoped settlement/accounting

For initial foundation, customer-facing Payment may target CheckoutGroup/order total while retaining seller order references in immutable allocation snapshot/seam.

Do not couple gateway payment to one seller only.

Payment Allocation Snapshot

If one payment covers multiple seller orders, preserve a deterministic allocation snapshot.

Conceptually:

SellerOrderId
AllocatedAmount
Currency

This is not settlement/payout implementation.

Sum must equal Payment amount.

No FX inside Payment.
