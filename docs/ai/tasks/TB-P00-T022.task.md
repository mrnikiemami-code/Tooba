# A. Core Separation

Hard rules:

```text
Order != Fulfillment
Payment != Fulfillment
Inventory != Fulfillment
Shipment != Order
Carrier != Fulfillment Domain
```

Define responsibilities clearly.

Order owns commercial commitment/order truth.

Inventory owns stock/reservation truth.

Payment owns financial transaction truth.

Fulfillment owns post-order physical/service delivery execution state.

---

# B. Fulfillment Scope

```text
Fulfillment Request

Carrier/Provider
Tracking

Delivery status
Pickup readiness
Delivery exception
```

Do not create schema.

# C. Fulfillment Unit

Analyze a stable fulfillment unit concept.

Potential grouping dimensions:

```text
Order
Seller
Ship-from location
Delivery method
Destination
Fulfillment provider
Availability/timing
Item constraints
```

One Order may produce multiple fulfillment units.

One fulfillment unit may later produce one or multiple Shipments where needed.

Do not assume:

```text
1 Order = 1 Shipment
```

---

# D. Marketplace Split

Marketplace must support:

```text
one customer Order
multiple seller-owned fulfillment responsibilities
```

Potential conceptual shape:

```text
Order
├── Seller A Fulfillment
└── Seller B Fulfillment
```

Do not force all sellers into one logistics lifecycle.

Order remains customer-facing commercial aggregate/read experience.

---

# E. Single-Store

Single-Store uses same Fulfillment capability.

Seller may be implicit.

Do not create a separate fulfillment architecture.

Future multi-location warehouses must remain possible.

---

# F. Inventory Boundary

Inventory owns:

```text
stock
availability
reservation
allocation authority where defined
```

Fulfillment may consume confirmed/reserved allocation references.

Fulfillment must not directly mutate Inventory tables.

Stock decrement/release interactions happen through approved contracts/events.

---

# G. Order Boundary

Order owns:

```text

```

Fulfillment owns execution after fulfillment is authorized/created.

Fulfillment events may influence Order's customer-facing derived status through contract/event handling.

Do not let Fulfillment rewrite Order tables.

# BC. Decision Summary

Classify:

```text
RECOMMENDED_FOR_ADR
NEEDS_LATER_P00_DETAIL
DEFERRED
```

At minimum recommend:

1. Fulfillment is separate from Order, Payment and Inventory.
2. One Order may create multiple fulfillment units/shipments.
3. Marketplace seller fulfillment responsibilities remain separable.
4. Single-Store reuses same fulfillment architecture.
5. Shipping Method is distinct from Carrier/Provider.
6. Carrier/provider integrations are behind internal adapters.
7. Order snapshots delivery destination; Fulfillment does not use mutable address-book truth.
8. Inventory remains stock/reservation authority.
9. Payment policy affects fulfillment eligibility but Payment state is not Fulfillment state.
10. Shipping raw carrier rate is not automatically customer shipping price.
11. Partial and split shipment are first-class.
12. Provider callbacks/tracking updates are idempotent and state-regression-safe.
13. Cancellation requires orchestration/compensation, not a boolean.
14. Full Returns/RMA remains a separate future capability.
15. COD evidence does not let Fulfillment directly mutate Payment.
16. Fulfillment is tenant- and seller-authorized through SpiceDB.
17. Reconciliation is first-class.
18. Manual operational actions are authorized and audited.
19. Fulfillment UI is queue/workflow/workspace oriented, not CRUD.
20. Order Workspace presents coherent shipment timeline regardless of backend module boundaries.
21. Operational read models support high-volume workflows without cross-module joins.
22. Fulfillment architecture is future 3PL/multi-location/microservice ready.

Do not create final ADR yet.
