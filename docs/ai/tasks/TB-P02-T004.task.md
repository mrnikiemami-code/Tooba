## Locked Principles

Preserve:

```text
Authentication != Authorization
Session != User
Refresh credential != Password credential
Reset token != Login token
Verification challenge != MFA enrollment
```

Do not create custom cryptography.
Do not store raw refresh/reset/verification secrets.

## Session Model

Implement Identity-owned session persistence with at minimum:

```text
SessionId
UserId
CreatedAt
ExpiresAt
LastUsedAt
RevokedAt
RevocationReason
Credential/SessionVersion
Edition
TenantId when applicable
```

Optional safe metadata may include device label/client id. Avoid raw full user-agent/IP retention unless justified.

## Session Scope

Marketplace sessions belong to the marketplace identity database.

SingleStore sessions belong to the tenant identity database.

No cross-tenant session lookup. No Host parsing inside Identity lifecycle code.

## Refresh Credential

Implement secure opaque refresh credentials.

Preferred:

```text
high-entropy random secret
store only cryptographic hash
return raw secret only at issuance boundary
```

Do not persist plaintext refresh tokens. Do not use predictable GUID-only bearer secrets.

## Rotation

Successful refresh must rotate credentials:

```text
refresh token A used
→ A becomes unusable
→ refresh token B issued
```

Detect reuse where practical. Do not allow indefinitely replayable refresh credentials.

## Revocation

Support:

```text
revoke one session
revoke all sessions for User
revoke on security-sensitive credential changes
```

Revoked sessions must not refresh.

## Session Version / Security Stamp

Provide one coherent durable mechanism such as:

```text
SecurityStamp
CredentialVersion
SessionVersion
```

Security-sensitive events such as password change, account disable, or high-risk reset must be able to invalidate prior session state.

## Access Token Boundary

Do not lock Tooba to one transport forever.

Preserve future support for:

```text
secure cookie/session
JWT access token
BFF session
external IdP token exchange
```

If a short-lived access-token implementation is needed for tests, keep it behind a Tooba abstraction.

Do not invent custom JWT cryptography.

## Password Reset

Implement password-reset challenge lifecycle:

```text
request reset
issue high-entropy one-time secret
store only hash
expire
single use
purpose bound
complete reset
revoke/invalidate according to policy
```

Public reset request must avoid obvious account enumeration.

No real email/SMS provider in this task.

## Identifier Verification

Support verification lifecycle for:

```text
Email
Phone
```

Challenge must be purpose-bound, identifier-bound, expiring, and single-use.

Generating a code must not automatically mark an identifier verified.

## OTP Durability

The earlier in-memory OTP/challenge store is not sufficient for production.

Replace or supplement it with Identity-owned durable PostgreSQL challenge persistence for:

```text
login OTP where applicable
identifier verification
password reset
MFA challenge foundation
```

Keep sender provider abstract.

Never persist plaintext OTP/code.

## Challenge Model

Use controlled purpose values such as:

```text
Login
VerifyIdentifier
PasswordReset
Mfa
```

Persist at minimum:

```text
ChallengeId
UserId optional where safe
Identifier reference/value hash where applicable
Purpose
SecretHash
CreatedAt
ExpiresAt
ConsumedAt
AttemptCount
```

Do not allow arbitrary client-supplied purposes.

## Brute-Force / Attempt Limits

Implement configurable per-challenge attempt limits.

After threshold:

```text
challenge invalid/locked
```

Full commercial rate limiting/anti-fraud remains deferred.

## Password Change

Implement authenticated password-change lifecycle:

```text
verify current credential
validate new password policy
replace hash
update security version/stamp
apply session revocation policy
emit security event
```

Never log passwords or hashes.

## Credential Events

Use existing event infrastructure where appropriate.

Potential events:

```text
session_created
session_revoked
password_changed
password_reset_completed
identifier_verified
refresh_reuse_detected
```

Never publish secrets.

Technical logs != Security Audit.

Use the existing security-event sink seam.

## Error Semantics

Keep internal/public failure semantics separate.

Public surfaces must avoid unnecessary account enumeration.

Internally distinguish:

```text
invalid/expired challenge
consumed challenge
too many attempts
revoked session
refresh reuse
disabled/locked user
```

No sensitive details in ProblemDetails.
