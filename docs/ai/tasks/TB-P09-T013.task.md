Title:
Quantity Decimal Foundation — Discovery-First Migration, Multilingual Units, Product Quantity Policy, Offer Min/Max, Global Rounding

Architect Context

Tooba currently uses integer quantity in important paths, including:

public int Quantity { get; init; }

order.order_lines.quantity -> integer

fulfillment quantities such as:

quantity_ordered

quantity_processing

quantity_packed

quantity_shipped

The product must support weighted/fractional goods.

This is a high-impact foundation change. It must be implemented safely, incrementally, and without duplicating existing systems.

LOCKED PRINCIPLE:
Discovery first -> gap analysis -> minimal migration -> focused regression

Do NOT redesign Inventory, Product, Offer, Pricing, Order, Fulfillment, Return, or language infrastructure if equivalent concepts already exist.
Do NOT create duplicate quantity/unit systems.

Product Decisions — LOCKED
Quantity

Domain-wide product quantity must support decimal values.

Target storage default:
numeric(18,6)

Do not blindly convert every integer named "count".
Only quantities representing an amount of product are decimalized.

Examples that SHOULD become decimal where applicable:

cart quantity

order line quantity

inventory on-hand/reserved/available-related persisted quantities

fulfillment ordered/processing/packed/allocated/shipped/delivered quantities

return/requested/approved/returned/returnable quantities

shipment allocations

inventory adjustments/reservations

Examples that SHOULD remain integer:

number of orders

number of rows

pagination counts

employee count

item type count

aggregate record counts

Product Quantity Policy

For the current product scope, Product is the source of truth for quantity semantics.

Required effective fields, reusing existing fields if present:

UnitOfMeasureId

QuantityDecimalPlaces

QuantityStep nullable

Variant does NOT duplicate these fields in this phase.

However, introduce/reuse a central effective policy abstraction/resolver so future Variant override can be added without redesigning Cart/Order/Inventory/Fulfillment.

Conceptual contract:
EffectiveQuantityPolicy

Today it resolves from Product only.

Step

QuantityStep is OPTIONAL.

If no Step:

any quantity valid under DecimalPlaces is allowed.

Example:
DecimalPlaces=2, Step=null
valid:

1

1.2

1.25

If Step exists:

quantity must normalize according to Step and global rounding mode.

Offer Policy

Seller-specific purchase limits belong to Offer.

Required, reusing existing fields if present:

MinimumOrderQuantity nullable

MaximumOrderQuantity nullable

Rules:

Min/Max are optional

Min <= Max when both exist

values must be compatible with effective quantity policy

Do NOT put Unit/DecimalPlaces/Step into Offer in this phase.

Multiple Selling Units

OUT OF SCOPE for this task.

Do NOT implement:

simultaneous gram/kg selling units for one offer

Architecture should not prevent future implementation, but current feature remains simple.

Rounding — GLOBAL AND SINGLE

User requires one globally visible rounding result across the system.

Add/reuse ONE global/store-level rounding mode.

Required supported modes:

Floor

Ceiling

Nearest

Bankers may be left extensible but need not be surfaced unless already supported.

LOCK:

no Product-specific rounding mode

no Offer-specific rounding mode

no separate invoice rounding that produces a different visible result

no module should independently call Floor/Ceiling/Round for business quantity normalization

Use/reuse a central rounding/quantity normalization service.

Conceptual responsibility:
IQuantityNormalizer or equivalent
using:

DecimalPlaces

optional Step

GlobalRoundingMode

The same normalized business value must flow into cart/order/inventory/fulfillment/returns/invoice calculations where quantity is used.

Important Rounding Examples

If DecimalPlaces=2 and Step=null:

Floor:
1.239 -> 1.23

Ceiling:
1.231 -> 1.24

Nearest:
normal nearest behavior according to chosen canonical implementation.

If Step=0.25:

Floor:
1.37 -> 1.25

Ceiling:
1.37 -> 1.50

Nearest:
1.37 -> nearest valid step according to canonical rule.

No floating-point (double) normalization.
Use decimal arithmetic.

2. Migration Strategy

After discovery, make minimal changes only.

For persisted product quantities that are integer:

migrate to numeric(18,6) or current project equivalent

preserve existing integer data exactly, e.g. 5 -> 5.000000

preserve nullability/defaults/constraints

review indexes/check constraints

no destructive data rewrite

Migration must be backward-safe for existing data.

Do not change unrelated count columns.
