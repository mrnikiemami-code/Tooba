3. Locked Lifecycle Rule

Once a checkout/order has a successful Payment:

no new payment initiation is allowed

no manual payment initiation is allowed

no sandbox retry is allowed

no second payment attempt is created

no second payment evidence submission is accepted

UI must not expose actionable payment CTA

The only post-success financial operations are the existing canonical ones such as:

refund

return-related refund

settlement/adjustment flows

Payment initiation is not one of them.

4. Canonical Capability

Centralize payment initiation eligibility in backend/application capability, equivalent to:

CanInitiatePayment
CanRetryPayment
CanSubmitManualEvidence

Frontend must not infer from translated labels.

Rules:

Allowed examples

no Payment yet and Order eligible

Failed payment retry

Expired unpaid retry after EnsureOrderSupply succeeds

Rejected manual attempt retry when policy allows

Forbidden

Payment Succeeded

fully refunded/cancelled terminal state if payment initiation is no longer legal

any state where Order is not payment-eligible

5. API Guard

Every payment-initiation endpoint must enforce the same backend rule.

If called after Payment Succeeded:

Return stable domain error, e.g.:
payment.already_succeeded

Customer-safe FA:
پرداخت این سفارش قبلاً با موفقیت انجام شده است.

Do NOT return 200.
Do NOT silently no-op as success if a new attempt was requested.
Do NOT create another attempt.

Idempotent replay of the SAME successful callback/event is separate and remains safe.

6. Manual Evidence Guard

If Payment is already Succeeded:

manual evidence upload/submit must be blocked

no new tracking/reference attached as a new attempt

existing historical evidence remains immutable

If manual payment was Rejected/Expired and retry is allowed:

same Order retry remains valid

new attempt/evidence allowed through canonical retry flow

No redesign.
