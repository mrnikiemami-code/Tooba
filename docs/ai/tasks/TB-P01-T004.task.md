## 5. Module-Owned DbContext

Each persistence owner has its own DbContext.

For this task, implement one sample owner:

```text
PlatformProbe
```

Conceptual shape:

```text
PlatformProbeDbContext
PostgreSQL schema owned by PlatformProbe
migrations owned by PlatformProbe
```

Exact type/project names may follow existing solution conventions, but the ownership rule is mandatory.

A future Catalog module would own `CatalogDbContext` and schema `catalog`. Do not create those now.

Business modules must not share a DbContext.

Host/platform may compose registration. Host must not become the owner of module tables.

---

## 6. No Mega ToobaDbContext

Forbidden:

```text
ToobaDbContext
AppDbContext
a single DbContext that maps every module
a shared “god” model builder for all business tables
cross-module entity sets on one context
```

Do not create a mega context “for convenience” even if Marketplace currently uses one database.

Physical colocation of schemas in one PostgreSQL database does not license one DbContext.

---

## 7. Tenant Database Selection

Database selection must follow the existing T003 chain only:

```text
Host
→ TenantContext / CommerceContext
→ ConnectionReference
→ IDatabaseConnectionResolver
→ Npgsql connection string
→ module DbContext
```

Marketplace: use the marketplace `ConnectionReference` already resolved on `CommerceContext`.

Single-Store: use the tenant’s `ConnectionReference` after successful resolution. Never open another store’s database.

Do not:

```text
parse Host inside persistence
derive credentials from hostname
pick connection strings in a module
use a process-wide mutable connection singleton
switch tenant mid-request
```

Empty/unconfigured/invalid connection references remain fail-closed.

Existing `/health` and `/ready` must remain reachable without requiring a storefront tenant.

---

## 8. DbContext Lifetime

Register module DbContext as scoped (per HTTP request / explicit scope).

Do not register DbContext as:

```text
Singleton
a process-wide shared instance
a static accessor
```

Do not cache a DbContext across tenants.

Connection pools may be reused by the provider for the same actual connection target. Partitioning remains by real connection string / target, not by hostname.

A later background job must create its own scope with an explicit TenantId / Marketplace deployment identity. Do not implement the job product here; document the rule.

---

## 9. PostgreSQL Schema Ownership

Each module owns a PostgreSQL schema.

PlatformProbe must use a dedicated schema, for example:

```text
platform_probe
```

Do not dump sample tables into `public` as the architecture pattern.

Do not share one schema across future modules.

Search_path / schema mapping must be explicit in the module’s EF model.

Cross-module tables in the same schema are forbidden.

---

## 10. Module-Owned Migrations

Migrations are owned by the same module that owns the DbContext.

```text
one module → one DbContext → one schema → one migration history for that context
```

Do not create a single Host-wide migrations assembly for all future business modules.

Do not hand-author SQL as a substitute for the EF migration workflow unless a documented, reviewed exception is required for PostgreSQL provider limitations. Prefer EF migrations.

PlatformProbe must include at least one initial migration that creates its schema/table(s).

History table must not be treated as a shared product-wide migrations table for every module.

---

## 11. No Cross-Module Foreign Keys

Forbidden:

```text
database foreign keys across module schemas
database foreign keys across module ownership boundaries
ORM relationships that imply cross-module table ownership
```

Even inside one physical PostgreSQL database, modules reference other modules by opaque IDs only.

PlatformProbe must not create FKs to imagined Catalog/Order/Identity tables.

If the sample needs an external reference column for demonstration, store an opaque UUID with no FK.

---

## 12. No Cross-Module Query

Forbidden:

```text
cross-module SQL JOIN
DbContext querying another module’s tables
FromSql against another module’s schema
shared IQueryable spanning owners
repository access into another module’s persistence
```

Reads across modules remain contracts, projections, or events (not implemented here).

Do not add a “just this once” join helper.

Admin/reporting composition is not a license to join module tables.

---

## 13. Transaction Boundaries

Default:

```text
one business transaction commits inside one module’s ownership boundary
```

No distributed ACID as the default.

Do not start an ambient TransactionScope that spans multiple module DbContexts as the architecture pattern.

Do not implement outbox, inbox, or saga product here.

Document that cross-module workflows later use local commit plus eventual consistency / outbox, not two-phase commit.

If a request later needs two modules, each module saves its own changes; coordination is application-level, not a shared mega transaction.

---

## 14. Unit of Work

Provide a clear Unit of Work seam for a module persistence owner.

Acceptable shapes (choose one consistent with ASP.NET + EF):

```text
the module DbContext is the UoW for that module
an explicit IUnitOfWork / IPlatformProbeUnitOfWork wrapping that DbContext
```

Rules:

```text
UoW is per module, not global
UoW lifetime is the request/scope
UoW does not wrap every module in the process
```

Do not invent a product-wide `IToobaUnitOfWork` that flushes all modules.

---

## 15. SaveChanges Policy

Saving is explicit.

Do not auto-save on dispose as the architecture truth.

Do not hide SaveChanges inside random helpers that make it unclear when a commit happens.

A successful command path should call SaveChanges (or UoW.Commit) once at the application boundary of that module.

Failed validation / fail-closed paths must not persist.

Do not use global EF interceptors to rewrite business meaning.

If interceptor/save-hook is used, keep it technical (timestamps, audit columns for the probe only) and document it.

---

## 16. UUID v7

New persisted entity keys for this foundation use UUID version 7.

PlatformProbe sample entity primary key must be UUID v7, not identity integers, not UUID v4 as the convention.

Generation must be application-side (or a single shared technical helper), not left to ad-hoc `Guid.NewGuid()` scattered through modules if a helper already exists or is introduced here.

Do not leak internal sequence surrogates into public contracts.

Do not issue a separate ADR file in this task. Record the convention in the architecture note as the P01 persistence default for new entity keys.

Opaque cross-module references remain UUIDs without FK.

---

## 17. NodaTime

Authoritative timestamps on persisted rows use NodaTime, not `DateTime` as architecture truth.

Use Instant (UTC) for recorded-at / created / updated technical timestamps on the probe entity.

Do not store local wall time as if it were UTC.

Do not confuse Locale, Market, or tenant timezone with Instant.

If the Npgsql + NodaTime plugin / EF mapping package is required, add it. Keep versions compatible.

A clock abstraction in BuildingBlocks is allowed if it stays technical and free of business types.

Do not implement a timezone product, market calendar, or “store local time” feature.

---

## 18. Connection Opening

DbContext must open against the resolved connection string for the current `ConnectionReference`.

Do not open the database at process start for every tenant.

Do not fail Host startup solely because a sample tenant DB is absent, unless a development configuration explicitly requires it. Prefer fail-closed on first data-plane use.

Health/liveness remains process-alive.

Do not probe every tenant database inside `/health`.

If `/ready` is extended, document honestly. Do not fake global readiness for unconfigured tenant databases.

Never log the connection string when opening.
