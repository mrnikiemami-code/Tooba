## Objective

Design Tooba's Identity and Authentication architecture deeply enough to support:

- extensible login identifiers;
- username / email / phone / future identifiers such as national ID;
- password login;
- OTP login;
- optional MFA / 2FA;
- account recovery;
- verification;
- session/device management;
- external identity provider integration;
- future Keycloak integration;
- Marketplace and Single-Store deployments;
- future B2B organizations and memberships;
- strict separation from SpiceDB authorization;
- secure tenant/edition context handling.

This task is architecture documentation only.

Do not implement authentication code, Keycloak, OTP providers, DB schemas, controllers, UI, or SpiceDB schema.

# A. Terminology & Separation of Concerns

Define and separate:

```text
Identity
Party
Account
Login Identifier
Credential
Authentication Method
Verification
MFA Factor
Session
Device
External Identity
Authorization
```

Hard rule:

```text
Authentication != Authorization
```

SpiceDB belongs to authorization, not credential validation.

Also preserve:

```text
Identity != Party
```

A person or organization in the business domain must not be reduced to an authentication record.

---

# B. Identity Ownership

Define what Identity owns conceptually.

Likely ownership includes:

```text
identity/account lifecycle
login identifiers
credential references
verification state
authentication methods
MFA enrollment
session lifecycle
external identity bindings
security events
recovery mechanisms
```

Identity must NOT own:

```text
customer profile business data
organization business data
pricing
orders
seller commercial data
SpiceDB relationship graph as business authorization truth
```

Party/Customer owns business identity/profile concepts.

---

# C. Extensible Login Identifier Model

Confirmed requirement:

Users must be able to authenticate with:

```text
username
email
phone
future identifiers
```

Example future identifier:

```text
national ID
```

Do not implement login as fixed columns such as:

```text
UserName
Email
Phone
```

with hardcoded branching.

Design a conceptual extensible identifier model around:

```text
Identifier Type
Normalized Value
Display Value
Verification State
Primary / Preferred indicator where appropriate
Uniqueness Policy
Tenant/Deployment Scope
Created / Revoked lifecycle
```

Do not lock persistence schema.

Analyze uniqueness scope:

```text
global
per deployment
per tenant/store
per identifier type
```

and mark exact policy as NEEDS_LATER_P00_DETAIL where business rules are not yet known.

# D. Identifier Normalization

Define that each identifier type may require its own normalizer.

Examples:

```text
email -> case/domain normalization policy
phone -> E.164-style canonicalization
username -> canonical case/Unicode policy
national ID -> country-specific validation/normalization
```

Do not hardcode all identifier types into one generic string transformation.

Design conceptual strategy:

```text
ILoginIdentifierTypeHandler
```

or equivalent.

Names are conceptual, not implementation requirements.

# E. Authentication Methods

Architecture must support multiple independent methods:

```text
Password
OTP
External Identity Provider
Future Passkey/WebAuthn
Future Enterprise Federation
```

Important:

```text
Login Identifier != Authentication Method
```

Example:

```text
phone + password
phone + OTP
email + password
email + OTP
username + password
external provider
```

must be representable without redesign.

---

# F. Password Authentication

Define architecture/security principles:

- passwords are never stored reversibly;
- use modern adaptive password hashing;
- password hashing algorithm must be replaceable/versioned;
- password rehash on successful login should be possible;
- password policy belongs to security/config policy, not UI validation only;
- breached/common password checks may be added later;
- secrets must never enter logs/telemetry;
- reset tokens must be short-lived and single-use.

Do not choose exact algorithm parameters unless clearly marked later security configuration.

---

# G. OTP Authentication

Design generic OTP architecture.

Separate:

```text
OTP Challenge
Delivery Channel
OTP Provider
Verification Attempt
Rate-Limit / Abuse Policy
```

Possible channels:

```text
SMS
Email
future channels
```

Do not couple Identity to one SMS provider.

Provider integration must be behind internal adapters.

OTP requirements:

- expiration;
- one-time consumption;
- bounded retries;
- replay prevention;
- rate limiting;
- resend policy;
- correlation to intended identifier/action;
- tenant/store branding context where relevant;
- no OTP value in logs.

Do not implement provider or tables.

---

# H. MFA / 2FA

Support optional MFA.

Architecture should allow factors such as:

```text
TOTP authenticator
OTP via verified channel
Future WebAuthn / passkey
Recovery codes
```

Do not equate OTP login with MFA.

A single OTP login may be the primary authentication method.

MFA means an additional independent factor/policy step.

Define conceptual:

```text
Authentication Assurance Level
```

or equivalent, so sensitive operations can later require step-up authentication.

---

Examples:

future high-assurance identifier verified

Verification must be separate from simple identifier existence.

Analyze:

verified-at
verification method
revocation/reverification

# J. Session Architecture

Design sessions independently from credentials.

Requirements:

```text
multiple devices/sessions
session revocation

logout all sessions
session rotation
security-sensitive reauthentication
session metadata
```

Consider safe metadata:

```text
SessionId
IdentityId
CreatedAt
LastSeenAt
Authentication Method / Assurance
Tenant/Deployment Context
Device label / user agent summary
RevokedAt
```

Do not store raw sensitive telemetry unnecessarily.

Do not finalize cookie/JWT implementation in this task.

# L. Tenant / Deployment Scope

Identity architecture must work across:

```text
Marketplace deployment
Single-Store shared deployment
```

Analyze whether identity namespace is:

```text
deployment-wide
tenant-specific
shared-across-tenants
```

Do not invent business policy.

Important security rule:

Authentication resolution must never cause cross-tenant data leakage.

For Single-Store, tenant/store context must already be resolved from trusted host routing before tenant-sensitive authentication policy/data access.

Do not equate:

```text
same email
```

with:

```text
same Party across all stores
```

unless later business policy explicitly decides that.

---

# M. Party Link

Define the boundary between:

```text
Identity
```

and:

```text
Party
```

Possible relationship:

```text
IdentityId -> PartyId
```

through explicit contract/reference.

Future B2B must allow:

```text
one human identity
belongs to / acts for
multiple organizations
```

Authorization to act for an organization belongs to SpiceDB/Party membership model, not Identity credentials.

---

# N. External Identity Providers

Architecture must remain ready for:

```text
Keycloak
OIDC
OAuth 2.x
Enterprise IdP
Social login if later required
```

Use anti-corruption/provider adapter boundary.

Do not make Keycloak the canonical owner of all Tooba business identity unless explicitly decided later.

Document two possible future operating modes:

```text
Tooba-managed authentication
External-IdP-managed authentication
```

and how an internal Identity record/binding can preserve domain continuity.

# O. External Identity Binding

Design conceptual binding:

```text
Provider
Issuer
Subject
IdentityId
LinkedAt
Status
```

Do not trust email alone as stable external identity key.

OIDC-style:

```text
issuer + subject
```

should be considered the stable external identifier.

No schema.

---

# P. Account Recovery

Design recovery independently from normal login.

Support future policies:

```text
verified email recovery
verified phone recovery
recovery codes
support-assisted high-assurance recovery
```

Security principles:

- prevent account enumeration;
- rate limit;
- notify on sensitive changes;
- invalidate/rotate sessions when appropriate;
- audit recovery attempts/outcomes.

---

# Q. Security Events / Audit

Identity should emit/record security-relevant facts such as:

```text
login success
login failure
OTP requested
OTP failed
password changed
identifier added/removed
MFA enabled/disabled
external identity linked/unlinked
session revoked
recovery completed
```

Distinguish:

```text
security audit event
```

from:

```text
technical application log
```

No passwords, OTPs, tokens, secrets in logs.

---

# R. Abuse Protection

Define architecture requirements for:

```text
rate limiting
credential stuffing defense
brute-force protection
OTP abuse
identifier enumeration defense
suspicious login detection hooks
CAPTCHA / challenge escalation hooks
temporary lock/throttle
```

Do not select CAPTCHA vendor.

Rate limiting may later use Redis, but architecture must not depend on Redis existing initially.

---

# S. Privacy / Sensitive Data

Define rules:

- authentication secrets never logged;
- national ID or similar future identifiers are sensitive;
- telemetry must avoid raw identifier values unless explicitly safe/necessary;
- consider hashed/pseudonymous dimensions for security analytics;
- data retention and deletion policies need later detail;
- external provider tokens must be protected.

Do not create compliance claims not established by product requirements.

# T. Authentication Flow Examples

Document at least these conceptual flows.

## Password Login

```text
resolve tenant/deployment context
identify identifier type
normalize identifier
resolve identity
verify password
evaluate MFA/step-up policy
create/rotate session
emit security event
```

## OTP Login

```text
resolve context
normalize identifier
issue OTP challenge
deliver via adapter
verify challenge
evaluate assurance policy
create/rotate session
emit security event
```

## External IdP Login

```text
resolve context
redirect/challenge
validate issuer/signature/state/nonce
resolve issuer+subject binding
link/create internal identity according to policy
evaluate authorization separately
create local session if architecture requires
```

## Sensitive Operation Step-Up

```text
existing authenticated session
policy requires stronger assurance
challenge additional factor
upgrade assurance for bounded duration/action
audit
```

# V. Relationship with SpiceDB

Hard separation:

```text
Identity proves who is authenticated.
SpiceDB answers what that subject may do.
```

Design flow:

```text
Authentication
→ authenticated subject/IdentityId
→ Party/organization relationships
→ SpiceDB authorization decision
```

Identity must not contain a fixed role matrix that duplicates SpiceDB.

Bootstrap/system roles may exist later only by explicit design.

---

# W. Relationship with B2B

Preserve future:

```text
Identity: human login principal
Party: human/business party
Organization: business entity
Membership/Delegation: relationship
SpiceDB: authorization graph
```

One person may act for multiple organizations with different permissions.

Do not model one account = one company.
