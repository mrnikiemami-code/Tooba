## 4. Architectural Constraints

Host/tenant/database resolution is platform/infrastructure.

Business modules may consume resolved identity/edition/capability context when business-relevant.

They must not:

```text
parse Host headers
look up the tenant registry
pick connection strings
construct credentials from hostname
switch tenant mid-request
```

Two commercial deployments from shared code/composition:

```text
Tooba Marketplace deployment
Tooba Single-Store shared deployment
```

Do not implement one mixed runtime that serves Marketplace and Single-Store simultaneously.

Do not fork the product.

---

## 5. Edition Resolution

Resolve Edition from deployment/configuration, not from arbitrary Host guessing.

Supported edition identities at this foundation:

```text
Marketplace
SingleStore
```

Unset/invalid edition must fail closed in environments that require resolution. Development may remain explicit and configuration-driven.

Do not scatter `if (isMarketplace)` through future business modules. Edition differences belong in composition/policy.

---

## 6. Deployment / Marketplace Context

Provide a stable marketplace context/deployment identity.

Marketplace requests must not run Single-Store Host→tenant→per-store DB lookup.

Marketplace foundation should expose a stable:

```text
Commerce Context / Deployment Context
```

with at least:

```text
Edition = Marketplace
Deployment identity
single DatabaseKey / ConnectionReference for the marketplace database
correlation / TraceId
```

Do not invent fake Single-Store tenant semantics for Marketplace.

---

## 7. Single-Store Tenant Resolution

For Single-Store, implement the resolution direction:

```text
HTTP Request
→ trusted Host extraction
→ host normalization
→ allowlisted domain mapping lookup
→ tenant/store resolution
→ tenant status validation
→ immutable tenant context
→ database connection resolution by ConnectionReference
```

Unknown hosts fail closed and never fall through to another store’s database.

Domain/Host is a resolution key/alias, not TenantId.

---

## 8. Host Extraction and Normalization

Extract Host only from a trusted source.

Normalize before lookup:

```text
lowercase
strip default port where appropriate
IDNA / punycode handling as required
reject empty/invalid hosts
```

Match allowlisted registered mappings only.

No wildcard fallback to an arbitrary tenant.

---

## 9. Trusted Proxy / Host Header Safety

Trust `X-Forwarded-Host` / forwarded headers only from configured trusted proxies.

Document the threat model in the architecture note:

```text
Host spoofing
untrusted forwarded headers
proxy/CDN
domain takeover/misconfiguration
cache poisoning
cross-tenant DB selection
```

Never construct DB credentials from hostname.

Log resolution failures without leaking secrets.

---

## 10. Control-Plane Registry Seam

Single-Store Host→tenant→connection reference cannot be discovered only from the tenant data-plane DB.

Introduce a control-plane registry seam owned by Host/platform.

Minimum conceptual records:

```text
Tenant/Store identity
Domain aliases
Primary domain
Tenant status
Database ConnectionReference
Edition/capabilities reference
Theme reference if already modeled as a reference only
```

A configuration-backed / in-memory development registry is acceptable for this task.

Do NOT build the production control-plane product, admin UX, provisioning workflow, or SQL control-plane schema product.

Do NOT centralize customer business data in the control plane.

---

## 11. Tenant Status and Fail-Closed Behavior

Unknown, disabled, suspended, missing-mapping, and missing-connection-reference cases must fail closed.

Do not open another tenant’s data-plane database.

Do not pick a silent winner on domain conflict.

Customer-facing payloads must remain generic and safe.

---

## 12. Immutable Tenant / Commerce Context

After successful resolution, create an immutable per-request (or explicit per-job later) context.

Minimum identifiers/references, not secrets:

```text
TenantId / StoreId when Single-Store
Edition
Deployment identity
Status
ResolvedDomain / PrimaryDomain identifiers
DatabaseKey / ConnectionReference
ThemeId reference if present
Correlation / TraceId
```

Do not put connection strings, passwords, or full config blobs into a process-wide mutable singleton.

Mid-request tenant switch is forbidden.

---

## 13. Database Connection References

Database selection uses ConnectionReference / DatabaseKey, never hostname.

Marketplace: one marketplace database reference (current model).

Single-Store: one database per store, selected after tenant resolution.

Business modules must not pick connections.

No tenant data in process-wide singletons.

Do not invent a second database product. PostgreSQL remains the architecture truth.

No SQL Server. No SQLite substitution as architecture truth.

---

## 14. Database Connection Resolution

Implement a platform connection-resolution seam, conceptually:

```text
ITenantResolver / host resolution
ITenantContextAccessor / immutable context
ITenantConnectionResolver / ConnectionReference → connection
```

Exact type names may follow existing BuildingBlocks/Host conventions.

Connection pools must be partitioned by actual connection target.

Do not implement domain EF models, business migrations, or module persistence.

If a PostgreSQL provider package is required for the connection seam, keep it minimal.

Empty/unconfigured connection references must fail closed rather than guessing.

---
