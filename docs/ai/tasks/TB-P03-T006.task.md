Checkout Orchestration

Implement application-layer checkout orchestration that:

loads Cart snapshot through Cart contract
revalidates Offer
re-resolves Pricing
revalidates Inventory reservation
creates Order
marks/converts Cart appropriately

Do not directly query Cart/Pricing/Inventory/Offer persistence.

No distributed transaction.

Use idempotent orchestration and compensating/reconciliation seams where required.

Order Mode

Model order mode explicitly.

At minimum:

RequestToReserve
OnlinePurchase

Do not infer mode from payment state.

Do not create two unrelated Order aggregate types unless repository architecture clearly requires it.

Prefer one Order aggregate with explicit mode and mode-specific state-machine rules.

Buyer vs Acting User

Preserve the locked distinction:

BuyerPartyId
BookedByPartyId / ActingUserId

For e-commerce naming, use a repository-consistent equivalent while preserving semantics:

BuyerPartyId = economic/customer party
PlacedByUserId / ActingUserId = authenticated principal performing action

Do not collapse these into one field.

For guest checkout, preserve a future seam; full guest checkout may remain deferred unless Cart architecture already supports it cleanly.

Order Aggregate

OrderId

Mode
Status
BuyerPartyId optional/future-ready
PlacedByUserId
Market
Currency
SalesChannel
CreatedAt
UpdatedAt
SubmittedAt

Do not store authentication credentials.

Do not make UserId the seller or buyer organization identity.

Order Lines

Order lines must originate from Cart Offer-based lines.

At minimum:

OrderLineId
OfferId
CatalogVariantId/reference
SellerPartyId/reference where available
Quantity
UnitPriceSnapshot
Currency
LineTotalSnapshot
pricing reference/version where available

Snapshots belong to Order history.

Hard rule:

Order price snapshot != current Pricing truth

Once Order is created/submitted, historical commercial values must not mutate because current Pricing changes.

Do not add Order state back into Product/Offer.

Pricing Revalidation

Checkout must re-resolve current price before Order creation/submission.

Do not trust Cart quote as authoritative.

If Cart snapshot differs from current Pricing:

detect mismatch
return explicit repricing outcome/failure

Do not silently charge a different price.

For foundation, choose and document a deterministic policy such as:

checkout fails with PRICE_CHANGED and client must reconfirm

No promotion engine yet.

Inventory Handoff

Cart currently owns temporary holds.

Checkout/Order foundation must define handoff semantics.

For OnlinePurchase:

temporary Cart hold
→ Order reservation/commit ownership seam

For RequestToReserve:

temporary hold may become request-associated reservation
or be revalidated under request policy

Choose a bounded, documented foundation.

Do not directly mutate Inventory tables.

Use Inventory contracts.

Do not consume stock merely because Order row was inserted unless lifecycle semantics require it.

Payment capture is not implemented yet.

Inventory Reservation Reference

Order must persist enough reservation reference/status to reconcile future Payment/Fulfillment.

Do not persist Inventory entity copies.

No cross-module FK.

Order Status

Create a minimal lifecycle supporting both modes.

Possible foundation states:

Draft
Submitted
PendingReservation
PendingPayment
Reserved
Confirmed
Cancelled
Expired
Rejected

Exact names may vary.

Do not overbuild final state machine.

Rules must make semantic sense for each mode.

Example:

RequestToReserve does not require payment to exist
OnlinePurchase may enter PendingPayment
Request-to-Reserve Semantics

This is NOT just another name for unpaid online order.

Foundation must preserve:

customer submits a reservation/request
merchant/seller/system may later accept/reject/confirm
payment may be absent or later

Do not force payment gateway dependency.

Online Purchase Semantics

Foundation must preserve:

checkout validates price/inventory
order enters payment-capable lifecycle
payment will be separate module

Do not mark order paid without Payment module evidence.

Multi-Seller Order Structure

Marketplace Cart may contain multiple sellers.

Order architecture must not assume one seller per entire customer checkout.

Choose and document one safe foundation:

Parent Order + Seller Order / Order Group

or:

Checkout creates N seller-scoped Orders under one CheckoutReference

Avoid a monolithic order row that cannot support seller-specific fulfillment/cancellation later.

Hard requirement:

seller-specific lifecycle must remain possible

Do not implement fulfillment yet.

Order Number

Use a customer-facing/reference number separate from internal UUID.

Requirements:

non-secret
human/support friendly
unique in appropriate deployment scope
not used as sole authorization credential

Do not expose sequential DB identity if that creates enumeration/security concerns without mitigation.

Idempotency

Checkout submission must be idempotent.

A repeated same checkout request must not create duplicate orders or double-handoff inventory.

Use explicit:

IdempotencyKey / CheckoutAttemptId

with persistence uniqueness.

Tests must prove duplicate submission is safe.

Totals

Order totals are immutable commercial snapshots derived from line snapshots.

At minimum:

Subtotal
Tax placeholder/seam
Discount placeholder/seam
GrandTotal
Currency

Do not implement actual Tax engine or Promotion engine now.

Given current locked architecture:

base price = Tax Exclusive

Do not fabricate tax.

If tax is not yet calculated, model it explicitly as not-yet-applied / zero-by-policy only where correct.

Do not silently imply tax-inclusive pricing.

Address / Fulfillment Boundary

Do NOT implement full Address/Fulfillment module in this task.

Order may preserve an opaque future fulfillment/contact snapshot seam.

Do not add shipping provider logic.

Do not tightly couple Order Domain to customer profile persistence.

Payment Boundary

Create only stable payment intent/reference seam for future:

OrderId

PaymentPurpose

Do NOT:

mark paid

call payment gateway

Cancellation

Cancellation must expose future Inventory release seam.

Do not implement seller/customer policy matrix yet.
