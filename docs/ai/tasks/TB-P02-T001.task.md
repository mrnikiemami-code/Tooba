## Locked Identity Principles

Preserve:

```text
Identity/User != Party/Organization
Authentication != Authorization
User account != Customer profile
User account != Seller organization
User account != Tenant
```

The identity module authenticates principals.

Business relationships belong elsewhere.

```text
Identity
```

Use the P01 module structure and boundary rules.


or equivalent aligned with current repository conventions.

```text
DbContext

```

## User Aggregate

Implement a minimal User aggregate.

At minimum preserve:

```text
UserId
Status
CreatedAt
UpdatedAt
credential/authentication-related state
```

Do not add customer-business fields such as:

```text
address
loyalty
company
tax profile
seller profile
```

Those belong to other capabilities.

---

## Login Identifier Model

Support multiple identifiers without hard-coding a single username field.

Required identifier kinds:

```text
Username
Email
Phone
```

Architecture must allow future:

```text
NationalId
external/provider identifier
other verified identifiers
```

Model identifiers as first-class owned records/entities.

Each identifier should support:

```text
type
normalized value
verification state
primary/preferred marker if needed
created/verified timestamps where useful
```

---

## Normalization

Normalization must be explicit and type-specific.

Examples:

```text
email normalization
username normalization
phone normalization
```

Do NOT apply one generic lowercase rule to all identifiers.

Normalization logic must be testable.

Do not bake Iran-only assumptions into canonical phone identity.

---

## Identifier Uniqueness

Uniqueness must be enforced for normalized login identifiers.

Hard rule:

```text
same normalized login identifier cannot authenticate two different users
within the same applicable identity scope
```

Document scope carefully for Marketplace vs SingleStore deployment model.

Do NOT use hostname as identity scope.

---

## Password Credential

Implement secure password credential foundation.

Use modern ASP.NET Core password hashing facilities or equivalent proven algorithm.

Do NOT invent custom cryptography.

Store only password hash metadata needed for verification.

Never store plaintext passwords.

Never log:

```text
password
password hash
OTP
authentication token
reset secret
```

Support future rehash/algorithm upgrade.

---

## Password Policy Boundary

Do not hard-code final commercial password policy into the domain.

Provide configurable policy seam for:

```text
minimum length
complexity if required
breached-password checks later
password history later
```

Keep current minimum safe and testable.

---

## Authentication Use Cases

Implement application-level contracts/use cases for at minimum:

```text
register/create user foundation
authenticate by identifier + password
identifier lookup
credential verification
disable/suspend user behavior
```

Do not expose EF entities directly.

No final HTTP API design explosion.

A minimal platform endpoint/test surface is acceptable if needed for integration tests.

---

## OTP Abstraction

Create an OTP verification/challenge abstraction only.

Conceptually:

```text
IOtpChallengeService
IOtpSender
```

or equivalent.

Do NOT integrate real SMS/email provider yet.

A fake/dev provider may be used in tests.

OTP must support future purposes such as:

```text
login
identifier verification
password reset
MFA
```

Do not hard-code one OTP purpose.

---

## MFA Readiness

Provide minimal MFA-ready model/boundary.

Do NOT implement full authenticator-app/WebAuthn UI.

Preserve future factors:

```text
OTP
TOTP
WebAuthn/Passkey
external IdP step-up
```

MFA policy belongs to authentication policy, not business roles.

---

## External Identity Provider Boundary

Create a clean boundary for future:

```text
Keycloak
OIDC
OAuth2
enterprise IdP
social login
```

Do NOT integrate Keycloak in this task.

Do NOT couple User aggregate to one provider.

External identities should map to durable internal UserId.

---

## Session / Token Boundary

Define authentication result/session boundary.

Do NOT prematurely hard-code one forever-token model.

Support future:

```text
cookie/session
access token
refresh token
external IdP token exchange
```

For this task, a minimal internal authentication result is enough.

Do not implement custom JWT crypto unless necessary and architecturally justified.

---

## Account Status

At minimum support safe conceptual states:

```text
Active
Disabled
Locked
```

Exact enum may vary.

Disabled/locked user must not authenticate.

Do not leak unnecessary account existence details in public authentication errors.

---

## Error Semantics

Use existing ProblemDetails foundation.

Authentication failure responses must avoid user enumeration where appropriate.

Separate conceptual outcomes such as:

```text
invalid credentials
disabled account
locked account
identifier not verified where policy requires
```

Public surface may intentionally collapse some outcomes for security.

Document internal vs public semantics.

---

## Audit Boundary

Do NOT implement full Business/Security Audit store here.

But authentication actions must expose events/seams so later Security Audit can record:

```text
login success
login failure
credential change
identifier verification
account lock/disable
```

Technical logs are NOT the audit system.

Use existing event foundation.

Do NOT publish every domain event externally.

Only explicit integration contracts may leave the module.

No MassTransit types in Domain/Application.

## Persistence

Use module-owned:

```text
IdentityDbContext
```

or repository naming convention.

Use dedicated PostgreSQL schema:

```text
identity
```

or equivalent.

Identity migrations are owned by Identity module.

No cross-module foreign keys.

---

## Tenant / Edition Semantics

Identity architecture must explicitly handle deployment context.

Marketplace:

```text
one marketplace identity store in marketplace DB context
```

SingleStore:

```text
identity data lives in each tenant's own database
```

Do NOT create one shared SingleStore identity database across tenants unless P00 says so.

Tenant resolution comes from existing context.

Identity code must not parse Host.

---

## Party / Organization Separation

Do NOT add:

```text
CustomerId
SellerId
OrganizationId
AgencyId
Company fields
```

into User just to make future flows easy.

Future linkage should be through Party/Membership contracts.

Document this strongly.
