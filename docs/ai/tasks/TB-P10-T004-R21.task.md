Title:
Atomic Checkout Commit Gate — Order + Reservation + Cart Conversion Must Succeed or Roll Back Together

Architect Intent

This is a SHORT, DECISIVE, HIGH-VALUE correctness gate.

We must prove that clicking «پرداخت» never clears/converts the Cart merely because the frontend was clicked.

Locked invariant:

Cart conversion is backend-authoritative and may occur ONLY after the atomic checkout commit succeeds.

Atomic commit scope must include the business state necessary before payment initiation:

Revalidate Cart

Revalidate final price / shipping inputs required by current flow

Acquire ALL required inventory atomically

Create Order

Create SellerOrders / OrderLines / required order aggregates

Create Reservation Cycle #1

Bind canonical reservations

Mark source Cart = Converted

COMMIT

Only AFTER successful DB commit may the frontend:

treat old Cart as converted/empty

show the committed Order as pending payment

initiate/navigate to payment

External payment initiation is NOT part of the database transaction.

If any step before COMMIT fails:

transaction rolls back

Cart remains Active with original lines/quantities

no Order remains

no SellerOrder remains

no active reservation remains

no Reservation Cycle remains active/orphaned

frontend must not clear Cart

no payment attempt starts

This task is intentionally narrow.
Do NOT redesign UX.
Do NOT alter reservation policy.
Do NOT create TB-P10-T005.
