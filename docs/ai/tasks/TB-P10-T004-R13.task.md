Title:
Committed Checkout Ownership + Active Cart Rotation — Payment Must Survive Order Commit While New Shopping Uses a Fresh Cart

Architect Review

Manual testing found two coupled post-commit lifecycle defects.

Defect A — Payment ownership still depends on converted Cart

Known Order:
01a096cd-eee4-7000-8954-683cb41244de

Known source Cart:
01a096ad-bcce-7000-8176-6c6820748fa9

Facts:

Order was successfully created.

SellerOrders are PendingPayment.

no Payment row exists yet.

source Cart is Converted.

/fa/payment loads checkout through GET /v1/storefront/checkout/{id}?cartId=....

guest ownership still depends on the old Cart secret.

missing/mismatched secret becomes a checkout access failure.

Host maps that failure to checkout.rejected.

customer sees the false message:
ثبت سفارش انجام نشد. لطفاً دوباره تلاش کنید.

The Order DID succeed. The Payment page lost committed-order ownership.

Defect B — active browser Cart still points to Converted Cart

After Order commit:

browser keeps old converted cartId

GET returns that converted Cart

ensureStorefrontCart does not rotate it

next AddToCart posts to the dead Cart

mutation is rejected because only Active Cart may mutate

customer sees:
عملیات سبد انجام نشد.

The old Cart was intentionally kept alive to preserve Payment ownership. That workaround is architecturally wrong.

Locked Rule

After successful Order commit:

committed Order/Checkout/Payment journey gets its own stable ownership proof;

active shopping Cart is detached from the converted source Cart;

Payment/Order ownership no longer depends on current active Cart;

converted Cart stays immutable history;

customer may start a fresh Cart while the previous Order is still PendingPayment;

starting a new Cart must not break Payment page/initiate/result/retry for the committed Order.

Do NOT patch only ensureStorefrontCart.
Do NOT keep Payment ownership coupled to Cart.
Do NOT make Converted Cart mutable.
Do NOT copy old secret into a new Cart.
Do NOT create duplicate Order/Payment.
Do NOT create TB-P10-T005.

5. Rotate Active Cart After Successful Order Commit

Once Order commit definitively succeeds:

source Cart stays Converted

persist committed Order proof before navigation

detach active-cart session pointer from old Cart

next ensureStorefrontCart creates/resolves a NEW Active Cart

Payment proof remains intact

Lazy creation is preferred if current design allows:
clear/rotate active Cart pointer at commit; create a fresh Cart on next shopping action.

Do not create an empty Cart eagerly unless necessary.

6. Harden ensureStorefrontCart

If stored current Cart resolves to:

Converted

Cancelled

Expired/terminal

inaccessible for current cart ownership

then:

discard/rotate only the active-cart reference

create/resolve a fresh Active Cart

preserve committed Order/Payment proof

Normal AddToCart must never POST against a Converted Cart.

No retry loop on cart.rejected.

7. Payment Page Ownership

/fa/payment must authorize the committed checkout as:

Authenticated

authenticated user/session + committed Order ownership.

Guest

committed Order/Checkout proof.

It MUST NOT require the current active Cart to equal the source Converted Cart.

If cartId remains temporarily in request shape for compatibility, backend must not use current active Cart state/secret as post-commit ownership.
