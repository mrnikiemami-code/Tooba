## 1. Verified current limitations (why a change is required)

| Area | Verified today | Consequence |
|---|---|---|
| Order draft | `cart_shipping_drafts` is keyed by `CartId` with ONE `ShippingMethodCode`/`Amount`/date/window | one method per cart |
| Accepted order | `checkouts` has ONE `ShippingMethodCode`(32)/`Label`(64)/`Amount`(18,2), `UNIQUE(CartId)` | one method per order |
| Order line | `order_lines` has **no** shipping column | an item cannot express its own method |
| Seller totals | `seller_orders` totals are merchandise-only; shipping is added at the payable boundary (`StorefrontCheckoutService.cs:357-358`) | shipping is a scalar, not a group fact |
| Fulfillment unit | `fulfillments`: `HasIndex(SellerOrderId).IsUnique()` | exactly **one** unit per seller today |
| Fulfillment shipment | `shipments`: `HasIndex(FulfillmentId)` **not** unique; `Shipment` already carries `ShippingMethodCode`/`Label` | **multiple shipments (hence multiple methods) per seller are legal today** |
| Payment | one `SellerOrder` allocation per seller (merchandise) + **one** `StoreShipping` allocation with a fixed sentinel target | shipping is one cart-wide bucket |
| Settlement | `settlement_entries` per `SellerOrder` with `gross × commission rate → net`; no shipping component anywhere | shipping money is never settled, shared or cost-tracked |
| Eligibility | `LoadEligibleMethodsAsync(cartSubtotal, province, language)`; `MaxSellerPreparationDays` = slowest seller | no seller/origin dimension exists in shipping selection |

Source of truth for these statements: `authority-map.txt`.

**Decisive finding:** the smallest owner-correct execution mapping does **not** need a new Fulfillment aggregate and does **not** need to break the one-unit-per-seller constraint — one `Shipment` per Order-owned shipping group inside the existing unit is already legal.

## 2. Proposed design (summary)

**Identity/lifecycle.** `ShippingGroupId` (UuidV7) is generated by Order at draft-selection time and carried unchanged through draft → accepted order → fulfillment → settlement. Tenant isolation is structural (per-tenant module database), so no tenant column and no cross-tenant relation. A group always belongs to exactly one `SellerOrderId`; a seller may have many groups.

**Merge rule (domain-enforced).** Two lines share a group only when seller, canonical `MethodCode`, fulfillment origin/context *(pending decision a)*, destination snapshot and scheduling inputs all match and both are eligible. Equal method code alone is never sufficient; two sellers are never merged.

**New state (additive, module-owned).**
- Order draft: `cart_shipping_groups` + `cart_shipping_group_lines` (membership keyed by Cart-owned `CartLineId` with **no cross-module FK**; whole-line assignment in v1).
- Accepted order: `order_shipping_groups` (+ FK to `checkouts` and `seller_orders`) + `order_shipping_group_lines` (+ FK to `order_lines`) with `UNIQUE(OrderLineId)` so no line can be double-assigned.
- Fulfillment: `shipments.ShippingGroupId` (nullable, stable correlation id, no cross-module FK) and one Shipment per group via the existing `CreateShipment(...)` overload.
- Settlement: `shipping_fee_allocations` + `shipping_fee_adjustments`.

**Contracts (additive only).** `StorefrontShippingSelectionRequest` gains `Groups[]` and keeps the legacy scalar as a single-group shorthand; `StorefrontShippingProjection`/`DraftView` gain per-group views; `PayableCheckoutSnapshot` gains `ShippingGroups[]` while keeping the aggregate `ShippingAmount`. The existing UI keeps working unchanged during the transition.

**Migration order:** M1 Order draft groups → M2 Order accepted groups → M3 Fulfillment `shipments.ShippingGroupId` → M4 Settlement allocations. No destructive change, no backfill: historical rows keep the legacy single-method read path.

**Money (Settlement-owned).** All amounts per group in one currency with an immutable placement snapshot and a versioned allocation policy. Reconciliation invariant, enforced fail-closed:

```
CustomerChargeAmount − DiscountAmount
  == CarrierPayableAmount + SellerShareAmount + MarketplaceShareAmount + ShippingTaxAmount
```

`SellerShareAmount` and `MarketplaceShareAmount` are **signed** (a marketplace subsidy is explicitly allowed); the discount funder is stored, not inferred; quoted vs actual carrier cost is an auditable `shipping_fee_adjustments` row, never an overwrite; one live allocation per group plus unique idempotency keys prevent double pay/refund. No percentage or commercial split is invented.

**UI.** Reuse the verified existing components/tokens only: method-card and selection classes from `storefront-shipping.tsx:613-633`, summary-card classes from `storefront-payment-handoff.tsx:270` (`bg-surface rounded-2xl border border-gray-200 p-5 shadow-sm`), item-row markup from `storefront-cart.tsx:230`, `formatOfferAmount` for Persian currency, existing RTL/responsive behaviour. Group wrapper is the same card plus a group header; no global CSS, no new tokens, no redesign.
