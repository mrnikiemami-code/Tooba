نسخه: 1.0 — 2026-11-21 (Asia/Tehran)  
وضعیت: الزام اجرایی مالک برای تسک‌های جدید و کار جاری در حد اختیار همان تسک.  
مرجع محصول: [OPERATOR-UX-ACCEPTANCE](../product/OPERATOR-UX-ACCEPTANCE.md)  
مرجع انتقال: [BRIDGE-WAKE-V1](../ai/TOOBA-PIPELINE-PROTOCOL.md)

## ۱. مسئله و تصمیم

تسک حجیم بدون نقشهٔ اجرا، تست‌های جزیره‌ای و پذیرش بر مبنای گزارش worker، به تحویل ناقص منجر شده است؛ نمونهٔ اصلی «ویرایش باز می‌شود ولی ذخیره/بازخوانی کار نمی‌کند». این سند تعریف کار تمام‌شده را اصلاح می‌کند؛ جایگزین معماری Domain، قاعدهٔ Contracts، CQRS، Design System یا قرارداد Bridge نیست.

یک تسک اصلی و یک محدودهٔ ثابت داشته باشیم، ولی اجرای آن به مراحل کوچک و وابسته شکسته شود. هر مرحله یک مسیر کاربر را تا دادهٔ ذخیره‌شده و بازخوانی آن تمام کند. چند فایل تغییرکرده یا تعداد بالای تست، واحد پیشرفت نیست.

هیچ سند یا ابزار، نبود همهٔ باگ‌ها را تضمین نمی‌کند. این روش باید نقص شناخته‌شده، حذف سناریو و ادعای بی‌شاهد را پیش از تحویل آشکار کند؛ مالک محصول نباید نقش تستر اولیهٔ مهندسی را داشته باشد.

## ۲. مسئولیت‌ها و اختیار

| نقش | مسئولیت | نمی‌تواند |
|---|---|---|
| معمار | خواندن سورس جاری، تعیین مرز و قرارداد، شناسه‌گذاری الزامات، نقشهٔ وابستگی، معیار پذیرش و بازبینی مستقل diff/شواهد | ابهام معماری را به worker واگذار کند، گزارش PASS را پذیرش تلقی کند یا بررسی‌نشده را قطعی بنامد |
| worker، از جمله Cursor | تکمیل برنامهٔ grounded پیش از کد، اجرای مراحل، تست خرابی و موفقیت، حفظ داده و شواهد صادقانه | دامنه را کوچک کند، تست متناسب با کد خود بسازد و جای معیار اصلی بنشاند، پذیرش معمار/مالک صادر کند یا تسک بعدی بسازد |
| مالک محصول | تعیین رفتار کسب‌وکار، اولویت و پذیرش تجربهٔ محصول | موظف به کشف اشکال‌های شناخته‌شدهٔ ذخیره/مجوز/بازیابی نیست |

برنامهٔ معماری پیش از کد الزامی است، ولی مراسم تأیید تازه برای هر تصمیم معمول لازم نیست. تصمیم در چارچوب اختیار تسک و معماری موجود گرفته و ثبت شود. تغییر قفل معماری، دامنه یا اقدام مخرب خارج از اختیار، blocker واقعی است. یک worker، بدون delegation مگر دستور صریح؛ review داخلی worker، بازبینی مستقل محسوب نمی‌شود.

## ۳. پیش‌نیاز صدور تسک

معمار قبل از صدور باید سورس entry pointها، جریان قدیمی/جدید، read/write و تست‌های مرتبط را بخواند. اگر هنوز مالک فرمان، قرارداد پاسخ یا رفتار محصول معلوم نیست، تسک را «رفع همه چیز» نام‌گذاری نکند. کار اکتشافی مجاز می‌تواند ابتدای همان تسک باشد؛ خروجی آن باید قبل از اولین تغییر production ثبت شود.

هر تسک باید این موارد را داشته باشد:

- Task-ID یکتا، Parent واقعی، Expected-Base واقعی و همان نام فایل و envelope مرسوم؛ بدون پسوند خودسرانهٔ COMPLETION یا استفادهٔ مجدد از یک Task-ID برای دامنهٔ متفاوت.
- شناسه‌های ثابت REQ-01 و بعدی؛ تعریف دقیق رفتار و مثال قبل/بعد، معیار موفقیت و شکست؛ صفر الزام ضروریِ مبهم مثل «UX حرفه‌ای شود».
- ریسک، data boundary، مرجع مجوز/زبان/تاریخ/DS، مسیرهای ورود مانند New/Edit/ردیف/bulk و نقش‌های مؤثر.
- معیار خروج روشن و نتیجهٔ مورد انتظار معمار؛ هیچ ادعای «همه بسته» با بند اجباری باز مجاز نیست.

الزامات به‌دلیل سخت‌بودن تست حذف نمی‌شوند. عدم کاربرد هر سناریو باید از قبل با دلیل ثبت شود؛ یک gate اجرایی اجباری را نمی‌توان در پایان به N/A تبدیل کرد.

## ۴. قبل از کدنویسی: ARCHITECTURE-PLAN.md

worker باید با الگوی [برنامه](../ai/delivery/PLAN-TEMPLATE.md) این موارد را پر کند:

1. **نقشهٔ مسیر واقعی:** UI entry → فرم و state → transport/BFF → endpoint → مجوز → validator/CQRS → Domain/persistence → serializer/DTO → mapper/verifier → نتیجهٔ UI → GET مستقل.
2. **مالکیت و قرارداد:** روش‌ها و فایل‌های واقعی، فیلدها، status/actionCode، version/occurrence و media identity؛ چه چیزی optional presentation است و چه چیزی اعتبارسنجی الزامی.
3. **وابستگی‌ها:** مثلاً قرارداد پاسخ پیش از success predicate؛ predicate پیش از recovery UI؛ بدون جایگزینی معماری موجود با abstraction عمومی تازه.
4. **جدول سناریوها:** happy path، cancel، خطای قطعی، نتیجهٔ نامشخص، retry/remount، تغییر actor/shop در حال اجرا، پاسخ دیررس، نسخهٔ stale، مجوز منفی و مسیرهای موجود قدیمی.
5. **مراحل کوچک:** هر مرحله یک اثر قابل مشاهده و آزمون دارد؛ مسئولیت UI و backend را طوری جدا نکند که «دکمه هست ولی فرمان وصل نیست».
6. **برنامهٔ بررسی:** کدام تست روی production method، کدام mounted UI، کدام browser، کدام persistence/provider اجرا می‌شود؛ جای خالی زیر اسم «تست کامل» پنهان نشود.

اگر برنامه بسیار بزرگ شد، task اصلی و تمام الزاماتش حفظ شوند؛ مراحل به کوچک‌ترین اثر قابل بررسی شکسته شوند. ایجاد چند Task-ID، توقف پس از هر مرحله یا گردش تأیید تازهٔ مالک، پیش‌فرض این روش نیست.

## ۵. چرخهٔ اجباری هر مرحله

**بازتولید → اصلاح → بررسی همان ضدنمونه → اتصال مسیر واقعی → بازبینی مرحله → ادامه**

- برای باگ، ابتدا counterexample معتبر روی رفتار قبل ثبت شود. تستی که از ابتدا سبز است اثبات رفع باگ نیست؛ اگر لازم بود negative control دقیق روی source قبل، در محل کنترل‌شده، بدون commit کد خراب انجام شود.
- شکست اولیه باید شکست رفتار موردنظر باشد، نه import/build/fixture شکسته.
- اجرای نو و ویرایش قدیمی، لینک مستقیم و ورود از جدول، هرکدام که در دامنه است واقعاً به owning command وصل شوند.
- هنگام تغییر shared component، مصرف‌کنندهٔ مجاورِ واقعاً در معرض ریسک هم بررسی شود؛ sweep بی‌ربط کل مخزن جای بررسی مرتبط را نمی‌گیرد.
- قبل از مرحلهٔ بعد، worker diff را با الزامات همان مرحله و invariants مرور و اشکال پیدا‌شده را همان‌جا رفع کند.
- این checkpoint داخلی مجوز Architect ACCEPT نیست. checkpointها خودکار به Task بعدی تبدیل نمی‌شوند.

## ۶. حداقل قرارداد پذیرش فرم ویرایش/ذخیره

هر تسک مؤثر بر ویرایش و persistence باید در ورودی واقعی محصول این چرخه را اثبات کند:

| سناریو | شاهد لازم |
|---|---|
| بازکردن رکورد موجود | مقدار واقعی و هویت همان رکورد/فروشگاه، نه فقط بازشدن modal |
| ویرایش و Save | capture دقیق method/path/body/version/key، یک فرمان مالک، بدون side effect ناخواسته |
| پاسخ موفق | تغییر خواسته‌شده در پاسخ معتبر؛ HTTP200 یا matching id به‌تنهایی کافی نیست |
| بازخوانی | خروج/بازکردن مجدد یا GET مستقل، همان مقدار جدید را نشان دهد؛ optimistic state شاهد persistence نیست |
| لغو/Escape/Back | حفظ/دورریختن تغییر با تصمیم روشن، URL صحیح، صفر درخواست در Cancel |
| شکست قطعی | دلیل محلی و قابل فهم، پیام موفقیت صفر، وضعیت فرم قابل اصلاح |
| قطع ارتباط/پاسخ malformed | نتیجه نامشخص صادقانه، intent حفظ‌شده و recovery در همان صفحه؛ retry همان فرمان بدون تکرار upload/add |
| تغییر context/همزمانی | پاسخ قدیمی state جدید را ننویسد؛ قفل به همان request تعلق داشته باشد؛ مسیر مجاز بعدی قابل اجرا بماند |
| مجوز | نقش صحیح مجاز، نقش فاقد permission/cross-shop مستقیم از API رد شود؛ ترکیب عملیات مجوز لازم خود را دارد |

برای delete، receipt/tombstone/occurrence معتبر طبق قرارداد مالک معیار است؛ GET404 و افزایش نسخه به‌تنهایی برای همهٔ replayها کافی نیستند. برای فهرست، query/selection/scroll و حذف آخرین ردیف صفحه؛ برای media، هویت قبل/بعد و مراحل upload/update؛ برای public player، load/ended/visibility/expiry؛ برای زبان، مرجع registry و RTL/LTR واقعی اضافه شود.

## ۷. درجات شواهد و ممنوعیت جایگزینی

| شاهد | چه چیزی را ثابت می‌کند | چه چیزی را ثابت نمی‌کند |
|---|---|---|
| خواندن سورس/تحلیل | مسیر و ریسک | اجرای موفق |
| unit/pure function | قرارداد همان تابع | ذخیره از فرم واقعی |
| mounted component با HTTP کنترل‌شده | رفتار فرم و transport/state | backend حقیقی، SQL، هندسه یا ویدیوی مرورگر |
| owning backend + serializer + controlled persistence | رفتار واقعی فرمان در provider اعلام‌شده | اجرای PostgreSQL از InMemory یا اتصال مرورگر |
| browser روی served UI با HTTP کنترل‌شده | interaction/geometry/media/browser | live backend outcome |
| مسیر متصل با owning backend کنترل‌شده/rollback | جریان کامل با provider و fixture مشخص | تغییر دادهٔ زندهٔ مالک یا پذیرش مالک |

هر شاهد label و محدودیت خودش را دارد. regex/source scan جای آزمون رفتاری نیست. 200 route، chunk marker و build فقط هویت/آمادگی فنی‌اند. mocked success که همیشه نتیجهٔ مطلوب می‌دهد، به‌تنهایی اثبات command نیست. «همان کامپوننت استفاده شده» معادل اجرای تمام سناریوها نیست.

حفظ داده اصل است: هیچ fixture زنده، seed/grant/reset/restore/cleanup/migration بدون اختیار صریح. از harness موجود کنترل‌شده یا rollback-only استفاده شود. نبود محیط، NOT_RUN/BLOCKED است؛ دادهٔ ساختگی را واقعی معرفی نکنید.

## ۸. کنترل اجرایی و گیت‌ها

در کنار TASK.md، فایل DELIVERY.json با [الگو](../ai/delivery/DELIVERY-TEMPLATE.json) ثبت شود. شناسه‌های manifest باید با ردیف‌های REQ تسک دقیقاً برابر باشند. TASK.md باید byte-exact بماند؛ hash ورودی gate از artifact صادرشدهٔ معمار گرفته شود، نه از بازنویسی worker.

دستور:

```bash
node docs/ai/delivery/check-readiness.mjs <task-folder> --stage plan --task-sha <issued-task-sha256>
node docs/ai/delivery/check-readiness.mjs <task-folder> --stage review --task-sha <issued-task-sha256>
```

- plan gate: برنامهٔ معماری، مراحل وابستگی و سناریوهای قابل‌آزمون قبل از production edit موجود باشند.
- review gate: تمام سناریوهای ضروری PASS و evidence واقعی دارای path/hash باشند؛ هیچ بند OPEN/FAIL/NOT_RUN/BLOCKED پنهان نباشد.
- هر evidence شامل file (نسبی داخل پوشهٔ همان task)، kind، provider، phase (before/after)، codeSha و sha256 واقعی فایل است. codeSha نسخهٔ production بررسی‌شده است؛ commit بعدیِ صرفاً اسناد را با نسخهٔ کد اشتباه نگیرید. شاهد before می‌تواند SHA پیش از اصلاح داشته باشد؛ شاهد after باید همان codeSha نهایی را پوشش دهد. زمان/commit برنامه باید قبل از تغییر production مستقل بررسی شود؛ hash به‌تنهایی ترتیب زمانی را اثبات نمی‌کند.
- ابزار فقط انسجام و تمام‌بودن ساختار و وجود/hash شواهد را کنترل می‌کند، نه حقیقت محتوای log یا کفایت مهندسی. worker می‌تواند log بسازد؛ معمار باید شواهد را مستقل بخواند و در دسترسی موجود rerun کند.
- gate باید در رسید نهایی همان task اجرا شود؛ در این نسخه به CI/Bridge متصل نشده است. موفقیت آن «آمادهٔ بازبینی ساختاری» است، نه پذیرش.
- تست‌های اثرپذیرفته و tsc پس از مرحلهٔ مرتبط؛ backend build/tests فقط در صورت تغییر backend؛ build production و هویت served در پایان کار UI. build کل solution در هر مرحله پیش‌فرض نیست.
- تغییر storefront تابع critical-storefront contract موجود است. خطای غیرمرتبط مستند شود؛ guard تضعیف نشود و الزام صادرشده با عبارت «known limit» حذف نشود.

## ۹. تحویل، بازبینی مستقل و وضعیت‌ها

قالب ثابت Bridge و enumهای آن دست‌نخورده می‌ماند: Status همان PASS/PARTIAL/BLOCKED/RECOVERY_CONFLICT است. PASS فقط ادعای فنی worker است و در body باید Readiness: READY_FOR_ARCHITECT_REVIEW بیاید. Worker PASS != Architect ACCEPT != OWNER_ACCEPTED.

معمار پیش از پذیرش:

- TASK اصلی و hash، تمام REQها، دامنهٔ واقعی diff و ورودی‌های New/Edit/legacy را تطبیق دهد.
- test names را با assertions بخواند؛ helper را mount و mount را backend/browser ننامد.
- counterexampleها و مسیر persistence/recovery/permission را بررسی و در محیط در دسترس rerun کند؛ انجام‌نشده را روشن بنویسد.
- build/served identity را به آخرین تغییر کد متصل کند؛ build قبل از fix شاهد fix نیست.
- نقص‌ها را به BLOCKING_DEFECT / EVIDENCE_GAP / RISK / MAINTENANCE_DEBT تفکیک کند؛ بدهی غیرمرتبط تاریخی را بی‌دلیل مانع تحویل نکند.
- ARCHITECT-REVIEW.md را با یافته‌های مستند و تصمیم ACCEPT/REPAIR/BLOCK ثبت کند؛ صرف PASS یا بیلد قبول نیست.

بند اجباریِ ناقص یعنی PARTIAL/BLOCKED. تغییر محدوده فقط با اختیار معمار/مالک و ثبت دلیل ممکن است، نه بازنویسی نتیجه. پس از پذیرش معمار، مالک تجربهٔ محصول را بررسی می‌کند؛ کاربر نباید برای بار اول بفهمد دکمهٔ Save وصل نیست.

## ۱۰. بازیابی و اعمال روی کار جاری

این سند در ابتدای AGENTS، recovery، START-HERE و پروتکل pipeline لینک می‌شود. در بازیابی جلسه، ابتدا این سند، سپس task دقیق، برنامه، manifest و آخرین review خوانده شود. pointerهای قدیمی تاریخچه‌اند، پذیرش نسخهٔ جدید نیستند.

این تغییر فقط governance و ابزار کنترل اسناد است؛ هیچ feature را کامل، هیچ R20/R21 را ACCEPT و هیچ کار جدیدی را در Bridge dispatch نمی‌کند. برای کار درحال‌اجرا، برنامه و manifest در همان Task-ID و قبل از مرحلهٔ بعد تکمیل شوند؛ شواهد قبلی فقط با provenance قابل استفاده‌اند. گیت‌های داخلی ادامهٔ کار مجاز را متوقف نمی‌کنند مگر blocker واقعی یا توقف صریح.

معیار موفقیت این روش، کم‌شدن تعداد تسک‌ها یا زیادشدن تعداد تست نیست: کاهش نقص فرارکرده از پذیرش، نبود ادعای بی‌شاهد و اثبات مسیرهای واقعی کاربر است. هر نقص فراری باید سناریوی جاافتاده و علت را به همین چک‌لیست برگرداند.
