# TOOBA Next.js design fidelity protocol
Status: mandatory for new or revised UI designs; does not authorize changes to approved visuals or frozen architecture.

## Design stage
OpenDesign MUST deliver runnable React/TypeScript TSX in the existing Tooba Next.js workspace, not standalone HTML as the acceptance artifact. Inspect installed OpenDesign capabilities first. If direct TSX output is unavailable, use its verified export capability BEFORE owner approval; approve only the resulting Next.js preview. If neither works, report BLOCKED, not a substitute HTML approval.
Reuse actual shared components (including AppDataGrid, forms, tokens, fonts, icons), routing/layout and locale registry. No parallel shell, duplicate controls, new dependencies or global style overrides without authorization. Preview uses isolated deterministic fixtures, no production writes, no fake production values. Separate presentation from typed data/action adapters using existing feature boundaries.
Design states: desktop/mobile, fa RTL/en LTR, loading, empty, error, validation, disabled/enabled, long content, and all affected tabs. Define intentional numeric formatting (localized display, canonical machine values).
## Approval lock
Record approved TSX/CSS paths and commit/blob identity, preview route, fixtures, viewport, browser/font settings, and owner approval in the active OpenSpec change. No implementation until owner approves. Existing approved designs are not redesigned automatically. Keep approved source immutable; any visual deviation requires explicit approval and new reference. Do not replace a baseline to make a failing comparison pass.
## Implementation
Reuse the approved presentation source in the production route; connect real typed API/state/actions without reconstructing the JSX or styling. Any unavoidable component adaptation must be recorded and reviewed. Preserve permissions, ownership, persistence and business contracts. Preview-only fixtures must never enter production data paths.
## Acceptance
Independent verifier compares reference and actual runtime with identical fixtures, locale, viewport, browser and fonts. Use existing visual harness where available; otherwise deterministic Playwright comparisons of geometry and computed styles (alignment, spacing, typography, wrapping, overflow) plus automated pixel comparison only where existing policy permits screenshots. No screenshot evidence in chat. For pilot use 1 CSS px geometry tolerance and exact comparable typography/color values; justify any exception before acceptance. Test fa/en and desktop/mobile. Fail on unexpected mismatch, mixed digits, broken tabs, clipped labels or nonfunctional save; prove persistence by independent reread. Include negative control deliberately introducing a layout mismatch and prove the verifier rejects it; restore immediately. Run applicable build/typecheck, focused tests, existing regression gates and independent Impeccable audit (audit only, not redesign). Worker PASS is not owner acceptance. Record commands, reference identity, measured results and failures; unrun gates are NOT_RUN. STOP_FOR_ARCHITECT.
## Pilot
Offer product-variation tab only: inspect existing approved TB-295 design and TB-296 implementation, preserve intended UI and existing behavior. First prove runnable Next.js reference using shared components; STOP_FOR_ARCHITECT for owner design approval before integration. No other tabs, domain changes, migrations or live writes authorized by this protocol.

## Feedback surface rule (TB-296-R9)
Offer and other repaired feature routes use the shared existing notification mechanisms: `react-toastify` `ToastContainer` from `app/providers.tsx` with `autoClose=3000` for transient success, and the shared `design-system` `MessageBox` for blocking operation errors, duplicate/conflict with authorized record navigation, uncertain outcomes requiring reconciliation and dirty-exit confirmation. Inline validation stays at the field. No persistent success banner, no duplicate banner+toast/modal for one outcome, and no parallel notification system.
