MISSION A - REPAIR THE VERIFIED 500  [DONE]
Cause reproduced from source: RuleFor(x => x.Scope).NotNull() followed by RuleFor(x => x.Scope.CountryId).
FluentValidation's default CascadeMode.Continue means a failed NotNull rule does not stop the next rule, and
evaluating that rule dereferences x.Scope (null when scope is omitted from the JSON body) -> NullReferenceException.
That is not a SemanticError, so it never reached the canonical validation.failed path and surfaced as
platform.unexpected / 500.
Repair, in BOTH ShippingRatePolicyWriteRequestValidator and ShippingCoverageGrantWriteRequestValidator:
  - new stable declared code ShippingValidationCodes.ScopeRequired = "shipping.validation.scope_required";
  - RuleFor(x => x.Scope).NotNull().WithErrorCode(ScopeRequired);
  - every nested-property rule moved behind When(x => x.Scope is not null, ...) so the member access is never
    evaluated for an absent scope.
Untouched and still enforced: shipping.validation.country_required, shipping.validation.service_area_requires_city
(including service-area-without-city), the body-vs-route service-code rule, the Geography domain validator
(IShippingDestinationScopeValidator), all rate/grant persistence semantics.
Proof (in-memory, NOT a live HTTP claim): (1) a locally built validator using the OLD rule shape throws
NullReferenceException for a null scope, while the repaired validator returns a declared failure;
(2) ValidationBehavior raises FluentValidation.ValidationException, and SafeErrorMapper.MapValidation maps it to
