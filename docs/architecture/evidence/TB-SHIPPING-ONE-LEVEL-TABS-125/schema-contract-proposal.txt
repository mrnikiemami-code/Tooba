TB-SHIPPING-ONE-LEVEL-TABS-125 — MISSION B(i): proposed schema + contract evolution

Labels: [VERIFIED] = exists in code/DB today (see authority-map.txt).
        [PROPOSED] = does not exist; this document proposes it for Architect approval.
Nothing here is implemented, migrated or applied. No migration code is written in this task.
Owner invariant: Order owns draft + accepted order snapshot; Fulfillment owns execution
identity/method binding and actual carrier cost; Settlement/Wallet/Payment own allocations,
ledger and money movement; Pricing/Tax own calculations. Host composes only.

================================================================================
1. GROUP IDENTITY AND LIFECYCLE
================================================================================
Identity: ShippingGroupId = UuidV7, generated by Order at draft-selection time and carried
unchanged through draft -> accepted order -> fulfillment execution -> settlement entries.
This satisfies "stable ShippingGroupId ... preserve stable IDs for traceability".

Tenant: satisfied structurally — each tenant has its own module database (the Order
DbContext resolves its connection from ICurrentCommerceContext via ToobaNpgsql), so a
tenant column is NOT added and no cross-tenant relation is possible. [VERIFIED pattern]

Lifecycle states (Order-owned, minimal):
  Draft -> Confirmed (at order conversion) -> Cancelled (cancel/full reversal)
Execution state remains Fulfillment-owned (ShipmentStatus); Order does not mirror it.

Group scope key: (CartId) in draft, (CheckoutId, SellerOrderId) in accepted order.
A group ALWAYS belongs to exactly one seller order; a seller order MAY have many groups.

Merge rule (the core of the requirement, domain-enforced):
  two order lines are placed in the same group only when ALL hold:
    - same SellerOrderId / SellerPartyId
    - same canonical MethodCode (and same LegacyServiceCode/OptionCode when present)
    - same authorized fulfillment origin/context  [if origin is adopted; see decision (a)]
    - same destination snapshot + same delivery scheduling inputs
    - both eligible for that method per Fulfillment/Pricing eligibility policy
  Equal method code ALONE is never sufficient. Two sellers are never merged.

================================================================================
2. [PROPOSED] DRAFT STATE (Order-owned) — extends the existing cart_shipping_drafts
================================================================================
cart_shipping_drafts keeps its header role (recipient/address/contact/note/guest hash).
Its cart-wide method columns become DEPRECATED FOR WRITE; they are retained for
backward compatibility and as the trivial single-group projection (see §6).

  cart_shipping_groups                                       [PROPOSED]
    ShippingGroupId     uuid        PK, ValueGeneratedNever
    CartId              uuid        NOT NULL, FK -> cart_shipping_drafts(CartId) ON DELETE CASCADE
    SellerPartyId       uuid        NOT NULL
    MethodCode          varchar(64) NOT NULL      (canonical, e.g. tipax:standard)
    ServiceCode         varchar(64) NULL          (distinct field, per contract)
    OptionCode          varchar(64) NULL          (distinct field, per contract)
    MethodLabelSnapshot varchar(128) NOT NULL     (presentation only)
    AmountSnapshot      numeric(18,2) NOT NULL    (server-computed; client cannot forge)
    Currency            char(3)     NOT NULL
    MinimumDeliveryDate date        NOT NULL
    SelectedDeliveryDate date       NULL
    SelectedDeliveryTimeWindow varchar(32) NULL
    LeadDaysSnapshot    int         NOT NULL
    QuotePolicyVersion  varchar(64) NOT NULL      (rate/policy version used)
    State               varchar(16) NOT NULL      ('Draft')
    UpdatedAt           timestamptz NOT NULL
    indexes: PK(ShippingGroupId); IX(CartId); IX(CartId, SellerPartyId)
    checks:  AmountSnapshot >= 0; Currency ~ '^[A-Z]{3}$'

  cart_shipping_group_lines                                 [PROPOSED]  (membership)
    ShippingGroupId     uuid        NOT NULL, FK -> cart_shipping_groups ON DELETE CASCADE
    CartLineId          uuid        NOT NULL      (Cart-owned id; NO FK across modules)
    AssignedQuantity    numeric(18,6) NOT NULL    (v1: full line quantity)
    PK(ShippingGroupId, CartLineId)
    UNIQUE(CartLineId)                            <-- a line is in at most ONE group
    checks: AssignedQuantity > 0

  CartLineId is deliberately NOT a foreign key: Cart owns cart lines and Order must not
  create a cross-module physical relation. Order already reads cart lines through
  ICartPresentationGateway. [VERIFIED seam]

================================================================================
3. [PROPOSED] ACCEPTED ORDER STATE (Order-owned) — new sibling of checkouts
================================================================================
  order_shipping_groups                                     [PROPOSED]
    ShippingGroupId     uuid        PK, ValueGeneratedNever
    CheckoutId          uuid        NOT NULL, FK -> checkouts(CheckoutId) ON DELETE CASCADE
    SellerOrderId       uuid        NOT NULL, FK -> seller_orders(SellerOrderId) ON DELETE CASCADE
    SellerPartyId       uuid        NOT NULL            (denormalized for lookup/lookup-index)
    MethodCode          varchar(64) NOT NULL
    ServiceCode         varchar(64) NULL
    OptionCode          varchar(64) NULL
    MethodLabelSnapshot varchar(128) NOT NULL
    OriginRef           varchar(64) NULL                [only if decision (a) = adopt]
    ShippingChargeSnapshot numeric(19,4) NOT NULL
    Currency            char(3)     NOT NULL
    MinimumDeliveryDate date        NOT NULL
    RequestedDeliveryDate date      NULL
    RequestedDeliveryTimeWindow varchar(32) NULL
    LeadDaysSnapshot    int         NOT NULL
    QuotePolicyVersion  varchar(64) NOT NULL
    CalculatedAt        timestamptz NOT NULL            (immutable placement snapshot time)
    State               varchar(16) NOT NULL            ('Confirmed' | 'Cancelled')
    indexes: PK(ShippingGroupId); IX(CheckoutId); IX(SellerOrderId);
             IX(SellerPartyId); IX(ShippingGroupId, State)
    checks:  ShippingChargeSnapshot >= 0

  order_shipping_group_lines                               [PROPOSED]  (membership)
    ShippingGroupId     uuid        NOT NULL, FK -> order_shipping_groups ON DELETE CASCADE
    OrderLineId         uuid        NOT NULL, FK -> order_lines(LineId) ON DELETE CASCADE
    AssignedQuantity    numeric(18,6) NOT NULL
    PK(ShippingGroupId, OrderLineId)
    UNIQUE(OrderLineId)                          <-- no line assigned twice
    checks: AssignedQuantity > 0

  Address is NOT duplicated on the group: it stays on checkouts (single address per
  checkout today) to avoid a second source of truth. Delivery SCHEDULING is per group
  because different methods legitimately promise different dates/windows.

Invariants (domain + focused tests; coverage is not expressible as a simple constraint):
  I1 every order line of a SellerOrder appears in exactly one group of THAT SellerOrder;
  I2 no order line appears in two groups (DB-enforced by UNIQUE(OrderLineId));
  I3 sum(AssignedQuantity) per order line == order line quantity (v1: whole-line, so exact);
  I4 every group's SellerOrderId belongs to the same CheckoutId;
  I5 a group's method is eligible for that seller/destination (Fulfillment/Pricing policy);
  I6 an order with one seller and one method still produces exactly ONE group.

================================================================================
4. [PROPOSED] CONTRACTS / COMMAND-QUERY TRANSITION (Order.Application + Payment.Contracts)
================================================================================
Order storefront Contracts (evolve, not replace):
  StorefrontShippingSelectionRequest
    keeps: CartId, ExpectedCartVersion, recipient/address fields, CustomerNote, names
    adds : IReadOnlyList<StorefrontShippingGroupSelection> Groups
             { string ShippingMethodCode, string? ServiceCode, string? OptionCode,
               IReadOnlyList<Guid> CartLineIds, string SelectedDeliveryDate,
               string SelectedDeliveryTimeWindow }
    legacy: ShippingMethodCode/SelectedDeliveryDate/SelectedDeliveryTimeWindow retained as
            an OPTIONAL single-group shorthand; if Groups is empty and the legacy scalar is
            present, the server materializes exactly ONE group covering all cart lines of the
            cart (identical to today's behaviour). Additive => no breaking change for the
            current UI during the transition.
  StorefrontShippingProjection
    adds : IReadOnlyList<StorefrontShippingGroupView> Groups
             { Guid ShippingGroupId, Guid SellerPartyId, string MethodCode,
               string? ServiceCode, string? OptionCode, string MethodLabel,
               decimal PriceAmount, string Currency, decimal SubtotalExclusiveOfTax,
               IReadOnlyList<Guid> CartLineIds, string MinimumDeliveryDate,
               string? SelectedDeliveryDate, string? SelectedDeliveryTimeWindow }
    keeps: Methods (eligible catalog for the chosen destination), Draft, SelectedMethodCode,
           SelectedShippingAmount (now = sum of group amounts; retained for compatibility)
  StorefrontShippingDraftView
    adds : Groups[] with the same per-group identity + amounts; header fields unchanged.

Payment contracts:
  PayableCheckoutSnapshot.ShippingAmount stays as the aggregate customer charge.
  adds : IReadOnlyList<PayableShippingGroupSnapshot> ShippingGroups
           { Guid ShippingGroupId, Guid SellerOrderId, decimal ChargeAmount, string Currency }
  => Payment keeps ONE customer charge but can allocate and reference per-group identity.
     The existing StoreShipping sentinel bucket survives as the "platform bucket" default.

Command/query flow (CQRS, unchanged shape):
  SaveStorefrontShippingSelectionCommand        -> validates + upserts draft groups (Order)
  GetStorefrontShippingProjectionQuery          -> per-group projection (Order)
  GetStorefrontPaymentDraftQuery                -> per-group payable breakdown (Order->Payment)
  Checkout submit (existing)                    -> converts draft groups -> order groups
                                                   idempotently inside the existing
                                                   checkout idempotency key boundary
  Fulfillment handoff (existing bridge)         -> one spec per group

Order conversion snapshot: at submit, Order freezes group method/label/amount/currency/
lead-days/quote-policy-version/date-window and the destination snapshot taken from the
draft. Later changes to the shipping catalog or rates never rewrite these rows.

5. [PROPOSED] FULFILLMENT EXECUTION MAPPING (minimum possible change)
================================================================================
KEEP fulfillments.HasIndex(SellerOrderId).IsUnique()  [VERIFIED] — unit granularity unchanged.
USE the already-legal multiple-Shipments-per-unit capability      [VERIFIED]:
  shipments
    adds: ShippingGroupId uuid NULL (no cross-module FK; stable correlation id)
  index: IX(ShipmentId), IX(ShippingGroupId) [PROPOSED]
  rule: one Shipment per Order-owned shipping group is created through the existing
        FulfillmentUnit.CreateShipment(..., shippingMethodCode, shippingMethodLabel, ...)
        overload, so no new Fulfillment aggregate/method is introduced.
  shipment_items already bind OrderLineId + Quantity          [VERIFIED]
  => Fulfillment consumes the authoritative Order grouping instead of inferring it from
     Persian labels, and partial dispatch/cancel/tracking already operate per shipment,
     which is now exactly per group.

OrderFulfillmentBridge handoff becomes: for each SellerOrder, pass its groups
  (ShippingGroupId, MethodCode, MethodLabel, [OrderLineId, Quantity]...) instead of the
  single checkout-level code. OrderFulfillmentContracts gains that list additively.

6. BACKWARD COMPATIBILITY AND MIGRATION SEQUENCE (module-owned only)
================================================================================
Confirmed existing schema (must not be destructively altered): checkouts, cart_shipping_drafts,
seller_orders, order_lines, fulfillments, shipments, shipment_items, settlement_entries,
payment allocations.

Compatibility strategy:
  - All new tables are ADDITIVE; existing columns are kept (no drop, no rename, no
    destructive overwrite). Legacy rows keep working exactly as before.
  - Legacy/historical checkouts with a cart-wide method remain readable and settle as today
    (single StoreShipping bucket). A legacy checkout is treated as "one implicit group" at
    read time by the projection/readers, NOT back-filled by a migration.
  - New orders: draft always materializes at least one group, so every new order has an
    explicit group set; checkouts.ShippingMethodCode/Amount continue to be written as the
    single-group projection for readers that are not yet group-aware (bounded transition
    window; retirement is decision (d)).

Migration sequence (one migration per module, in this order):
  M1 Order: create cart_shipping_groups + cart_shipping_group_lines (+ indexes/checks)
  M2 Order: create order_shipping_groups + order_shipping_group_lines (+ indexes/checks)
  M3 Fulfillment: add shipments.ShippingGroupId (nullable) + index
  M4 Settlement: create shipping_fee_allocations + shipping_fee_adjustments (+ indexes/uniques)
No data backfill migration in v1: historical rows remain legacy; the legacy read path is
explicit and testable. No Host-owned persistence, no generic DbContext, no raw SQL.

================================================================================
7. ACCEPTANCE CASES -> OWNER-MAPPED INVARIANTS
================================================================================
(1) one seller + two methods            => 2 order_shipping_groups, I1..I6 hold, 2 shipments
(2) two sellers + same method           => 2 groups (never merged), 2 units
(3) same seller + same method + incompatible origin => 2 groups [requires decision (a)]
(4) compatible items                    => 1 group, membership/quantity exact
(5) persisted roundtrip                 => methods/grouping/fees/schedule survive reload+back-nav
(6) partial shipment or cancel          => only the affected group/shipment changes;
                                           UNIQUE(OrderLineId) and per-group money prevent
                                           double assignment / double charging
Each case must be proved by DB readback through authorized module APIs, not by a UI mock.
