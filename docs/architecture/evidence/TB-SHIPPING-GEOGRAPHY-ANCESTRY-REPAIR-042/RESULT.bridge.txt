INSERT / UPDATE LOOPHOLES - FALSIFIED THEN CLOSED (log-insert-gap.txt)
The 041 claim "a freshly inserted row's id is new, so it cannot already be in a chain" considered only one
new row at a time and is WRONG for a multi-row INSERT: the composite FK is an AFTER ROW constraint fired at
end of statement, so a pair of rows created by ONE statement satisfies it and commits a cycle.
- G1: same-statement two-row INSERT (A->B, B->A) with the new insert trigger disabled -> "INSERT 0 2" and
  the table afterwards held G1->G2 and G2->G1: a committed cycle, exactly the 041 hole, reproduced on a real
  PostgreSQL 17.
- G2: identical statement with the insert trigger enabled -> ERROR 23514
  geography.administrative_area.ancestry_cycle, and rows_after_rejected_insert = 0 (nothing committed).
- G3: the same pair built by two UPDATEs -> first UPDATE 1, second ERROR 23514; graph remains acyclic.
- T2b in the deterministic log is the same falsification: multi-row INSERT cycle rejected with 23514.
Repair: TriggerSql now installs two ordinary, non-deferrable, immediate triggers sharing one function -
trg_administrative_areas_ancestry_guard_update (AFTER UPDATE ... WHEN NEW.parent IS NOT NULL AND
(OLD.parent IS DISTINCT FROM NEW.parent OR OLD.country_id IS DISTINCT FROM NEW.country_id)) and
trg_administrative_areas_ancestry_guard_insert (AFTER INSERT ... WHEN NEW.parent IS NOT NULL).
Two triggers instead of one is empirically forced: PostgreSQL rejected the first attempt with
"SqlState 42P17: INSERT trigger's WHEN condition cannot reference OLD values" (trigger.c:620). Splitting
keeps the precise "an ancestry link actually changed" predicate instead of weakening the guard to a blanket
per-row call (which would take the serialization lock for every unrelated column write).
Immediate instead of deferrable (041 used DEFERRABLE INITIALLY IMMEDIATE): a deferred check would run at
COMMIT under a commit-time snapshot whose visibility of concurrently committed edges is not demonstrable,
and would let a cycle exist transiently inside a transaction. Statement-end firing is what makes the
multi-row-INSERT cycle visible, and it removes the deferred window entirely. The recursive walk, the depth
bound 4096, the advisory lock pg_advisory_xact_lock(20261014, 41), the READ COMMITTED fail-closed
precondition, the stable tokens and every previously accepted constraint are unchanged.
