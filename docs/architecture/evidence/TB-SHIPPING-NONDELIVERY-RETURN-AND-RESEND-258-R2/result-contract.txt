--- CONFIRMED ROOT CAUSES (measured, not guessed) ---
A. AdminOrderOperationsOrchestrator.Operations.cs sent record_non_delivery / start_return / record_return_receipt /
   resend_shipment into RunProjectedCoreAsync, whose EnsureProjectedActionAllowedAsync requires the action to exist in
   the CURRENT projection. After a resend consumed source capacity, or a receipt moved Returning -> Returned, that
   action disappeared, so an exact retry of a LOST RESPONSE was rejected before the owning Fulfillment replay could
   answer it. The durable fact existed; the public command could not reach it.
B. admin-order-operational-delivery-section.tsx mounted the exception dialog only from a normal action button, and
   those buttons exist only while canRecordNonDelivery / canStartReturn / canRecordReturnReceipt / canResend are true.
   The section never read the retained attempt store, so after a refresh or partial/full progress the operator had no
   visible way back to the reviewed request still owed an answer.
C. post-dispatch-exception-dialog.tsx modelled a receipt line as one quantity + one condition selector and emitted ONE
   item per line, so the ordinary "2 usable + 1 damaged" physical receipt for one parcel line was unreachable in the
   UI even though the domain already accepted it.

--- LANDED (A) public-command exact-intent reconcile ---
New narrow read-only contract Tooba.Fulfillment.Contracts.Operations.PostDispatchIntent / PostDispatchIntentKind /
PostDispatchIntentState (NotRecorded | Recorded | ResolvedCancelled | Conflict) / PostDispatchIntentResult and
IFulfillmentAdminOperations.ReconcilePostDispatchIntentAsync, implemented by FulfillmentAdminOperationsAdapter ->
FulfillmentDirectory.Returns.cs -> new FulfillmentUnit resolvers ResolveRecordedNonDelivery /
ResolveRecordedReturnStart / ResolveRecordedReturnReceipt / ResolveRecordedResendIntent.
ONE orchestrator seam RunPostDispatchExceptionAsync now serves all four public operations and, in order:
 1. loads the checkout and the CURRENT actor's effective access - a retained browser envelope is never authorization
    (order.operation.denied);
 2. requires the parcel to belong to THIS checkout AND the requested fulfillment (order.operation.invalid otherwise);
 3. builds the exact reviewed intent with the same validation the mutation uses (shared BuildReceiptItems /
    BuildResendLines), so replay and mutation cannot disagree about the request;
 4. asks the owning durable facts: Recorded / ResolvedCancelled return the authoritative snapshot with ZERO writes and
    no actor/time reattribution (a cancelled recorded resend is history, never recreated); Conflict raises the typed
    fulfillment.nondelivery.conflict / fulfillment.return.receipt_conflict /
    fulfillment.return.receipt_already_recorded / fulfillment.resend.intent_conflict;
 5. ONLY NotRecorded falls through to the unchanged EnsureProjectedActionAllowedAsync (allowReturnLifecycleFallback
    false) and then the real mutation - an absent record can never turn a readiness failure into a new allocation.
Receipt identity now has ONE authority (ShipmentReturnReceipt.MatchesItems) shared by the mutating replay and the
read-only answer; resend identity stays one authority (RecordedResendAnswersIntent). No global guard was removed, no
client flag is trusted as authorization, no bare error text is used as proof, no generic idempotency framework added.
