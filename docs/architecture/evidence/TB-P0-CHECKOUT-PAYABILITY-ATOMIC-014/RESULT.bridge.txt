FINDINGS
 F1 A gate that trusts the cycle row STATUS alone authorizes money on released stock for 6–15 s per cycle.
    The canonical ReservationCyclePayabilityPolicy.IsActive (Order.Application/ReservationCycle/Policies/ReservationCyclePayabilityPolicy.cs:10-14:
    Active && SecondsRemaining > 0) does reject inside that window; a status-only check does not.
 F2 reservation.expires_at == cycle.expires_at in all observed rows is a CONFIGURATION COINCIDENCE, not an
    enforced invariant: both derive from the same `now` + store policy here (policy_source='store',
    effective_hold_minutes=1 on all 11 cycles), but they are computed by different calls with different
    fallbacks — reservation: CheckoutDirectory.Reservations.cs:42 -> :114-131 (cycle policy, else
    _holdPolicy.ResolveInitialExpiresAt(now), else +2 h); cycle: :83-111 with policy from :133-146 whose
    FALLBACK is new ReservationCyclePolicySnapshot(120, 120, 3, "platform"). If the cycle-policy resolver is
    absent while a store/category setting clamps the reservation TTL to minutes, the cycle stays Active for
    up to 120 min after the hold is gone. Nothing in code or schema ties the two deadlines.
 F3 Neither worker coordinates: the Inventory release is not subordinate to the cycle row, and the cycle
    row is not closed by the Inventory release. There is no shared row, lock, or CAS today.

== 9. RESIDUAL RACES (even after S1-S3; must not be called race-free) ==

Between the CAS commit and the provider request the hold can elapse by wall clock (inherent; today handled by the
paid-supply reacquisition path EnsurePaidDurableSupplyAsync), and the cycle close worker may mark the cycle Expired
right after our CAS (harmless ordering, same reason). The CAS closes the COMPETING-TRANSACTION race; it is not a
global "no money after expiry" proof.
