ROOT CAUSE (confirmed deterministically, not statistically)
The generated member reference used the first eight hex characters of a UUIDv7 ShipmentId:
  memberCode = $"{baseCode}-{member.ShipmentId.ToString("N")[..8].ToUpperInvariant()}"
Those eight characters are the top 32 bits of the UUIDv7 millisecond timestamp and are CONSTANT for
about 65.5 seconds, so every member of a package generated the SAME code. The second member hit the
global unique guard and threw fulfillment.tracking.duplicate. Live proof (read-only):
  package MP-01A12F796EF1 | status=Created | tracking_reference=125444
  member 01a12f79-1ad4-7000-9174-3237c0d645bf | Dispatched | 125444-01A12F79
  member 01a12f79-33ed-7000-b7ad-e562dcf67be8 | Created    | (none)
  first eight hex characters of BOTH shipment ids = 01A12F79  (identical)
The second defect is the loop shape: DispatchConsolidatedPackageAsync called _db.SaveChangesAsync()
per member (AssignTrackingCoreAsync + DispatchShipmentCoreAsync), so member 1 was committed and left
permanently Dispatched while member 2 threw and the package stayed Created and unretryable.

GATE A — WHAT CHANGED
BuildMemberTrackingReference(packageTrackingReference, shipmentId):
  suffix = shipmentId.ToString("N").ToUpperInvariant()          // full 128-bit identity, 32 hex chars
  base   = packageTrackingReference.Trim() trimmed to 128-32-1 = 95 chars
  code   = base.Length == 0 ? suffix : $"{base}-{suffix}"
Uniqueness now has a proof, not a heuristic: member shipment ids are distinct, the suffix is the
complete identity, and the base prefix is identical for every member of the package, so distinct
identities can never map to equal codes. Length is bounded to the shipments.tracking_reference
column ceiling (128). No carrier/DB contract change was needed: nothing in the repository parses the
generated suffix (searched Substring/Split suffix parsing: zero matches) and no consumer depends on
the eight-character form. Existing references are NEVER rewritten: generation happens only when the
member reference is empty and the package has a central code; an already-Dispatched member is
skipped before any mutation, so the live 125444-01A12F79 row cannot be touched.

GATE B — WHAT CHANGED
DispatchConsolidatedPackageAsync is now two phases:
 (1) BuildDispatchStepsAsync — validate and plan, write nothing: load each active member, validate
     its shipment status (Dispatched/InTransit/Delivered => skip; anything but Created => throw
     fulfillment.package.member_state_changed), generate the collision-free reference, reject
     in-batch duplicates via a case-insensitive Dictionary, then run ONE query
     (EnsureGeneratedTrackingReferencesAreFreeAsync) that checks every generated code against the
     global unique guard excluding the members themselves. Any failure throws BEFORE any mutation.
 (2) apply all tracking + all ApplyShipmentDispatched + inventory consumption, derive the member
     status dictionary from the tracked shipments, call package.MarkDispatched, then exactly ONE
     SaveChangesAsync => one atomic DB commit covering every member update and the package
     transition (EF Core wraps a single SaveChangesAsync in one transaction; all member and package
     writes share the single FulfillmentDbContext).
NOT done deliberately: no BeginTransactionAsync around the loop (it would not make the Inventory
consumption atomic and would turn a retryable failure into a permanently stuck one), no silent
skipping of not-yet-dispatched members, no invented state transitions, no schema/migration change.
Traced external side effect: ConsumeInventoryForShipmentAsync -> IFulfillmentInventoryGateway ->
InventoryDirectory.ConsumeAsync runs on the Inventory module's own DbContext with ExecuteUpdateAsync
+ its own SaveChangesAsync (separate connection/transaction, physically outside the Fulfillment
transaction), and StockReservation.MoveTo throws inventory.reservation.not_active unless still Held,
i.e. ConsumeAsync is NOT idempotent. Wrapping it in the Fulfillment transaction would commit the
reservation but roll back the dispatch, and the retry would then fail permanently; consuming after
the commit would silently leak reservations. Therefore that half is BLOCKED and reported, not
papered over with an unsafe transaction hack.

GATE C — FINDINGS (design only, no mutation)
The state "package = Created + member = Dispatched" is NOT representable through the current public
API: CreateConsolidatedPackageAsync rejects non-Created members
(fulfillment.package.shipment_not_eligible) and direct member dispatch is blocked
(fulfillment.shipment.locked_by_consolidated_package). It could only be produced by the pre-repair
non-atomic loop, which is why the NeedsDispatch == false skip branch exists as defensive recovery
logic. Invariants: CancelConsolidatedPackageAsync IS allowed for a Created package (it releases the
lock) but does not fix the package; Shipment.CancelPreDispatch throws
fulfillment.shipment.cancel_invalid for a Dispatched member; CorrectTrackingAsync refuses dispatched
shipments; DeliverConsolidatedPackageAsync requires package Dispatched; a replacement package cannot
be rebuilt because member 1 is not Created.
