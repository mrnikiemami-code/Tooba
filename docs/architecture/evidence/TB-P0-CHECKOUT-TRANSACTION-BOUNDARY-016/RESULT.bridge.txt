RISK

R1 A multi-DbContext ambient scope is not a safe boundary here. 015 measured on this server (PostgreSQL
   17.10, max_prepared_transactions = 0) that a second enlisting connection inside one scope promotes it
   and the commit fails with 55000 "prepared transactions are disabled". F3 shows the existing submit path
   already holds several module connections in one scope. Whatever currently protects that path is
   provider/pool behaviour that 015 proved fragile, and must not be extended to the money path. No naive
   multi-DbContext TransactionScope is offered.
R2 Row locks cannot cross the PSP call (F1), so "keeping the hold" must be state, not locking.
R3 Gate input has no ownership binding: IInventoryPaymentHoldGate only proves the supplied distinct ids are
   Held and unexpired; a caller passing foreign Held ids gets Verified.
R4 The gate returns with its DbContext connection deliberately still open, invisibly to the scope owner; the
   next module DbContext in that scope is what triggers R1.
R5 Inconsistent time authority: reclaimer compares against an application-clock parameter, the gate against
   the database clock; skew can make a row simultaneously live-for-gate and release-eligible.
R6 For the online provider success arrives later through PaymentWebhookEndpoints
   (Webhooks/PaymentWebhookEndpoints.cs:19) and nothing owns the checkout in flight; only the TTL keeps stock.

REVIEW OF 015 (defects / subtle issues found)

2 EvaluatePaymentHoldGate and NormalizePaymentHoldGateIds are public static on the Infrastructure class

3 The fail-closed catch is narrow (PostgresException only, :86/:213); other provider failures propagate as an

4 HeldCount is a verdict projection, not a count: NotHeld always reports 0 and Verified reports

5 Guid.Empty is reported as "unavailable" rather than "invalid"; the contract does not distinguish a caller

6 No in-repo controlled lock-contention test; the decisive evidence came from an external throwaway harness

7 Duplicate/missing/NULL-TTL handling is tested only at the pure-verdict level; the SQL predicate
  (expires_at IS NULL OR expires_at > clock_timestamp()) and the = ANY($1) binding have no repository test.

Note: 015's guarantee is real but narrow — it proves liveness at one instant and holds the rows only until
the caller's transaction ends. It must not be presented as an end-to-end payability guarantee.

THE THREE GUARANTEES, SEPARATED

(a) Authorizing an attempt on valid reserved stock at one linearization point — ACHIEVABLE, but the gate
    alone does not create it: the verdict dies with its transaction, so the authorization is durable only
    if that same transaction also writes the durable fact protecting the stock. Verified-but-not-persisted
    is worth nothing.
(b) Keeping a hold during asynchronous PSP operation — NOT achievable with locks (R2); achievable by making
    the hold durable for a window that provably covers the PSP worst case (TTL extension/promotion written
    in the transaction of (a)), with the window longer than the provider timeout (U3) and the reclaimer
    poll interval.
(c) Reconciliation for late success — ALREADY owned by Order (F4); the gap is before the charge, not after it.

DECISION (one bounded next implementation task)

Do not implement a cross-module ambient scope, and do not put initiation inside a transaction. Make the
linearization point a single-connection, single-module Inventory write that both proves and extends, and
keep the PSP call outside any transaction.

Candidate: Inventory-owned atomic payability proof + hold extension.
1) One new Inventory Contracts member beside the 015 gate (same Contracts/Orders capability, no new error
   code) that inside a SINGLE Inventory-owned transaction (its own connection; no ambient scope required,
   so no enlistment and no promotion) proves every supplied distinct reservation is Held and unexpired
   under FOR UPDATE in deterministic order, then raises expires_at to max(existing, db_now + window) for
   exactly those rows, returning per-id Applied/Unavailable proof plus the effective deadline.
2) Order (already owner of the checkout and cycle) calls it before POST /v1/storefront/checkout/{checkoutId}/
   payments, deriving ids from its own persisted lines; Payment then initiates exactly as today, outside any
   transaction.
3) Keep the 015 gate unchanged for callers that genuinely own an ambient scope.

Pros: no distributed transaction (one connection, one module, one SaveChanges); no migration and no new
status (reuses expires_at and the existing promote semantics); no network call under locks; an unused
extension is harmless (reclaimed at the new deadline); cycle-status lag (F6) stops mattering because the
stock hold outlives the cycle row; (c) unchanged and already safe.
Cons: the stock is protected by a time window, not a lock, so the window must be sized from the provider
timeout; a failed initiation costs one window of availability; Inventory must refuse rather than invent a
deadline when the caller cannot supply the policy window.

Three essential tests: (1) all-or-none — one released/consumed/missing/expired id means no row extended and
no Applied proof; (2) idempotent and monotonic — a second application never shortens expires_at and never
lowers the deadline; (3) NULL-TTL preservation — a durable hold (expires_at IS NULL) stays NULL and is still
Applied. Plus one source guard extending task 015's guard file: the new method opens no ambient scope, uses
one connection, and is never called inside a TransactionScope.

Explicit refusal condition: STOP and return to the Architect instead of implementing if extending
expires_at requires a new column, a new status, a migration, or a new typed error code beyond the pinned
set; if any of the three tests cannot be written without a live Host or a running database; if the caller
must be a module other than Inventory (cross-module write); or if Host/Host.Tests would have to change. In
each case the correct next artefact is a durable claim/lease design (explicitly owned state), not a widened
transaction.
