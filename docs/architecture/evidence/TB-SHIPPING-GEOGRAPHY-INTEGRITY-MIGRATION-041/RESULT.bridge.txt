CYCLE REJECTION
Self-parent: the walk's anchor is the proposed parent, so when it equals NEW.id the first recursion row
already matches -> rejected (the Domain also rejects it earlier; the DB guard makes it unforgettable).
Indirect A->B->...->A: the walk enumerates the complete upward chain of the proposed parent, so the moved
node appearing anywhere in it is rejected. Because each edge is validated when written against the
committed graph plus the current transaction's own change, no path that closes a cycle can be inserted.

CONCURRENCY / RACE ARGUMENT (design argument, NOT an empirical proof)
(1) Mutual exclusion: every ancestry mutation takes the same transaction-scoped advisory lock as its
first action; PostgreSQL releases it at end of transaction and only after the committing transaction is
marked committed, so at most one mutation is inside the check at a time and a later acquirer observes
everything the previous holder committed.
(2) The walk must not take row locks and does not: the mutating statement already holds its own row, so a
locking read of another row would create a real lock cycle (T1 holds A wants B; T2 holds B waits for the
advisory lock held by T1). Plain reads never block on uncommitted rows, so the advisory lock stays the
only shared resource and mutual exclusion is deadlock-free by construction. Statically enforced: the
guard text contains no FOR UPDATE / FOR NO KEY UPDATE / FOR SHARE (verified).
(3) Ordering: if a cycle C could be committed, take the transaction T* whose edge of C committed last.
Every other edge of C is then committed and visible to the statements T* runs after acquiring the lock;
T*'s walk from its new parent follows the chain upward, reaches the node T* is moving, raises, and T*
aborts. Contradiction, so no cycle can be committed.
(4) The argument needs READ COMMITTED (fresh snapshot per statement). This is enforced, not merely
documented: REPEATABLE READ/SERIALIZABLE writes are refused with 0A000 instead of being accepted on a
potentially stale snapshot. Platform default is READ COMMITTED (ToobaNpgsql does not change the level);
the repo deviates deliberately only in Order checkout (ReadCommitted) and Wallet refunds (Serializable),
which is exactly why the precondition is enforced rather than assumed.
(5) Out of invariant scope: superuser DDL bypass (ALTER TABLE ... DISABLE TRIGGER,
session_replication_role = replica, manual DROP TRIGGER). No application write path can bypass the guard.
