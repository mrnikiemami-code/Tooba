HEADLINE
An Order-owned, checkout-bound preparation seam now exists as a building block:
IOrderPaymentHoldPreparationPort.PrepareAsync(OrderPaymentHoldPreparationRequest, ct). It authorizes through
the EXISTING Order ownership rule, derives the reservation set only from persisted order lines, checks
Order-owned reservation-cycle payability by wall clock before and after, takes the absolute deadline from the
already existing Payment-owned effective per-method hold policy, applies the 017 Inventory atomic all-or-none
extension for the whole set in one call, and never reports Prepared when the Order cycle closed. No endpoint,
no PSP, no wallet debit, no payment attempt, no Cart conversion, no Order write, no new cross-module contract
and no new error code. Works exactly inside the allowed budget: 2 new production files + 1 one-line
registration change.

WHAT THE SEAM GUARANTEES
At the instant Prepared returns: the checkout was owned by the caller under the existing Order access rule
(actor + cartId match + guest cart proof); every persisted line had a distinct reservation id; the Order
reservation cycle was payable with wall-clock time remaining BOTH before and after the call; and Inventory
proved every hold Held and unexpired by DATABASE time and committed the all-or-none extension to the
policy-derived deadline. The result reports RequestedDeadlineUtc, GuaranteedUntilUtc (weakest/earliest finite
resulting expiry, null when all reserved holds are durable), CycleNumber and CycleExpiresAtUtc.

WHAT IT DOES NOT GUARANTEE (not claimed)
 1. No cross-module ACID. The Order cycle and the Inventory hold expire INDEPENDENTLY in different modules and
    workers (014 measured 6-15 s per cycle); the two deadlines are reported side by side and never asserted
    to be aligned.
 2. No "no money after this instant" proof: the deadline can still elapse between the extension commit and the
    provider request, the cycle close worker may close the cycle, late callbacks and compensation remain
    Order/Payment's responsibility.
 3. No payment-attempt correlation: this task creates no payment attempt, so payment_attempt_id stays null and
    CorrelatePaymentAttemptAsync is not called here. That belongs to the future, separately authorized
    initiation step.
 4. No mode rule (OnlinePurchase vs RequestToReserve) was invented; only cycle payability gates.
 5. No PostgreSQL claim from fakes: the row-lock / all-or-none / monotonic-max semantics were behaviourally
    proven against real disposable PostgreSQL in 017 and are not re-proven here.
