2. SOURCE-TRACED ROOT CAUSE (Development-only seed ordering/coverage defect)
=====================================================================
Call chain on a modern Development startup (`Tooba:CatalogDemo:RunLegacyBootstraps=false`):

  Program.cs (IsDevelopment)
    -> DevelopmentSchemaMigrator.MigrateSchemaOnlyAsync
         => ApplyCoreAsync(services, seedCatalog: false)
            -> MigrateOrderedAsync(...)          // schema only
            -> if (!seedCatalog) return;         // *** returns before ANY module seed ***
       so SettingsFoundationDevelopmentSeedHost.ApplyAsync — which is what creates the Party
       development organizations via PartyOrganizationProfileDevelopmentSeed — is NEVER called.
    -> ContentDevelopmentSeedHost.ApplyAsync
    -> SupportDevelopmentSeedHost.ApplyAsync
         -> AdminDevActorBootstrap.EnsureAsync                       => actor + tenant#member tuple  (OK)
         -> AccessControlDevelopmentSeedPrelude.EnsureSupportSeedPrerequisitesAsync
              -> SellerDevContextBootstrap.EnsureAsync
                   -> creates seller-actor-a/b identities            (OK — that is why 3 users exist)
                   -> IPartyDevelopmentSeedGateway.FindDevelopmentOrganizationByDisplayNameAsync
                        => READ-ONLY; returns null because the Party demo orgs were never seeded
                   -> IPartyDevelopmentSeedGateway.FindDevelopmentMembershipSellerPartyAsync
                        => READ-ONLY over party.memberships; returns null because it is empty
                   -> `if (sellerA is null || sellerB is null) return;`  => returns WITHOUT Publish()
                        so ISellerDevContextStore.Current stays null
              (pre-fix) `if (seller is null) return null;`   <-- *** the defect ***
                        => IAccessControlDirectory.EnsureBootstrapAsync is NEVER invoked
                           => platform-admin role, its PermissionCatalog grants, the admin
                              assignment and the admin capability tuples are never created.
    -> WalletDevelopmentSeedHost.ApplyAsync

Evidence that this is the true cause and not an exception being swallowed:
  - "no exception" proof: zero Error-level records except the pre-existing, unrelated
    LanguageBootstrapHostedService advisories (which the Host logs and continues past); and
    zero "SupportDevelopmentSeed failed"/"WalletDevelopmentSeed failed" records. Program.cs wraps
    the Support/Wallet seeds in try/catch that LOGS on failure — nothing was logged.
  - "the gate, not the writer, is at fault" proof: AdminDevActorBootstrap writes its tuple through the
    SAME IAuthorizationTupleWriter and succeeded (dev-context 200), and SellerDevContextBootstrap
    creates its users through the SAME identity seam and succeeded (3 identities). The only step that
    was skipped is the one behind the `seller is null` early return.
  - "it is the Party seed that is missing" proof: party.parties holds only the unrelated
    "DEV-SEED OOS Seller" row and party.memberships is empty, exactly the two reads that
    SellerDevContextBootstrap performs. PartyOrganizationProfileDevelopmentSeed is invoked only from
    SettingsFoundationDevelopmentSeedHost, which MigrateSchemaOnlyAsync never calls.

So: the canonical platform-admin bootstrap was gated behind an unrelated demo-data precondition
(Party seller organizations) that the modern schema-only path deliberately does not create. The fix
must therefore decouple the canonical authorization bootstrap from demo seller data — NOT fabricate
roles/tuples, and NOT re-enable the broken legacy Catalog seeding.

3. MINIMAL FIX (one existing Development-only file, no bypass)
=====================================================================
File: src/backend/Modules/AccessControl/Tooba.AccessControl.Infrastructure/Development/AccessControlDevelopmentSeedPrelude.cs

  await _sellerDevContexts.EnsureAsync(ct);
  var seller = _sellerDevContexts.Current;
  IReadOnlyList<Guid> sellerPartyIds = seller is null ? [] : [seller.ActorA.SellerPartyId];

  await _access.EnsureBootstrapAsync(adminActorUserId, sellerPartyIds, tenantId, ct);   // ALWAYS the canonical logic

  if (seller is null)
      return null;                                                                     // only the Support demo seed stays gated

  await _access.SyncUserCapabilityTuplesAsync(seller.ActorA.ActorUserId, <seller scope>, ct);
  return new AccessControlDevelopmentSeedActors(...);

Boundary proof of "no bypass":
  - the ONLY thing called is the pre-existing canonical IAccessControlDirectory.EnsureBootstrapAsync —
    the same method the HTTP route (POST /v1/admin/access-control/bootstrap ->
    EnsureAccessControlBootstrapCommand) uses. No new permission ids, no hand-written inserts,
    no AllowAnonymous, no guard weakening, no capability tuple fabricated outside the directory.
  - with no known seller party it is simply passed an EMPTY seller list, so the seller-owner role /
    ceiling work is skipped exactly as before; only the platform-admin catalogue provisioning and the
    admin assignment/tuple sync (which are Party-independent) now run.
  - behavior for the Support demo seed is unchanged: it is still skipped (returns null) when the
    seller dev context is unavailable.
  - Production is untouched: this type is a Development seed prelude reached only from the
    IsDevelopment() block in Program.cs; nothing in the Production path resolves or invokes it.
  - the method stays idempotent: EnsureBootstrapAsync skips an existing platform-admin role and an
    existing admin assignment, reconciles missing catalogue grants, and SyncUserCapabilityTuplesAsync
    is a revoke-and-rewrite.
