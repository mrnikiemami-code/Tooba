ROW-LOCK AND AMBIENT-TRANSACTION EVIDENCE (isolated read-only harness)

Harness: temporary console app OUTSIDE the repository, Npgsql 8.0.7 against Development database
tooba_alpha on 127.0.0.1:5432. The live Development Host on :5088 was NOT stopped, rebuilt or
restarted, and was not touched at all; the harness only reads and takes row locks it rolls back.
Copied for reproducibility to evidence/probe/program.cs.txt. Server: PostgreSQL 17.10.
The xid/lock probes used the same FOR UPDATE shape without the status predicate, because the
Development inventory currently holds no live rows at all.

Observed:
- BINDING_ANY_COUNT=3                  Guid[] -> = ANY($1) array parameter binding works
- E_XID_ASSIGNED=True                  explicit connection transaction + FOR UPDATE => real block
- F_XID_ASSIGNED=False                 NO transaction + FOR UPDATE => implicit single-statement
                                       transaction, locks already released
- G_XID_ASSIGNED=True                  ambient TransactionScope + connection opened inside it =>
                                       Npgsql ENLISTED the connection
- J_NO_TRANSACTION_CONFIRMATION=0      shipped confirmation query, no transaction => fail closed
- K_AMBIENT_CONFIRMATION=1             shipped confirmation query, ambient scope => proceed
- H_COMPETING_FOR_UPDATE=BLOCKED_BY_HELD_ROW_LOCKS
                                       second backend with lock_timeout=750ms is blocked => locks
                                       persist BEYOND the statement and block other writers
- I_AFTER_SCOPE_FOR_UPDATE=NOT_BLOCKED_LOCKS_RELEASED
                                       after the scope ends => lock lifetime == caller transaction
Conclusion: row locks are taken inside the caller transaction, released exactly when it ends, and the
shipped confirmer discriminates that state from an implicit single-statement transaction.

NEGATIVE FINDING THAT CHANGED THE DESIGN (reported for the record)

The first implementation confirmed the guarantee via pg_locks granted locktype='tuple' rows. The
harness proved that observation unusable: pg_locks reported NO tuple locks in every case (explicit
transaction included), because PostgreSQL only materialises tuple-lock entries under contention. That
check would have made the primitive permanently return AmbientTransactionRequired. It was replaced by
a read-only txid_current_if_assigned() observation, which the harness shows is both reachable (K=1)
and discriminating (J=0).

INTEGRATION CONSTRAINT DISCOVERED

server attempted two-phase commit and failed (55000 prepared transactions are disabled,
max_prepared_transactions = 0 in Development). Callers must keep ONE connection per ambient scope when
using this gate. Recorded in the code documentation.
