## Cross-cutting observed facts

- Every authoring capability today is a **separate committing handler** and every one advances the same root
  `Revision`: `ReplaceRegionGroupsAsync`, `ReplaceGroupRateRowsAsync`, `ReplacePresentationAsync`,
  `ReplaceWeeklyScheduleAsync`, `ReplaceMethodSettingsAsync`, `ReplaceTypeAssignmentAsync`
  (`IShippingAuthoringDraftDirectory`). Each uses `expectedRevision` as its own optimistic token, so N browser
  PUTs cannot express one all-or-nothing Apply (decision section 9).
- Domain already separates **preflight** (pure, e.g. `PreflightRegionGroups`, `PreflightGroupRateRows`,
  `PreflightPresentation`, `PreflightWeeklySchedule`, `PreflightMethodSettings`, `PreflightTypeAssignment`) from
  **apply** (`Apply*` + one revision advance). That split is the natural reuse point for one composed save.
- `197-R1` lesson is binding: response composition must use facts validated before the write; no fallible
  catalog/registry/geography read after commit.
- Preview content languages (`PREVIEW_CONTENT_LANGUAGE_IDS = ["fa","en"]`) and store currency
  (`PREVIEW_STORE_CURRENCY = "IRR"`) are fixtures; TB-188 context is the only authority for both.
- `packaging`/`delivery` per row already exist in the draft contract; the real "packaging tab" and
  "operating schedule" dialogs belong to the **other** (legacy/coverage) method model and must not be merged.
