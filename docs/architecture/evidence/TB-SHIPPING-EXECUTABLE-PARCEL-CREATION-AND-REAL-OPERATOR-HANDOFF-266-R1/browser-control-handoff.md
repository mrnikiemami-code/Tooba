   `data-testid="admin-order-operational-create-01a1db20-ad98-7000-aa76-261f77230a71"` (44px tall).
   It opens the existing `AdminCreateShipmentModal` (`title="ایجاد مرسوله"`) showing the accepted group's
   read-only method / customer window / line quantity (1). Confirmed inside the modal with its
   «ایجاد مرسوله» submit.
   → Result: **one** `Created` parcel persisted, no second parcel, no toast on reload.
   Retained visual artifacts: `order-b-before-create-click.png` (the same forward control sitting on order B before
   any click) and `order-a-dispatched-tracking.png` (order A after the three steps). The authoritative
   end-state proof is the read contract and the served-page text reproduced below, not the images.

   opening the existing `AdminAssignShipmentTrackingModal` («ثبت کد رهگیری مرسوله»). The modal generated the
   internal identifier `TRK-01A1DB2C5F9F70008149360BCBC27C3A` and it was submitted through the modal's own
   «ثبت کد رهگیری» action.
   → Result: tracking stored on the same parcel, visible after reload.
3. **«ارسال»** — `data-testid="admin-order-shipment-dispatch-{shipmentId}"` for the `Created` parcel.
   Confirmed through the existing confirmation dialog.

## Internal tracking is not a carrier waybill

`TRK-…` is the internal **whole-parcel identity** from TB-257, generated by the existing tracking modal for a
task-owned manual/internal shipment. It is explicitly **not** a Tipax/post booking, no provider was called, and
no waybill number is claimed. The parcel's `carrierDisplayName` is the stored carrier label of the existing
shipment, nothing more.
