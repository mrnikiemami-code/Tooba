ROOT-CAUSE-1 (automatic tracking generated a used code):
`src/frontend/app/admin/admin-assign-shipment-tracking-modal.tsx` built the «تولید خودکار» suggestion locally as `TRK-` + `shipmentId.replace(non-alnum).slice(0,8).toUpperCase()` — the FIRST EIGHT HEX characters of the UUIDv7 shipment id, one 32-bit bucket that changes about every 65 seconds. Two parcels created in the same minute therefore received the SAME candidate. The button only fills the input; «ثبت کد رهگیری» posts that value through the ordinary assignment command, so the second parcel hit the real PostgreSQL unique index `ix_shipments_tracking_reference` and failed duplicate. Pressing Generate again re-derived the SAME deterministic value, which is why regenerating could never recover. The server had no automatic-allocation seam at all (candidate generation lived only in the browser), so no retry, reconciliation or reserve guarantee could exist.

FIX-1:
New `Tooba.Fulfillment.Contracts.Operations.FulfillmentInternalTrackingReference`: `ForShipment(shipmentId, attempt=0)` = `TRK-` + the WHOLE 32-character shipment identity (bounded `-N` retries, `MaxAllocationAttempts=5`, `MaxLength=128` = the real column ceiling), deterministic per parcel, `IsCanonicalSuggestion` marks attempt 0 as "automatic intent". New owning seam `IFulfillmentAdminOperations.AssignAutomaticTrackingAsync` → `FulfillmentAdminOperationsAdapter` → `FulfillmentDirectory.AssignAutomaticTrackingAsync`: (a) an existing reference is reconciled unchanged (never replaces a real code), (b) a candidate already owned by another parcel is skipped, (c) a real collision — `DbUpdateException` whose `PostgresException` is `23505` with `ConstraintName = ix_shipments_tracking_reference` — reverts ONLY that tracking assignment and moves to the next bounded candidate in the same scoped context, (d) every other persistence failure propagates unchanged (proven with a synthetic `23503` on a different index), (e) exhausted attempts fail closed with the existing `fulfillment.tracking.duplicate`. Both admin routes send canonical intent there (`AdminOrderOperationsOrchestrator.Fulfillment.cs`, `AdminOrderFulfillmentOperations.cs`); operator-typed values keep the strict inline + server duplicate validation; provider (CarrierApi/Tipax) identifiers are never overwritten or faked; no live provider call. Frontend mirrors the whole-id rule, the button restores this parcel's canonical candidate and the modal has a synchronous same-tick single-flight ref so a click burst sends exactly one request, retaining the operator value on refusal with one inline message.

ROOT-CAUSE-2 (shipped items still offered as a new parcel):
`Tooba.Order.Infrastructure/Integrations/Shipping/OrderCommittedCarrierShipmentFactsReader.cs` `ResolveFulfillmentEligibility` computed `remaining = item.QuantityPacked - openAllocated` and never subtracted `item.QuantityShipped`. A packed1/shipped1 group therefore still produced one executable line with `createParcelEligible=true`, while the owning create command refused and the create modal had nothing to select. Four further local copies of the same rule existed (order-detail composer, capability projector, orchestrator rules/projection, work-queue filters).

FIX-2:
New `Tooba.Fulfillment.Contracts.Operations.FulfillmentPackedQuantityAuthority`: `RemainingPackedQuantity(packed, shipped, openAllocated) = max(0, packed - shipped - openCreatedAllocations)`, `OpenAllocatedQuantity(...)` reading the same authoritative Fulfillment shipments (Created only, group-scoped). Now used by the facts reader, `AdminOrderDetailComposer`, `AdminFulfillmentCapabilityProjector`, `AdminOrderOperationsOrchestrator` rules/projection/fulfillment, `AdminOrderFulfillmentOperations` and `AdminFulfillmentQueueFilters`. ExecutableLines, remainingPackedQuantity, createParcelEligible and the owning blockers now agree; wholly shipped → no create; partial shipped + open allocation → only the real remainder; cancelled pre-dispatch allocation releases only its reservation; delivery never makes shipped quantity available again; sibling groups stay isolated. 249/253 exact-occurrence replay/reconcile still runs BEFORE these remaining-quantity gates (not modified), money and accepted evidence untouched. No migration, no schema change, no manual SQL, no backfill, no baseline/allow-list edit.
