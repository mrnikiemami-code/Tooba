DESIGN E AS LANDED
1. Durable journal `inventory.reservation_consumptions` (entity `ReservationConsumptionRecord`):
   `reservation_id` uuid PK (`pk_reservation_consumptions`, ValueGeneratedNever), `stock_item_id` uuid,
   `quantity` numeric(18,6), `consumer_key` varchar(128) NULLABLE, `consumed_at` timestamptz.
   Nullable key is deliberate: legacy callers are never silently given a fake ownership identity.
2. ONE real local Inventory transaction on the keyed path (`InventoryDirectory.ConsumeReservationAsync`):
   `BeginTransactionAsync` -> state-guarded CAS claim
   (`UPDATE inventory.reservations ... WHERE reservation_id=@id AND status='Held'`, must affect 1 row)
   -> guarded stock deduction on `inventory.stock_positions`
   (`reserved >= q AND on_hand >= q`) -> journal insert -> aggregate sync
   (`reservation.MoveTo(Consumed)` + `position.RecordConsumed` + `SyncQuantities`)
   -> single `SaveChangesAsync` (Inventory outbox row is written by the existing
   OutboxSaveChangesInterceptor in that same SaveChanges) -> `CommitAsync`.
   Any failure rolls back the claim, the deduction, the journal row and the outbox row together.
   The pre-existing immediate autocommitted `ExecuteUpdateAsync` deduction (the W7/W8 defect described
   in the parent evidence) is gone: the claim now happens inside the same physical transaction.
3. Replay truth table (proven, never assumed):
   - journal row present AND ConsumerKey ordinal-equal AND StockItemId equal AND Quantity equal
     => proven replay of the SAME consumer: returns success with NO new stock deduction.
   - journal row present with any mismatch (different consumer key, stock item, quantity)
     => typed `inventory.reservation.consume_mismatch`.
   - reservation already `Consumed` with NO journal row (historical/legacy consumption)
     => typed `inventory.reservation.consume_mismatch`; provenance is never invented and success is
     never synthesised. No backfill of historical Consumed rows.
   - racing loser re-reads the journal: proven replay returns, everything else conflicts.
   - blank/whitespace consumerKey => typed conflict BEFORE any write (cannot degrade to unguarded path).
4. Compatibility: `IFulfillmentInventoryLifecyclePort` gains an ADDITIVE member
   `ConsumeAsync(Guid reservationId, string consumerKey, CancellationToken)`. The existing unkeyed
   `ConsumeAsync(Guid, CancellationToken)` is unchanged in signature and in strictness (it stays
   strict and never becomes blanket-success) and now delegates to the same core with `consumerKey:null`.
   No existing caller was changed, so no caller is silently assigned fake ownership.
5. No new error code, no resx/catalog edit, no AMSC/guard/baseline weakening. `MoveTo` terminal-state
   semantics are preserved (the CAS enforces the same Held->Consumed rule in SQL).
