ROOT CAUSE A — F-063-1, malformed body surfaced as 500 platform.unexpected
- The five Shipping admin write routes bound the body as a minimal-API parameter (ShippingRatePolicyWriteRequest / ShippingCoverageGrantWriteRequest / the two active-request records). ASP.NET Core resolves that parameter BEFORE the handler runs, so an undeserializable payload (syntax-invalid JSON, non-Guid or empty GUID in scope, non-JSON content type, literal null) threw BadHttpRequestException outside the endpoint.
- SafeErrorMapper.Map has branches only for SemanticException, ValidationException and PlatformHttpException; everything else falls through to MapUnexpected() -> 500 platform.unexpected. A pure client-input failure therefore became an unexpected server error. 063 log-crud-063.txt probes S1/S2 are the reproduction.
- Global handler route rejected: SafeErrorMapper / ExceptionPresentationService / ToobaExceptionHandler are Host-owned global mapping and were explicitly forbidden without separate authorization; classifying BadHttpRequestException there would change every module at once.
- Endpoint-filter route rejected after empirical falsification: a throwaway minimal app proved that minimal-API argument binding runs BEFORE the filter pipeline, so an IEndpointFilter can never observe the binding failure. Evidence: binding failure returned the framework's own 400 and never reached a filter that would have answered 418.

ROOT CAUSE B — F-063-2, fresh Development database had zero canonical languages
- LanguageBootstrapHostedService is an IHostedService: it runs during host start before any commerce context is bound. It resolved LocalizationDbContext, whose factory calls ToobaNpgsql.ResolveForContext, which fail-closes with PlatformHttpException 503 platform.edition.unconfigured when ICurrentCommerceContext.Current is null.
- The assignment performed by DevelopmentSchemaMigrator.ApplyCoreAsync (ICommerceContextAssigner.Assign) lives in that method's own scope; the hosted service creates a different scope, so its accessor is fresh and empty. The resulting exception was swallowed by the service broad catch, logged at Error level, and the database stayed at zero languages. That is exactly why 063 had to create fa-IR manually over the admin API. Production is no better: the same service also cannot resolve a connection there, because no request context exists at startup either.
