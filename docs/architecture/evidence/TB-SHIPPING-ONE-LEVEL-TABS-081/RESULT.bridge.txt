B. ONE-LEVEL IDENTITY PROPOSAL
One merchant level means independently named, independently activatable delivery methods with no
service->option step anywhere in the merchant surface. The provider grouping survives only as HIDDEN internal
metadata (provider_kind) that is never rendered as a configurable second level. All six existing identities
keep their CURRENT composite code byte-identical, because that string is already persisted in
cart_shipping_drafts / checkouts / shipments and compared with OrdinalIgnoreCase at selection time:
post:standard (post/standard, active), post:express (post/express, INACTIVE), tipax:standard, tipax:express,
store_courier, in_person, snapp_courier (INACTIVE). Rules stated: never conflate the composite with the bare
service code; never erase historical order identity (no UPDATE of those columns); inactive stays inactive;
anchor identity on code, never on shippingServiceOptionId (which UpdateAsync re-creates); and new codes must
respect the NARROWEST persisted column, checkouts.shipping_method_code varchar(32). Existing records are NOT
migrated in 081.
