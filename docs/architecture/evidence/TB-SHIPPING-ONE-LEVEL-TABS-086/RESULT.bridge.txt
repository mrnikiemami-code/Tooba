MISSION A — SINGLE-LEVEL CONTEXT (authority mapping)
Method identity is the canonical persisted method_code (<=32 chars, one optional ':'). Its hidden
legacy binding is required to reuse the existing Shipping (service_code, option_code?) admin APIs.
The 085 public DTO deliberately omits that binding, and splitting method_code in the browser is
unsafe for optionless and composite identities. The narrowest authorized resolution was therefore
added server-side, Contracts-only, with no EF type leaking:

  GET /v1/admin/shipping-services/shipping-methods/one-level/{methodCode}/binding
  -> IFulfillmentAdminAuthorizer -> ResolveOneLevelShippingMethodBindingQuery
  -> IShippingOneLevelCatalogAdminRead.ResolveBindingAsync
  -> OneLevelShippingMethodBindingDto { gate, ready, resolved, methodCode, serviceCode?, optionCode?, isActive }

Hard guarantees enforced and unit-proven:
  * request carries ONLY methodCode; raw client serviceCode/optionCode can never substitute;
  * the pair comes exclusively from the catalog row's immutable legacy binding;
  * gate OFF => resolved=false and ZERO database queries (reader call count asserted = 0);
  * unmigrated catalog (Postgres 42P01) => ready=false, resolved=false, never 500, never fake success;
  * malformed/non-canonical code ('post:ex:press', 'post standard;drop', 'post:', blank, 'a!' etc.)
    is refused BEFORE any lookup, so it can never be normalized into a new identity;
  * canonical but absent code => resolved=false; 'tipax:express' is never split into (tipax, express);
  * handler publishes serviceCode/optionCode as null whenever Resolved is false, so a stray pair
    cannot leak even if a future implementation misbehaves;
  * provider_kind stays internal metadata and is absent from the wire shape.
No new selectable merchant level was created. No DI change was needed (the method lives on the
already-registered port). No Contracts change was needed.
