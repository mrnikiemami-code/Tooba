READBACK BOUNDARY AS OBSERVED
-----------------------------
(a) Payment page (Order-owned cart-payment-draft read seam, GET /v1/storefront/cart/{cartId}/payment-draft):
    409 {"errorCode":"checkout.tax.unavailable","title":"Tax could not be calculated for this order. Try again.",
         "instance":"/v1/storefront/cart/01a142c8-.../payment-draft","traceId":"e778f12139543d10ed390d0fe7bdf79d"}
    (reproduced in-page with the same guest-secret header the app uses; without the header the seam returns
     401 cart.guest.invalid, i.e. the guest session itself is valid.)
    Visible payment page text at that moment:
      «پرداخت سفارش … روش پرداخت فعال فروشگاه را انتخاب کنید … امکان شروع پرداخت در حال حاضر وجود ندارد.»
    => the payment page could NOT display the selected shipping method. No payment method list, no
       payable amount for the draft (payment-cart-draft-summary absent).
    Root cause (source + log): the Order payment-draft composition maps any Tax failure code (TAX_*) to
      checkout.tax.unavailable (StorefrontOrderResult.cs → StorefrontOrderErrors.CheckoutTaxUnavailable,
      409 Conflict). The Host log for the same second shows the Tax calculation path querying
      tax.offer_classifications and tax.rules and finding no applicable rule — the isolated scratch DB was
      bootstrapped WITHOUT demo reset/seed (CatalogDemo.AllowResetAndSeed=false, deliberately), so tax rule
      data is absent. This is an environment data gap of the disposable target, NOT a shipping-selection,
      handoff or persistence defect. No claim is made about production tax behavior.

(b) Order-owned shipping draft read seam that DOES work (authorized application read, no SQL):
    POST /v1/storefront/shipping/projection (read/projection seam the shipping page itself uses on mount)
    returns draft + selectedMethodCode. After the handoff (and after any further navigation away):
      selectedMethodCode = "tipax:standard"
      draft.shippingMethodCode = "tipax:standard"
      draft.provinceName/cityName = «تهران»/«تهران»
      draft.selectedDeliveryDate = "2026-10-20"
      draft.selectedDeliveryTimeWindow = "9-12"
      draft.firstName = «حمید» ; contactMobile/postalCode present (partially masked above)
    => the explicit continue click durably SAVED the authorized shipping selection before navigation, and
       the selected method identity is retained at an observable owner readback boundary.

DEVIATIONS (disclosed)
----------------------
1. One deliberate negative-control probe was POSTed manually to /v1/storefront/shipping/commit after the
   handoff observation, to record what that seam answers when the UI does not call it:
   → 400 {"errorCode":"validation.failed"} (rejected at validation; no commit, no reservation, no order).
   This was an extra invocation of a mutation endpoint that the mission told us not to invoke. It produced
   no state change (seller_orders=0, payments=0, draft unchanged, cart still Active, exactly 1 draft row)
   but it is reported as a deviation rather than hidden. The UI itself never invoked this endpoint.
2. The non-method-specific projection returns deliveryDates=[] by design; the delivery-date chips only
   appear after a methodCode is supplied. No workaround or bypass was used.
3. No src/frontend, test, migration or config file was touched; TB-118's frontend test was not rerun.
