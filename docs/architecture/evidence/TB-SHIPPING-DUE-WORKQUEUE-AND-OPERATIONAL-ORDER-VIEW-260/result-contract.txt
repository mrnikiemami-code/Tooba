Timing authority (one pure rule)
  AdminFulfillmentDispatchTimingAuthority.Classify(pending, inTransit, plans, explicit nowUtc)
    input = Order-owned durable accepted PlannedDispatch only (IOrderDispatchPlanFactsReader over the TB-256
            accepted-plan read model); the customer receiving date is NEVER an input.
    window = [open, close) in the accepted carrier zone, converted to instants.
  Buckets (mutually exclusive):
    Overdue     now >= close, or handoff day already past
    Today       handoff day == today in the carrier zone (Open or TodayNotOpen)
    Upcoming    handoff day strictly future
    Unspecified pending work with NO accepted plan (historical/legacy)
    InTransit   nothing left to prepare but a parcel is dispatched/in-transit/non-delivered
    NotQueued   delivered/cancelled with no open parcel
  Filters (deliberately overlapping, server-evaluated):
    dispatch_due        today-open + overdue            (سررسیدشده)
    dispatch_today      the whole today bucket          (ارسال امروز)
    dispatch_overdue    overdue only                    (عقب‌افتاده)
    dispatch_upcoming   strictly future                 (آینده)
    dispatch_unspecified no accepted plan                (موعد ارسال مشخص نشده)
  Counts are computed by the SAME engine over the SAME search/column-filtered set as the page, independent of
  the selected quick tab. Priority: overdue (earliest deadline first) -> today -> upcoming -> unspecified ->
  in-transit, tie-broken by handoff instant then row id.

Queue identity / target
  One row per physical work unit. Exactly ONE «عملیات ارسال» entry per row, no bulk dispatch, no duplicated
  child actions, no seller-aside duplicate. The entry carries locators only:
    /admin/orders/{checkoutId}/operations?fulfillmentId=…&shippingGroupId=…&from=queue&filter=…
  The selected quick filter travels with it so «بازگشت به صف کار» restores the same queue view.
  Timing columns are sortable server-side and deliberately NOT column-filterable: the query policy rejects a
  filter on dispatchBucket/dispatchDeadline instead of accepting and silently ignoring it.

Server-side wire contract
  Bucket and window state are PascalCase wire names (Today, TodayNotOpen, InTransit, NotQueued, None, …).
  The client normalises the token before any label is rendered (normalizeDispatchToken); an unknown token is
  shown verbatim rather than guessed, never a raw enum in the operator UI.

Shared operational view
  Route /admin/orders/[checkoutId]/operations renders OrderOperationsView (target facts + recipient frame)
  around the SAME AdminOrderItemsShippingPanel / AdminOrderOperationalDeliverySection the full order page
  renders: one component, one action owner, server capabilities, existing dialogs, retained envelopes.
  Absent financial surfaces: payment, settlement, refund, wallet, seller share.
  Exact target: the locator resolves to the matching group(s); an unresolvable locator is reported explicitly.
  A group with no accepted plan renders «موعد ارسال مشخص نشده» — never a derived or invented date.
