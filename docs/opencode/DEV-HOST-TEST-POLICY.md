# OpenCode development-host test policy — 2026-11-23 (owner decision)

Scope: development-only Tooba work (NOT staging, production, or a database holding non-test business data). Goal: reuse the EXISTING development Host and its EXISTING development database for ordinary safe connected tests. Do not waste time provisioning a fresh Host/DB for every attempt.

## Normal path (preferred)
1. Read the running development Host identity/port and actual DB connection identity (host, database, environment and **current code version**) BEFORE writes. If the DB target cannot be proven, STOP; never guess based on a port or environment label. Check whether other developers/test workers use this DB and whether the test can be scoped safely.
2. Reuse the currently running dev Host and same dev database. Never kill/restart other processes, overwrite the running Host, drop/recreate its DB, reset shared Catalog, or re-seed shared seller/admin roles merely to satisfy a test.
3. Generate a per-run unique prefix/IDs and tag or record EVERY created row, including dependent rows, so cleanup is ownership-exact. Preserve an independently recorded baseline for touched shared state. Prefer transaction rollback for tests that do not require committed reads; for committed-state tests, commit then independently read and clean ONLY owned test rows in dependency order, with before/after verification. No broad TRUNCATE, cascade across unknown owners, mass DELETE, or destructive demo reset.
4. Cleanup MUST run in finally-like code even on failure; prove no test-owned residual rows/side effects. Keep common fixture, normal dev data, shared principals and Catalog intact. Reuse fixture on next attempt rather than re-provision.
5. A real migration, database schema/permission mutation, destructive reset, concurrency-with-shared-side-effects, restart, or a proof requiring a fresh Host must NOT be forced onto the shared dev DB. Use existing explicitly authorized isolated fixture ONLY for those specific tests, or STOP and report the exact test blocked. Do not label unexecuted tests PASS. This policy does not retrospectively waive acceptance-matrix or migration evidence.
6. If the running dev Host does not contain the candidate source build / required schema, do NOT claim candidate-code verification using it. Report mismatch and use a preauthorized isolated verification target for that case, or BLOCKED. Do not silently redeploy/restart the common dev Host.
7. First transient fixture issue: inspect/fix only owned rows, no recreate. Never infinite re-seeding/re-provisioning loops. One actionable BLOCKER notice for material stall; follow the issued finite repair/verification budget. Always record actual elapsed time; tokens/cost when available.

## Legacy task compatibility
This policy is the owner's new prospective default. If a running task has a more restrictive immutably issued test isolation/teardown contract (e.g. 287), obey its existing contracted proof for any already-running final test unless a separate explicit bounded owner addendum specifies a SAFE alternative. In-flight migration/teardown proof must never be silently replaced with tests against an old common Host.
