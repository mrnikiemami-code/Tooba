# Tooba DEV execution policy — OWNER OVERRIDE 2026-11-24 (authoritative)

**The owner's existing development Host and existing development database are the sole default execution environment for all future Tooba tasks.** Never provision, create, clone, or start a NEW Host or a NEW database to run development tests, including migration, destructive Catalog reset, schema changes, concurrency, restarts, or test fixtures. Owner explicitly states the dev DB is entirely disposable TEST DATA and accepts destructive changes there. Prior instructions requiring isolated fixtures for migration/destructive tests are SUPERSEDED for this confirmed development environment; do NOT block solely because an operation is destructive on DEV, because Host must restart, or because a new fixture was previously mandated. This is a standing instruction until owner changes it.

## Executable procedure (same DEV Host + same DEV DB)
1. Identify and log exact current development host PID/binary SHA, actual DB name/server, tenant, environment, candidate source SHA, and test scope. Use existing Host/DB, never a newly provisioned one. Maintain only one active application Host on the configured development port; controlled restart/replacement of that same Host to execute candidate code is owner-authorized. Frontend development requests may briefly fail during this maintenance.
2. For schema changes or destructive tests, take or revalidate an existing restorable backup of the actual target DB (e.g. `pg_dump -Fc`, `pg_restore --list`, SHA256), preferably reuse the verified current baseline dump when its identity matches. Backup bytes stay local, outside Git. No repeated permission gate or new DB needed. A valid existing backup is enough. If verification fails, create one backup of the existing DB, not a new DB.
3. Apply required development-only migrations, demo resets, seed repairs, candidate deployment, and database test mutations DIRECTLY to the confirmed existing DEV DB within a bounded run. Do not let unaccepted migration status by itself prohibit dev-only verification; record exact migration and its effect, and roll back via verified restoration when needed. Never falsely use running old code as candidate proof. Do not restart or kill arbitrary processes; target only verified task-owned development Host PID.
4. Test against actual candidate Host + dev DB, using independent SQL/API/UI oracles and true PASS/FAIL/NOT_RUN. One preflight, one consolidated connected test, at most one consolidated fix and one final rerun. No repetitive boot/provision/seed loops or another task simply to obtain an environment.
5. After destructive tests, return the existing development Host/DB to a known healthy state: restore verified backup if that is needed to preserve baseline, restart original Host or documented desired candidate, verify Host/frontend and core DB counts. Preserve evidence and backup. If restore fails, report blocker with recovery details rather than claiming success.
6. **Only exceptions**: never touch production, staging, unknown DB identity, user data outside the expressly designated disposable Tooba development DB, or unrelated services. If target identity cannot be proven or a backup cannot be validated for an irreversible operation, STOP with exact reason. Real product failures can remain BLOCKED; do not fabricate acceptance.
7. Root `AGENTS.md`, `.cursor`, non-dev systems and unrelated modules remain protected. This owner override changes environment/test permissions, NOT module ownership, architecture acceptance authority, or requirements for actual test evidence.

# OpenCode development-host test policy — 2026-11-23 (owner decision)

Scope: development-only Tooba work (NOT staging, production, or a database holding non-test business data). Goal: reuse the EXISTING development Host and its EXISTING development database for ordinary safe connected tests. Do not waste time provisioning a fresh Host/DB for every attempt.

## Normal path (preferred)
1. Read the running development Host identity/port and actual DB connection identity (host, database, environment and **current code version**) BEFORE writes. If the DB target cannot be proven, STOP; never guess based on a port or environment label. Check whether other developers/test workers use this DB and whether the test can be scoped safely.
2. Reuse the currently running dev Host and same dev database. Never kill/restart other processes, overwrite the running Host, drop/recreate its DB, reset shared Catalog, or re-seed shared seller/admin roles merely to satisfy a test.
3. Generate a per-run unique prefix/IDs and tag or record EVERY created row, including dependent rows, so cleanup is ownership-exact. Preserve an independently recorded baseline for touched shared state. Prefer transaction rollback for tests that do not require committed reads; for committed-state tests, commit then independently read and clean ONLY owned test rows in dependency order, with before/after verification. No broad TRUNCATE, cascade across unknown owners, mass DELETE, or destructive demo reset.
4. Cleanup MUST run in finally-like code even on failure; prove no test-owned residual rows/side effects. Keep common fixture, normal dev data, shared principals and Catalog intact. Reuse fixture on next attempt rather than re-provision.
5. A real migration, database schema/permission mutation, destructive reset, concurrency-with-shared-side-effects, restart, or a proof requiring a fresh Host must NOT be forced onto the shared dev DB. Use existing explicitly authorized isolated fixture ONLY for those specific tests, or STOP and report the exact test blocked. Do not label unexecuted tests PASS. This policy does not retrospectively waive acceptance-matrix or migration evidence.
6. If the running dev Host does not contain the candidate source build / required schema, do NOT claim candidate-code verification using it. Report mismatch and use a preauthorized isolated verification target for that case, or BLOCKED. Do not silently redeploy/restart the common dev Host.
7. First transient fixture issue: inspect/fix only owned rows, no recreate. Never infinite re-seeding/re-provisioning loops. One actionable BLOCKER notice for material stall; follow the issued finite repair/verification budget. Always record actual elapsed time; tokens/cost when available.
